# 注释

## 核心前提

- 当代码本身没有办法或很难通过一种显而易见的方式表达它的**意图、功能、使用限制、内在结构**时，才需要写注释。
- 否则，应尽量用更优秀的**代码**来表达——代码是唯一决定程序行为的事实，注释越少，维护成本越低。

## 单行注释

### 何时该写（推荐情形）

> 以下情形仅供参考，不涵盖所有情况

- 提供信息：编写时决策的上下文、程序此处易遗漏的重要上下文、单行代码中细微值得说明之处
- 解释不寻常实现的意图（含作者的权衡）
- 阐释陌生代码：小众外部 API 库的调用规则、项目内不常见用法（判断范围是项目内）
- 警示后人：防止同类原因再次导致 BUG
- TODO 说明：占位并给出初步编写方向

### 写法规则

#### 规则 1：注释短，贴在代码旁

注释放在被解释代码的同一行，或紧邻的正上方一行；不要挂一段长文在代码上方。

不要：

```ts
const previousRootId = graphPath.value[0]
// 日志生命周期 = 根图谱：跨越到不同根图树时重置操作日志与 redo 栈；
// 同根图树内导航（子图↔根图）共享同一份日志，不清空。
// graphPath 为空（链断裂防御）时重置条件不成立，不重置。
if (path.length > 0 && previousRootId !== undefined && previousRootId !== path[0]) {
    operationLog.value = { entries: [], cursor: -1 }
    redoStack.value = []
}
```

而要：

```ts
// 生命周期：根图谱 = 日志
const previousRootId = graphPath.value[0]
if (path.length > 0 && previousRootId !== undefined && previousRootId !== path[0]) {
    operationLog.value = { entries: [], cursor: -1 }
    redoStack.value = []
}
```

#### 规则 2：一行一义，每行标注主题

多个要点拆成多行，每行只讲一个点，并在行首标注主题词。

不要：

```ts
// 跨 item 状态连续：同一图被多个 item 修改时，后续基于前一个操作后图数据的结果。
// toRaw 解包 Pinia reactive proxy——引擎 createReversal 内部 structuredClone
// 无法克隆 proxy（旧快照代码同为该原因改用 JSON 序列化），此处统一解包。
const inputGraph = toRaw(latestGraphs.get(item.graph.id) ?? item.graph)
```

而要：

```ts
// inputGraph：同一图被多个 item 修改时，后续基于前一个操作后图数据的结果。

// toRaw: 解包 Pinia reactive proxy
// 因为引擎 createReversal 内部使用 structuredClone 无法克隆 proxy
// 所以在此处统一解包。
const inputGraph = toRaw(latestGraphs.get(item.graph.id) ?? item.graph)
```

#### 规则 3：删掉代码已表达的内容，只说代码表达不了的部分

不要复述代码显而易见的逻辑，删掉多余的解释。

不要：

```ts
const { graph: resultGraph, validation } = applyBatch(inputGraph, item.operations, {
    // undo/redo 恢复型逆元批跳过前提校验（正向用户操作默认校验）
    skipValidate: options?.skipValidate,
    // recordLog: false（undo/redo 执行）时逆元已在日志中，无需再收集——跳过回调
    //（引擎 options?.onBeforeEachOperation?.() 对 undefined 天然零行为）
    onBeforeEachOperation: options?.recordLog === false
        ? undefined
        : (op, graphBeforeOp) => {
            // 图级操作由 registry_effects 在第三阶段正/逆向执行，不构造逆元
            if (op.type === 'add_graph' || op.type === 'delete_graph') return

            // 每 op 的逆元数组保持内部执行序（如 delete_node → [add_node, add_edge] 不动）；
            // createReversal 抛异常（正常流程不可达）时自然传播——
            // applyBatch Phase 2 中断 → 整批不执行不记录不持久化
            perOpReversals.push(createReversal(graphBeforeOp, op))
        },
})
```

而要：

```ts
const { graph: resultGraph, validation } = applyBatch(inputGraph, item.operations, {
    skipValidate: options?.skipValidate,  // 由 undo/redo传入，以跳过校验
    onBeforeEachOperation: options?.recordLog === false
        ? undefined  // undo/redo 执行时不收集逆元（日志已有）
        : (op, graphBeforeOp) => {
            if (op.type === 'add_graph' || op.type === 'delete_graph') return  //  图级操作由 registry_effects 在第三阶段正/逆向执行
            perOpReversals.push(createReversal(graphBeforeOp, op))
        },
})
```

不要：

```ts
// 操作级逆序：op 间逆序（后执行先撤销）——perOpReversals.reverse().flat()，
// 不再对打平数组整体 reverse（那会翻转单 op 逆元内部序，破坏恢复依赖）
if (perOpReversals.length > 0) {
    reversalItems.push({
        graphId: item.graph.id,
        operations: perOpReversals.reverse().flat()
    })
}
```

而要：

```ts
// 收尾：单次 Item 逆元收集
if (perOpReversals.length > 0) {
    reversalItems.push({
        graphId: item.graph.id,
        operations: perOpReversals.reverse().flat()  // 逆序收集并打平，保证 undo 时正向执行顺序
    })
}
```

不要：

```ts
// 注册 applyBatch 执行后的结果图（induce 空壳经后续 add_node 填入）；
// 该图未作为 item 输入（deconstruct 空壳即完整图）时回退 operation.graph
const builtGraph = latestGraphs.get(operation.graph.id)
const targetGraph = builtGraph ?? operation.graph

applyAddGraph(graphRegistry.value, targetGraph)

// 未进入 latestGraphs 的图（非 item 输入），
// 此处补齐持久化——软删撤销 / 刷新存活均依赖持久化数据仍在
if (!builtGraph) {
    saveGraph(targetGraph)
}
```

而要：

```ts
const builtGraph = latestGraphs.get(operation.graph.id)
const targetGraph = builtGraph ?? operation.graph  // 有由批操作构造完的图就用它，否则用 add_graph 自带的图

applyAddGraph(graphRegistry.value, targetGraph)

// 补持久化：未进入 latestGraphs 的图（不在第四阶段持久化范围内）
// 比方说 Deconstruct 后得到的图
if (!builtGraph) {
    saveGraph(targetGraph)
}
```

## TSDoc 注释

### 规范

核心原则：根据实际需要灵活选择 TSDoc，因为它很贵。

TSDoc 是微软提出的 TypeScript 文档注释标准（tsdoc.org），VS Code / vue-tsc 原生识别。tag 分三类：

- **Block tags**（块级，独占一行）：`@param` `@returns` `@remarks` `@typeParam` `@deprecated`（Core 必备组）；`@example` `@defaultValue` `@throws` `@see` `@inheritDoc`（Extended 扩展组）
- **Modifier tags**（修饰，标记 API 性质，放注释底部单行）：`@internal` `@public` `@alpha` `@beta` `@experimental` `@override` `@sealed` `@virtual` `@readonly` 等
- **Inline tags**（行内，花括号形式）：`{@link}` 等

关键概念：

- **summary 不是 tag**——注释里第一个 block tag 之前的那段文本即 summary（简要说明），无需 tag。
- **`@remarks`** 承载 summary 之外的全部细节，用 markdown 语法书写。
- **官方没有 `@summary` / `@precondition` / `@sideEffects` 这类 tag**——调用契约、前置条件、边界情况、副作用、设计动机，语义上全部归属 `@remarks`。
- **`@returns` 描述返回值含义，含成功 / 失败的不同取值**——"什么时候返回 false"这类返回值条件归 `@returns`，不归 `@remarks`。
- **`@throws`** 每一种异常类型单独一个 block，块首一行只写异常名。
- **`@privateRemarks`** 是"仅供维护者、文档工具须剔除"的备注，与对外展示的 `@remarks` 区分。

书写规范：

- tag 名固定英文 + camelCase（`@defaultValue` 非 `@defaultvalue`）。
- `@param` 语法：`@param name - 描述`（名 + 连字符 + 描述）。
- `@returns` 带 s（`@return` 是 JSDoc 旧拼写，TSDoc 不认）。
- 顺序惯例：summary（首段）→ `@remarks` → `@param`/`@returns`/`@throws` → `@example` → 底部 modifier。
- block tag 之间以空行分隔——空行 = markdown 段落分隔，不加则 LSP hover 会把标题与内容挤成一段。
- tag 名固定英文，描述内容尽可能用自然语言书写。

tag 与文字信息的匹配：

注释里的每一段文字，都要落到它对应的 tag 上，不要自创标题。对照如下：

| 文字信息类型 | 归属 |
| --- | --- |
| 一句话职责（做什么、返回什么核心含义） | summary（隐式，首段） |
| 实现机制 / 委派 / 前置条件 / 边界情况 / 副作用 / 设计动机 | `@remarks` |
| 每个参数：是什么、从哪来、有无特殊规则 | `@param` |
| 返回值含义（含成功 / 失败不同取值） | `@returns` |
| 可能抛出的异常类型（每种一个 block） | `@throws` |
| 泛型参数 | `@typeParam` |
| 仅供维护者、对外剔除的说明 | `@privateRemarks` |
| 代码示例 | `@example` |
| 相关引用 / 跳转 | `@see` / `{@link}` |

反例（来自真实代码的教训）：自创「说明 / 模型 / 调用契约 / 参数 / 返回」五段式标题，而非使用标准 tag——正确映射见上表。

几点说明：

1. TSDoc 本质是 markdown。tag 内容可含 markdown 元素与 inline tag（`{@link}`）。
2. 文件头注释的编写可以直接参考这里
3. 公开函数一定要有 TSDoc，非公开函数、接口等按需决定
4. 文件头不要写文件名
5. 注释应该按照其所在的地方有针对性

TSDoc 基础模板：

```ts
/**
 * <summary：一句话本质，无需 tag。会被单独展示在索引/列表页，须独立读懂；
 *  不重复签名已展示的类型/参数信息，只讲"是什么/做什么">
 *
 * @remarks
 * <详细说明：动机、调用契约、前置条件、边界情况、副作用。一个 tag 最多解释一个内容>
 *
 * @param paramName - <是什么 / 从哪来 / 特殊规则>
 * @returns <返回值说明>
 */
```

完整示例：

```ts
/**
 * 浮空窗定位引擎的实现：给定锚点与浮窗 DOM，决定浮窗的摆放方位与视口边缘行为。
 *
 * @remarks
 * 是 cytoscape-popper 注入的定位插槽。调用契约：
 * - 调用方须持有句柄，在关闭 / 切换目标 / 卸载时调 destroy
 * - update 随 pan/zoom/position 高频触发
 *
 * @param ref - 锚点引用对象（cytoscape-popper 注入）
 * @param content - 被锚定的内容元素
 * @returns 可重算的定位句柄 { update }
 *
 * @example
 * ```ts
 * const handle = attachElementPopper(cy, nodeId, el)
 * handle.update()   // 目标位移后重算
 * handle.destroy()  // 关闭时清理
 * ```
 */
```

### 写法规则

#### 规则 4：summary 一句话说本质，别复述实现

summary（第一段）只写"是什么"，不写实现细节。

不要：

```ts
/**
 * 说明：
 *
 *     撤销最近一次操作（日志驱动）：对当前 cursor 指向的 entry 执行逆元，
 *     成功后游标回退到 parentIndex 并把 entry 索引推入 redoStack。
 *
 * 调用契约：
 *
 *     1. 无历史（cursor < 0）→ false。
 *     2. 逆元执行失败（防御通道，正常不可达）→ false，游标不动。
 *     3. 成功后执行视图一致性检查（graphView 可能因撤销含 add_graph 的批而被注销）。
 */
function undo(): boolean {
    if (operationLog.value.cursor < 0) {
        return false
    }

    const entryIndex = operationLog.value.cursor

    if (applyEntry(entryIndex, 'reverse')) {
        redoStack.value.push(entryIndex)
        ensureViewConsistency()
        return true
    }

    return false
}
```

而要：

```ts
/**
 * 撤销最近一次操作。
 *
 * @remarks
 * 对当前 cursor 指向的 entry 执行逆元，成功后游标回退到 parentIndex
 * 并把 entry 索引推入 redoStack。
 */
function undo(): boolean {
    if (operationLog.value.cursor < 0) {
        return false
    }

    const entryIndex = operationLog.value.cursor

    if (applyEntry(entryIndex, 'reverse')) {
        redoStack.value.push(entryIndex)
        ensureViewConsistency()
        return true
    }

    return false
}
```

不要：

```ts
/** 锚定目标 id：draft 窗 → 预览节点 nodeId；编辑窗 → 实体 id（node.id / edge.id）。 */
const anchorTargetId = computed<string | null>(() => {
    if (draftNode.value) {
        return draftNode.value.nodeId ?? null
    }
    if (floatingData.value) {
        return floatingData.value.id
    }
    return null
})
```

而要：

```ts
/** 浮空窗的两个锚定目标 id */
const anchorTargetId = computed<string | null>(() => {
    if (draftNode.value) {
        return draftNode.value.nodeId ?? null
    }
    if (floatingData.value) {
        return floatingData.value.id
    }
    return null
})
```

#### 规则 5：分点结构化，别写大段散文

多要点用列表 / 序号组织，别写成连续长句段落。编号统一用 markdown 有序列表 `1. ` 风格，不用带圈数字 ①②③。

不要：

```ts
/**
 * 模型：
 *
 *     统一对称撤销模型：undo = 逆序执行 entry 的全部逆元，redo = 正序执行
 *     entry 的全部操作。图级逆元以兑现逻辑参与（add_graph → 整体注销，
 *     内容随图消失不单独动数据；delete_graph → 从持久化完整恢复注册），
 *     图内逆元以操作参与（createReversal 精确反转）。
 *     三段式（①→②→③）即该逆元序列的代码化：delete_graph 逆元最先（图内
 *     逆元执行前目标图需在 registry）、图内逆元居中、add_graph 逆元最后
 *     （正向批首新建的图撤销放末尾）。② 跳过 added 图逆元正是"add_graph
 *     逆元 = 整体注销"语义的自然结果。
 */
```

而要：

```ts
/**
 * 统一对称的撤销模型：
 * - undo = 逆序执行 entry 的全部逆元；
 * - redo = 正序执行 entry 的全部操作。
 *
 * 图内与图级以各自形态参与同一序列：
 * - 图内逆元：操作对象（createReversal 精确反转）
 * - 图级逆元：兑现逻辑
 *   - add_graph 的逆元：整体注销（内容随图消失，不单独动数据）
 *   - delete_graph 的逆元：从持久化完整恢复注册
 *
 * 三段式（1 → 2 → 3）即该逆元序列的代码化，顺序由执行依赖决定：
 * 1. deleted 恢复 —— 最先（图内逆元执行前目标图需在 registry）
 * 2. 图内逆元   —— 居中
 * 3. added 注销 —— 最后（正向批首新建的图，撤销放末尾）
 *
 * 第 2 步跳过 added 图逆元是"add_graph 逆元 = 整体注销"的自然结果——
 * 撤销建图 = 原子整体消失，图内内容随图消失。
 */
```
