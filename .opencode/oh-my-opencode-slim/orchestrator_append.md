## 不确定决策标记规则

### 核心规则

在项目开发过程中，你可以自行做出开发决策。但如果你尝试自行做一个决定时，**上下文中没有经过用户明确同意**或**现有文档里没有明确表达**，则：

1. **正在做的时候对那个决定进行标记**——在任务进行中就该意识到并记录
    → 如果你是Orchestrator，记录方式见 `@planning-with-files` skill：写入 `发现.md` 的"不确定事项"小节。否则直接在 task result 中报告不确定项。
2. **任务结束后统一告知用户**——呈现发现文档让用户确认，不要藏到代码里等人发现
3. **子任务向上冒泡**——以 try-catch 的机制返回到最顶层的Orchestrator，让用户做最终判断
4. **不得隐藏**——任何 Agent 自己觉得不确定的决策都不准试图隐藏

### 委派规则

这条规则在派发任务给 `@fixer`、`@oracle`、`@designer` 时，也必须在委托指令中明确告知他们遵守。他们必须在 task result 中报告不确定项，由编排者收集后写入发现文档。

## Git 提交格式

**全英文**。第一行为摘要行（`动词 + 模块 + 目的`），后续逐条罗列改动目的（不含具体文件名）：

规则：

1. 摘要行：一句话说清做了什么
2. 空一行后列表罗列改动项，每项 `- 动词 模块或作用域：具体改动描述`（禁止罗列具体文件名）
3. 改动项按模块分组，同模块相邻
4. 末尾附 `Co-Authored-By` 行（填入OpenCode）

**粒度原则**：宁可偏小，不偏大。每个提交尽可能只包含一个逻辑独立的变更（原子化提交）。同一文件的多个逻辑变更应通过 `git add -p` 拆到不同提交中。

**摘要行长度规则**：
- 尽量不超过 **50 字符**（Git 官方软限制）。超过说明本次提交体量可能偏大，应提示用户。
- 超过 **100 字符**，必须重新审视：是否需要拆分提交？摘要能否提炼？

## Git 提交权限

| 行为 | 允许 | 禁止 |
|------|------|------|
| 在对话中说明改动、解释 diff | ✅ | |
| 未经用户明确许可执行 `git commit` | | ❌ |
| 未经用户明确许可执行 `git push` / `git rebase` / `git reset` 等变基/推送操作 | | ❌ |
| 经用户检查并明确许可后提交 | ✅ | |

规则：

1. **AI 不得在未经用户明确许可的情况下执行任何 git 提交或推送类操作。** 即使改动已经通过测试，也必须等待用户检查并给出明确许可。
2. **AI 可以主动展示 `git status`、`git diff` 和测试结果**，帮助用户做提交决策。
3. 用户说"帮我 commit"或"提交"时，仍需先展示 diff 供用户确认，再执行。
