# 利用文档进行开发规划

用持久化的 markdown 文件作为你的"磁盘上的工作记忆"。

## 何时使用此模式

**适用场景：**
- 多步骤任务（3 步以上）
- 调研任务
- 跨多次工具调用的任务

**跳过场景：**
- 简单问题
- 单文件修改
- 快速查询

## 开发启动协议

**每次开始开发的第一件事：**

1. 执行 git diff 命令并读取最近一次 commit 日志，了解当前工作目录状态
2. 查找并读取对应的 `*步骤规划.md` 和 `*发现.md`，确定当前进度
3. 如果存在标记 `⏳` 的步骤，确认该从哪里继续
4. 如果没有规划文件，等待用户指示后再开始

## 两种核心文件

| 文件 | 包含的内容 | 何时更新 |
|------|------|---------|
| `步骤.md` | 步骤划分、完成标志、当前进度、重要决策 | 每个步骤完成后 |
| `发现.md` | 历史遗留BUG、可以改进的地方、相关报告 | 有任何发现后 |

注1：若文件过多，可以对大的阶段创建对应的文件夹，然后再创建小的阶段文件
注2：文件下的内容并非锁死只能是这几项，可以随时按照用户的新的需求进行删减或者引入新类型的内容

### 步骤规划文件

* 定义：在具体开发任务前 AI 与用户共同商讨过后制定的文件
* 创建时机：在开发开始前，先创建此文件
* 具体内容：
  * 步骤划分：
    * 步骤粒度（step 1、 step 1.1、 step 1.2、step 2...）
    * 步骤标题行标记状态：`✅` / `⏳`
      * `⏳`：当前正在进行的步骤
      * `✅`：已经完成的步骤
      * 没有标记的步骤默认是 Pending，不需要写标记
    * 每个步骤的完成标志
    * 难度：不确定度 / 算法复杂度 / 工作量
      * 用 `🟢`（低）/ `🟡`（中）/ `🔴`（高）标记难度等级
  * 重要决策：
    * 待确定决策：开始写代码之前需要用户确定的决策
    * 已确定决策
* 额外文件：总纲文件（前缀编号00）
  * 包含：
    * 开发范式指导
    * 总体方向
    * 开发步骤文件链接
    * 等

### 发现文件

* 定义：在开发过程中完全由 AI 顺手发现并记录的文件
* 创建时机：在开发过程中发现任何问题或改进点时，立即按步骤创建或更新此文件
* 具体内容：
  * 历史遗留 BUG：不是本次开发阶段产生的 BUG，但在本阶段中发现了
  * 可以改进的地方：如
    * 代码结构不合理
    * 代码可读性差
    * 代码可以简化
  * 相关报告（对应于 BUG 和可以改进的地方）：
    * 发现的内容
    * 发现的具体位置（文件名 + 行号）
    * 建议的解决方案
  * 不确定事项：
    * 定义：开发过程中临时决策，并且已经写出代码，而自己没有太大把握，需要用户确认的决策
    * 如：
      * 自己临时决策的架构设计，但不确定是否合理
      * 猜测某个用户对产品的使用意图
      * 对自己写的代码质量某一些地方没有信心
      * 等
    * 记录问题内容 + 具体影响 + 状态标记（待确认 / 已确认）+ 建议（可选）
* 发现文件与步骤规划文件的关系：
  * 优先在发现文件中记录 BUG 与优化项
  * 在用户确认后，将发现内容写入步骤规划文件中，作为开发任务的一部分，如：
    * 严重 BUG 修复
    * 具有显著收益的重构

### 步骤文档写作规范

* 语言风格与文档权威性
  * 已确定决策用断言式，**禁止**"建议""可以""或许"等软词
  * 待确定决策才允许用建议式，且**必须**用引用框隔离
  * 设计文档（`docs/设计/`）已覆盖的概念，步骤文档**只能溯源引用**，**不得**重新定义或改写语义
  * 涉及未经用户确认却自主推测设计意图的步骤，**必须**标注 `设计文档依据：docs/设计/XX.md §章节`
  * 无上游来源的技术决策**不得**写入步骤文档，改入发现文档的"不确定事项"
* 结构的标记
  * 步骤标题行用 `✅` / `⏳` 标记状态，未标记默认 Pending
  * 决策块分两种语气：
    * 已确定决策：直接陈述规则 + 理由（如需）。理由只解释"为什么这样"，不解释"为什么不那样"
    * 待确定决策：`> **Qn**：问题` → `**建议**：答案。理由：...`。决策权显式留给用户
  * 子任务表表头用 `子任务 / 内容 / 约束`。"约束"列承载红线，不是附注
  * 每个步骤**必须**有验收标准，形式为可勾选的事实断言列表。无验收标准的步骤**不得**标记 Complete
* 代码与图示
  * 文件路径 + 行号锚定（如果明确能定位到行）（格式：`file.ts:NNN`）
  * **禁止**贴大段代码实现细节
* 内容规范
  * 纯工程实现选择（数据结构、命名等）**尽量不**进入步骤文档
* 通用的md格式：
  * 步骤（如step 1）采用二级标题
  * 子步骤是标题（三级标题）
    * 某步骤实施过程中发现的BUG，从发现文档中提取过来，且需要进行的修复也算子步骤
  * 重要决策不算标题，但进行加粗

### 发现文档写作规范

* 语言风格与写作权归属
  * 事实陈述。记录"看到了什么"，**不**记录"决定了什么"
  * 决策权完整留给用户
  * 编排者是唯一写入者
* 组织方式
  * 发现文档内部按其所属步骤下子步骤归属分组
  * 每项独立成节
* 三种内容的发现写作规范
  * 历史遗留 BUG：纯事实。最少包含：`位置` + `现象` + `后果`
  * 可改进点：事实 + 可选建议。建议**必须**用 blockquote 隔离
  * 不确定事项：
    * 最少包含：`问题` + `状态：⏳ 待确认/✅ 已确认`。
    * 可选包含：`影响`、`建议` + `理由`。建议**必须**用 blockquote 隔离
* 引用与禁止
  * 只向下锚定代码（`文件:行号`）。
  * **不**写验收标准，**不**写子任务表，**不**写步骤编号体系。
* 确认后流转
  * 用户确认后的发现项，进过与用户协商后，编排者可以将其写入步骤文档作为正式任务
  * 发现文件中对应条目状态改为 `已确认`。

## 典型工作流

### 基本框架

* 规划
  * 操作对象：步骤文档
  * 执行者：@orchestrator（结构决策不委托）
  * 前置探查（按需，@orchestrator 缺乏上下文时触发）：
    * @explorer 探查代码现状与依赖
    * @librarian 查外部库 API，影响子任务拆分
  * 产出：步骤划分 + 完成标志 + 待确定决策 + spec
    * spec = 完成标志 + 涉及文件 + scope guard（禁止修改的文件/函数）
    * spec 是贯穿执行与验证的契约，三阶段共用同一份
* 用户确认
  * @orchestrator 呈现 spec + 待确定决策，暂停等待用户确认
  * 用户确认后进入执行；用户要求调整则回规划
  * **禁止**未经确认直接进入执行
* 执行
  * 操作对象：代码（少数情况下可能是文档）
  * 机械实现 → @fixer（spec 作为实现指令，无写冲突时可并行多实例）
  * UI/UX 实现 → @designer
    * 判断标准：改动涉及用户可见的视觉元素（布局、颜色、间距、动效、通知、浮层、错误展示位置）时，走 @designer
    * 纯逻辑改动（类型定义、状态管理、数据流、非渲染的计算逻辑）走 @fixer
  * 边做边决策的任务**不得**委托，@orchestrator 自行实现
  * 发现文档在此阶段创建，执行期间各 specialist 报告的发现由 @orchestrator 实时收集
* 简化
  * 操作对象：代码
  * 执行者：@explorer
  * 内容（simplify skill基础版）：
    * **搜索已有的工具函数和辅助函数**，看是否能替代新写的代码。在整个代码库中查找相似模式——常见位置包括工具目录、共享模块，以及变更文件相邻的文件
    * **标记任何与已有功能重复的新函数。** 建议改用已有函数
    * **标记任何可以用已有工具函数的内联逻辑**
  * 简化明确不通过 → 回Orchestrator重新安排原有执行者执行；不确定应不应该简化 → 向上报告
* 验证
  * 读取对象：spec + 原提示词 + git diff + 开发文档
  * 执行者：@oracle
  * 读取对象：代码
  * 代码审查（传入@fixer 执行阶段时的同一份 spec 作为审查契约）
    * 符合提示词契约
      * 检查是否满足最小实现，功能实现**不得**超过spec要求
      * 检查是否删除任何历史代码，除非 spec 明确要求
      * 若遇到不确定事项
        * 向 @orchestrator 报告
    * 符合既有架构规则
      * 检查是否满足CLAUDE.md中架构规则
      * 检查是否满足其他开发文档中架构规则
  * 审查不通过 → 回Orchestrator原委派对象执行；spec 本身有误 → 回规划
* 更新文档
  * 操作对象：步骤文档 + 发现文档
  * 执行者：@orchestrator（唯一写入者，不委托）
  * 步骤文档：标记状态（`⏳` → `✅`），删除临时实施细节，只保留关键产出
  * 发现文档：归档执行和验证期间收集的发现，分类（bug / 改进 / 不确定），状态标记为"待确认"
* 用户确认
  * @orchestrator 呈现更新后的步骤文档 + 发现文档，暂停等待用户确认
  * 用户确认发现项 → 发现文档对应条目状态改为"已确认"
  * 用户要求调整 → 回对应阶段
* 提交
  * 用户明确许可后执行 git commit
  * **禁止**未经用户许可执行 git commit

委托 @fixer 的条件：
1. 任务有明确的输入、输出和边界
2. 不需要边做边决策
3. 大文件提取可复用已读过该文件的 fixer 会话
注意：多个任务无写冲突时可并行

### spec 编写规范：目标导向约束

* 在这里spec = 给 fixer + oracle 的契约，由Orchestrator编写，贯穿执行与验证阶段。

spec 描述"做什么"，**不**描述"怎么做"。编排者提供目标和边界，实现细节由 specialist 自行判断。

* 核心原则
  * spec 是**目标与约束**，不是**命令行式指令**
  * 编排者负责"要什么、改哪里、不能碰什么"
  * specialist 负责"怎么改、改哪行、代码怎么写"
  * **禁止**在 spec 中给出完整代码块让 specialist 抄写
  * **禁止**在 spec 中指定精确行号（specialist 自己 grep 定位）
* spec 必备要素
  * 目标：说清改动的最终效果
  * 涉及文件清单：列出需要修改的文件路径
  * 改动规则：每个文件要做什么（用自然语言描述意图，不写代码）
  * scope guard：明确禁止修改的原有业务内容
  * 验收标准：可验证的完成条件（grep 零残留、类型检查通过、测试通过等）
  * 结果格式要求：必须返回的文件清单 + 自检确认项
* @fixer spec 特有
  * 改动规则描述到"函数级"或"逻辑块级"，不到"行级"
  * 涉及多个文件的紧耦合改动（写端和读端必须同步）放一个 fixer 任务，不拆分
  * 纯机械替换（如全局重命名）可描述到"符号级"
* @designer spec 特有
  * 描述用户可见的交互意图和视觉目标，不描述 CSS / 布局实现
  * 给出设计约束（如"浮空窗内就近显示""底部居中""不阻挡画布交互"）
  * 视觉风格由 designer 自行决定，编排者只审查是否符合约束
* 反面模式
  * ❌ 在 spec 中贴完整代码块
  * ❌ 指定精确行号（"第 126 行改为..."）
  * ❌ 给出完整搜索字符串（"找到 `this.lastOperationValidation = null` 改为..."）
  * ✅ 给出逻辑意图（"ui_store 删除 lastValidationResult 字段及所有相关清除逻辑"）

### 发现文件的创建与维护

* 创建者：编排者（不委托）
* 创建时机：对应步骤开始写代码时
* 写入者：编排者
* 内容来源：
  * @fixer 在 task result 中报告的原始发现（fixer 不自行分类，编排者判断）
  * @oracle 在审查报告中列出的自己的发现以及理解
  * @explorer 在探查报告中列出的发现（编排者判断）
  * 编排者在协调过程中自己注意到的
* 编排者职责：收到报告 → 复核/判断分类（bug / 改进 / 不确定）→ 写入文件 → 告知用户

### task 返回值格式规范

同一份 spec 传给 @fixer 作为实现指令、传给 @oracle 作为审查契约。两者返回值**必须**按固定格式组织。

#### @fixer 返回值

* 产出文件清单：`文件路径 + 行数`，逐个列出
* 关键内容确认清单：spec 要求的每项产出，逐项打勾或说明未完成原因
* 发现报告（可选）：执行期间注意到的 bug / 改进点 / 不确定项，按照fixer自己的理解直接陈述即可
* 异常说明：**禁止**空 result。无产出时也必须说明原因（如"scope guard 阻断""文件不存在"）。多次重复返回空，直接认为opencode本身异常

编排者收到后：
* 确认自检清单完整性（所有修复项均已打勾或说明未完成原因）
* 编排者不做代码抽查——验证职责归属 @oracle，编排者退为调度者
* @oracle 审查通过 → 信任实现质量，进入下一阶段
* @oracle 审查不通过 → 按回流建议派 fixer 重做或回规划修 spec

#### @oracle 在验证阶段的返回值

* 审查结论：逐项给出"通过 / 不通过 + 原因"
  * 契约符合：
    * spec 要求的都做了吗
    * spec 没要求的，fixer 做了吗
    * spec 没说删的，fixer 删了吗
  * 架构审查
    * 新增代码有无违法现有架构体系
    * 不能确定的架构安排直接当成不确定项标记
* 发现报告（可选）：审查中注意到的 bug / 改进点 / 不确定项，**按三类分类并标注严重度**（高/中/低）
* 回流建议：不通过项指明"回执行"还是"回规划"

编排者收到后：
* 审查全通过 → 进入更新文档阶段
* 有不通过并且非不确定项 → 按回流建议派 fixer 重做或回规划修 spec
* 发现报告归入发现文档，编排者复核分类后写入

## 关键规则

### 做完就更新

完成任意阶段后：
- 标记阶段状态：`⏳` → `✅`
- 删除开发的临时实施细节，只保留关键产出

### 让用户知情

重大发现或变更决策时：
- 在对话中主动告知用户
- 同时在 `*发现.md` 中记录
- 需要用户确认的决策标记为 **「待确认」**，确认后改为 **「已确认」**

### 开发文档文件名统一中文

- 不要使用英文文件名，统一使用中文文件名，以压缩文件名长度
