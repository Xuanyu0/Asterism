# 利用文档进行开发规划

用持久化的 markdown 文件作为你的"磁盘上的工作记忆"。

## 核心模式

```
上下文窗口 = 内存（易失、有限）
文件系统   = 磁盘（持久、无限）

→ 任何需要未来随时查阅的信息都要写到磁盘上
```

## 两种核心文件

| 文件 | 包含的内容 | 何时更新 |
|------|------|---------|
| `步骤.md` | 步骤划分、完成标志、当前进度、重要决策 | 每个步骤完成后 |
| `发现.md` | 历史遗留BUG、可以改进的地方、相关报告 | 有任何发现后 |

注：若文件过多，可以对大的阶段创建对应的文件夹，然后再创建小的阶段文件，如：

```markdown
phase2b/
├── 01-步骤-规则架构调整.md
├── 01-发现.md
├── 02-步骤-arrangement.md 
```

### 步骤规划文件

* 定义：在具体开发任务前 AI 与用户共同商讨过后制定的文件
* 创建时机：在开发开始前，先创建此文件
* 具体内容：
  * 步骤划分：
    * 步骤粒度（step 1、 step 1.1、 step 1.2、step 2...）
    * 步骤标题行标记状态：`--Complete` / `--In progress`
      * In progress：当前正在进行的步骤
      * Complete：已经完成的步骤
      * 没有标记的步骤默认是 `--Pending`，不需要写`--Pending`
    * 每个步骤的完成标志
    * 难度：不确定度 / 算法复杂度 / 工作量
      * 用显眼的unicode符号标记难度等级
  * 重要决策：
    * 待确定决策：开始写代码之前需要用户确定的决策
    * 已确定决策
* 额外文件：总纲文件（前缀编号00）
  * 包含：
    * 开发范式指导
    * 总体方向
    * 开发步骤文件链接
    * 等
* 格式：
  * 步骤采用二级标题
  * 子步骤是标题（三级标题）
    * BUG修复也算子步骤
  * 重要决策不算标题

### 发现文件

* 定义：在开发过程中完全由 AI 顺手发现并记录的文件
* 创建时机：在开发过程中发现任何问题或改进点时，立即按步骤创建或更新此文件
* 具体内容：
  * 历史遗留 BUG：不是本次开发阶段产生的 BUG，但在本阶段中发现了
  * 可以改进的地方：如
    * 代码结构不合理
    * 代码可读性差
    * 代码可以简化
  * 相关报告（对应于 BUG 和可以改进的地方）：
    * 发现的内容
    * 发现的具体位置（文件名 + 行号）
    * 建议的解决方案
  * 不确定事项：
    * 定义：开发过程中临时决策，并且已经写出代码，而自己没有太大把握，需要用户确认的决策
    * 如：
      * 自己临时决策的架构设计，但不确定是否合理
      * 猜测某个用户对产品的使用意图
      * 对自己写的代码质量某一些地方没有信心
      * 等
    * 记录问题内容 + 具体影响 + 状态标记（待确认 / 已确认）+ 建议（可选）
* 发现文件与步骤规划文件的关系：
  * 优先在发现文件中记录 BUG 与优化项
  * 在用户确认后，将发现内容写入步骤规划文件中，作为开发任务的一部分，如：
    * 严重 BUG 修复
    * 具有显著收益的重构

## 会话启动协议

**每次新会话的第一件事：**

1. 执行 git diff 命令并读取最近一次 commit 日志，了解当前工作目录状态
2. 查找并读取对应的 `*步骤规划.md` 和 `*发现.md`，确定当前进度
3. 如果存在处于 `--In progress` 的步骤，确认该从哪里继续
4. 如果没有规划文件，等待用户指示后再开始

## 关键规则

### 1. 做完就更新

完成任意阶段后：
- 标记阶段状态：`--In progress` → `--Complete`
- 删除开发的临时实施细节，只保留关键产出

### 2. 让用户知情

重大发现或变更决策时：
- 在对话中主动告知用户
- 同时在 `*发现.md` 中记录
- 需要用户确认的决策标记为 **「待确认」**，确认后改为 **「已确认」**

### 3. 智能体参与

规划文件的创建和结构决策由编排者完成（判断工作，不委托）。
文件的机械提取、批量创建、完全确定下来的代码实现委托 @fixer。

| 阶段 | 智能体 | 任务 |
|------|--------|------|
| 规划前 | @explorer | 探查代码库现状，确认依赖和现状 |
| 规划前 | @librarian | 研究外部库 API，影响子任务拆分 |
| 规划后 | @oracle | 审查步骤规划的合理性 |
| 执行 | @fixer | 有界实现，可并行（无写冲突时） |
| 执行 | @designer | UI/UX 设计和实现 |
| 验证 | @oracle | 代码审查 + 架构审查 |
| 验证 | @designer | UI/UX 审查 |
| 跟踪 | 编排者 | 更新规划文件（不委托） |

委托 @fixer 的条件：
1. 任务有明确的输入、输出和边界
2. 不需要边做边决策
3. 多个任务无写冲突时可并行
4. 大文件提取可复用已读过该文件的 fixer 会话

### 4. 文档文件名统一中文

- 不要使用英文文件名，统一使用中文文件名，以压缩文件名长度

### 5. 发现文件的创建与维护

* 创建者：编排者（不委托）
* 创建时机：对应步骤开始写代码时
* 写入者：编排者（唯一写入者，防止并行写冲突）
* 内容来源：
  * @fixer 在 task result 中报告的原始发现（fixer 不自行分类）
  * @oracle 在审查报告中列出的发现
  * @explorer 在探查报告中列出的发现
  * 编排者在协调过程中自己注意到的
* 编排者职责：收到报告 → 判断分类（bug / 改进 / 不确定）→ 写入文件 → 告知用户

### 6. 实现与审查的 spec 共享

每个步骤开始实现前，编排者从步骤规划文件中提取 spec（完成标志 + 涉及文件），
补充 scope guard（明确禁止修改的文件/函数），形成完整 spec。

同一份 spec：
- 传给 @fixer 作为实现指令
- 传给 @oracle 作为审查契约

oracle 审查项：
1. 契约符合：spec 要求的都做了吗？
2. 范围合规：spec 没要求的，fixer 做了吗？
3. 删除检查：spec 没说删的，fixer 删了吗？
4. 代码质量：实现是否正确、是否遵守规范？

### 7. 阻塞决策

* 任何在写代码前需要用户确认的决策，必须在继续开发前得到确认
* 否则，编排者必须暂停开发，等待用户确认

### 8. 旧文件处理

* 遇到需要整个文件删除的情况，必须先和用户确认，确认后再删除
* 否则，编排者必须在开发任务安排中，默认不删除，直到开发任务结束后告知用户

### fixer spec 的必备要素

spec 除了"做什么"，还必须包含"怎么汇报"。spec 五要素变为六要素：

1. 源文件路径
2. 提取/编辑规则（精确到章节边界）
3. 输出文件路径
4. 保留规则（scope guard）
5. 格式约束
6. **结果格式要求**（新增）
  - 必须返回的文件清单 + 行数
  - 必须逐项打勾的关键内容确认清单
  - 异常说明（不允许空 result）

编排者收到 result 后：
- 先看 fixer 的自检清单
- 抽查 1-2 个关键项独立验证
- 抽查通过 → 信任其余自检
- 抽查不通过 → 全面验证 + 重新派 fixer

## 何时使用此模式

**适用场景：**
- 多步骤任务（3 步以上）
- 调研任务
- 跨多次工具调用的任务

**跳过场景：**
- 简单问题
- 单文件修改
- 快速查询
