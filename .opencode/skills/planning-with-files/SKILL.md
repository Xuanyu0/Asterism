# 利用文档进行开发规划

用持久化的 markdown 文件作为你的"磁盘上的工作记忆"。

## 核心模式

```
上下文窗口 = 内存（易失、有限）
文件系统   = 磁盘（持久、无限）

→ 任何需要未来随时查阅的信息都要写到磁盘上
```

## 两个核心文件

| 文件 | 包含的内容 | 何时更新 |
|------|------|---------|
| `*步骤规划.md` | 步骤划分、完成标志、当前进度、重要决策 | 每个步骤完成后 |
| `*发现.md` | 历史遗留BUG、可以改进的地方、相关报告 | 有任何发现后 |

注：“*”用具体的开发阶段替换

### 步骤规划文件

* 定义：在具体开发任务前 AI 与用户共同商讨过后制定的文件
* 具体内容：
  * 步骤划分：
    * 步骤粒度（step 1、 step 1.1、 step 1.2、step 2...）
    * 每个步骤的完成标志
    * 当前进度（in progress / complete）
  * 难度（自评）
    * 开发的不确定度
    * 算法设计复杂度
    * 工作量（主要指代码行数）
  * 重要决策：
    * 待用户确定决策
    * 已确定决策

### 发现文件

* 定义：在开发过程中完全由 AI 顺手发现并记录的文件
* 具体内容：
  * 历史遗留 BUG：不是本次开发阶段产生的 BUG，但在本阶段中发现了
  * 可以改进的地方：如
    * 代码结构不合理
    * 代码可读性差
    * 代码可以简化
  * 相关报告（对应于 BUG 和可以改进的地方）：
    * 发现的内容
    * 发现的具体位置（文件名 + 行号）
    * 建议的解决方案
* 与步骤规划文件的关系：
  * 在必要时，将发现内容写入步骤规划文件中，作为开发任务的一部分，如：
    * 严重 BUG 修复
    * 具有显著收益的重构

## 关键规则

### 1. 先创建计划

在一个大的开发阶段开始前，创建对应的 `*步骤规划.md`。

### 2. 先读后做

做重大决策前，先读计划文件。

### 3. 做完就更新

完成任意阶段后：
- 标记阶段状态：`in_progress` → `complete`
- 记录完成时间
- 删除开发的临时实施细节，只保留关键产出

## 何时使用此模式

**适用场景：**
- 多步骤任务（3 步以上）
- 调研任务
- 跨多次工具调用的任务

**跳过场景：**
- 简单问题
- 单文件修改
- 快速查询

| 不要 | 应该 |
