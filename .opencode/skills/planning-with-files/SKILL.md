# 利用文档进行开发规划

用持久化的 markdown 文件作为你的"磁盘上的工作记忆"。

## 何时使用此模式

**适用场景：**
- 多步骤任务
- 一次完整的功能实现

**跳过场景：**
- 逻辑简单清晰的问题
- 单文件修改
- 快速查询
- 代码问答

## 开发启动协议

**每次开始开发的第一件事：**

* 执行 git diff 命令并读取最近两次 commit 日志，了解当前工作目录状态

## 三种核心文件

| 文件 | 包含的内容 | 安放位置 |
|------|------| ------| 
| `步骤.md` | 步骤划分、完成标志、当前进度 | `*开发文档/` |
| `发现.md` | 历史遗留BUG、可以改进的地方、不确定项、相关报告 | `*开发文档/` |
| `提示词.md` | 功能需求、验收标准、scope guard、交互规则 | `impl-spec/{对应开发阶段}/{对应步骤文件}/` |

注1：若文件过多，可进行合理拆分
注2：可以根据实际情况灵活变更对应文件的内容结构

### 步骤文件

* 定义：在具体开发任务前 AI 与用户共同商讨过后制定的文件
* 创建时机：在开发开始前，先创建此文件
* 具体内容：
  * 步骤划分的内容：
    * 子步骤（可选）
    * 步骤标题行标记状态：`✅` / `⏳`
      * `✅`：已经完成的步骤
      * `⏳`：当前正在进行的步骤
      * 没有标记的步骤默认是 Pending，不需要写标记
    * 每个步骤的完成标志
    * 难度：分为不确定度 / 算法复杂度 / 工作量三个维度
      * 可以用 `🟢`（低）/ `🟡`（中）/ `🔴`（高）标记难度等级
      * 难度标签写在每个子步骤或步骤的下一行
    * 待确定决策：
      * 开始写代码之前需要用户确定的决策
* 特殊：
* 阶段性对应的总纲文件（也是步骤文件，前缀编号00）
  * 包含：
    * 开发范式指导
    * 总体方向
    * 开发步骤文件链接
    * 已经确定的重要决策：
    * 等

### 发现文件

* 定义：在开发过程中完全由 AI 顺手发现并记录的文件
* 创建时机：在开发过程中发现任何问题或改进点时，立即按步骤创建或更新此文件
* 具体内容：
  * 历史遗留 BUG：不是本次开发阶段产生的 BUG，但在本阶段中发现了
  * 可以改进的地方：如
    * 代码结构不合理
    * 代码可读性差
    * 代码可以简化
  * 相关报告（对应于 BUG 和可以改进的地方）：
    * 发现的内容
    * 发现的具体位置（文件名 + 行号）
    * 建议的解决方案
  * 不确定事项：
    * 定义：开发过程中临时决策，并且已经写出代码，而自己没有太大把握，需要用户确认的决策
    * 如：
      * 自己临时决策的架构设计，但不确定是否合理
      * 猜测某个用户对产品的使用意图
      * 对自己写的代码质量某一些地方没有信心
      * 等
    * 记录问题内容 + 具体影响 + 状态标记（待确认 / 已确认）+ 建议（可选）
* 发现文件与步骤规划文件的关系：
  * 优先在发现文件中记录 BUG 与优化项
  * 在用户确认后，将发现内容写入步骤规划文件中，作为开发任务的一部分，如：
    * 严重 BUG 修复
    * 具有显著收益的重构

### 提示词文件

* 定义：由@orchestrator交付给@fixer/@designer（或@orchestrator自行参考）的完整提示词，是执行阶段的唯一输入契约。
* 创建时机：任务规划完成后、执行前，作为步骤文档中某一步骤的具体实现契约。
* 存放位置：`docs/impl-spec/` 目录下。与 `docs/spec/`（旧的引擎 spec）分开存放，避免混淆。
* 与步骤文档的关系：步骤文档描述"分几步、每一步做什么"，提示词文件描述"这一步具体怎么做"。一个是规划，一个是执行契约。
* 具体内容：
  * **设计文档依据**：溯源到 `docs/设计/` 或 `CLAUDE.md` 的具体章节。每一条 提示词 规则均可追溯至产品意图，不凭空产生。
  * **当前状态**：可以简述当前的问题以及对应的文件下的代码状态
  * **架构变更**（可选）：若涉及架构调整，用直观的字符画呈现。
  * **新增/修改文件**：以列表的格式列出所有涉及文件，每个文件附带一句话职责。
  * **核心任务**：本次任务需要完成的关键功能点，每个点一句话说明做什么。
  * **变更边界**：明确禁止修改的文件、模块、函数。这是 提示词 的红线。
  * **验收标准**：对应核心任务的每一项制定可验证的完成条件列表。无验收标准的 提示词 不得交付执行。
  * **不确定事项**（可选）：本次 提示词 书写过程中产生的不确定事项。
  * subagent task 的返回内容要求。

### 步骤文档写作规范

* 语言风格与文档权威性
  * 已确定决策用断言式风格
  * 待确定决策才允许用建议式，用引用框隔离
  * 设计文档（`docs/设计/`）已覆盖的概念，步骤文档**只能溯源引用**，**不得**重新定义或改写语义
* 结构的标记
  * 步骤标题行用 `✅` / `⏳` 标记状态，未标记默认 Pending
  * 决策块分两种语气：
    * 已确定决策：直接陈述规则 + 理由（如需）。理由只解释"为什么这样"，不解释"为什么不那样"
    * 待确定决策：`> **Qn**：问题` → `**建议**：答案。理由：...`。决策权显式留给用户
  * 子任务表表头用 `子任务 / 内容 / 约束`。"约束"列承载红线，不是附注
  * 每个步骤**必须**有验收标准，形式为可勾选的事实断言列表。无验收标准的步骤**不得**标记 Complete
* 代码与图示
  * 文件路径 + 行号锚定（如果能定位到行）（格式：`file.ts:NNN`）
  * **禁止**贴大段代码实现细节
* 通用的md格式：
  * 步骤（如step 1）采用二级标题
  * 子步骤是标题（三级标题）
    * 某步骤实施过程中发现的BUG，从发现文档中提取过来，且需要进行的修复也算子步骤
  * 标题行后紧接难度评估
  * 重要决策不算标题，但对应条目进行md加粗

### 发现文档写作规范

* 语言风格与写作权归属
  * 事实陈述。记录"看到了什么"，**不**记录"决定了什么"
  * 决策权完整留给用户
  * 编排者是唯一写入者
* 组织方式
  * 发现文档内部按其所属步骤下子步骤归属分组
  * 每项独立成节
* 三种内容的发现写作规范
  * 历史遗留 BUG：纯事实。最少包含：`位置` + `现象` + `后果`
  * 可改进点：事实 + 可选建议。建议**必须**用 blockquote 隔离
  * 不确定事项：
    * 最少包含：`问题` + `状态：⏳ 待确认/✅ 已确认`。
    * 可选包含：`影响`、`建议` + `理由`。建议**必须**用 blockquote 隔离
* 引用与禁止
  * 只向下锚定代码（`文件:行号`）。
  * **不**写验收标准，**不**写子任务表，**不**写步骤编号体系。
* 确认后流转
  * 用户确认后的发现项，进过与用户协商后，编排者可以将其写入步骤文档作为正式任务
  * 发现文件中对应条目状态改为 `已确认`。

### 提示词写作规范

* 用户身份迭代。编排者在写首个提示词文件时，不要闭门造车——先以**设计文档 + 术语映射表**为基础自行写一版，然后根据用户对第一版的审阅意见迭代。
* 语言风格
  * **断言式**：已确定决策用直接陈述。
  * **尽量不解释"为什么"**
* 内容组织
  * **最顶部**此次对应提示词的原步骤开发文档链接（地址），用md风格书写。可实现跳转功能。
  * **溯源优先**：L1文档内容引用放在有效提示词内容最开头，之后的所有规则以此为依据展开。设计文档覆盖的概念只溯源引用，不重新定义。
  * **新旧对比**（可选）：如需架构变更，必须先画`旧：`再画`新：`，让读者一眼看出变化。不要混着描述。
  * **文件清单表格**：单独成节。
  * **scope guard 单独成节**：放在核心职责之后、验收标准之前。不要把它藏在正文段落里。
  * **验收标准可验证**：用 md 的 check-box 风格书写
* 禁止项
  * ❌ 在提示词中贴完整代码块
  * ❌ 指定精确行号修改（如"第 126 行改为…"）
  * ❌ 给出完整搜索字符串（如"搜索 `this.lastOperationValidation = null` 改为…"）
  * ❌ 留"详见对话记录"这类外部引用 — 提示词必须自包含，零歧义

#### 特殊提示词编写规范

* 提示词 描述"做什么"，**不**描述"怎么做"。编排者提供目标和边界，实现细节由 specialist 自行判断。

* 针对@fixer
  * 改动规则描述到"函数级"或"逻辑块级"，不到"行级"
  * 涉及多个文件的紧耦合改动（写端和读端必须同步）放一个 fixer 任务，不拆分
  * 纯机械替换（如全局重命名）可描述到"符号级"
* 针对@designer
  * 描述用户可见的交互意图和视觉目标，不描述 CSS / 布局实现
  * 给出设计约束（如"浮空窗内就近显示""底部居中""不阻挡画布交互"）
  * 视觉风格由 designer 自行决定，编排者只审查是否符合约束

#### task 返回值格式规范

同一份 提示词 传给 @fixer 作为实现指令、传给 @oracle 作为审查契约。
两者返回值**必须**按固定格式组织。

##### @fixer 返回值

* 产出文件清单：`文件路径 + 行数`，逐个列出
* 关键内容确认清单：提示词 要求的每项产出，逐项打勾或说明未完成原因
* 发现报告（可选）：执行期间注意到的 bug / 改进点 / 不确定项，按照fixer自己的理解直接陈述即可
* 异常说明：**禁止**空 result。无产出时也必须说明原因（如"scope guard 阻断""文件不存在"）。多次重复返回空，直接认为opencode本身异常

编排者收到后：
* 确认自检清单完整性（所有修复项均已打勾或说明未完成原因）
* 编排者不做代码抽查——验证职责归属 @oracle，编排者退为调度者
* @oracle 审查通过 → 信任实现质量，进入下一阶段
* @oracle 审查不通过 → 按回流建议派 fixer 重做或回规划修 提示词

##### @oracle 在验证阶段的返回值

* 审查结论：逐项给出"通过 / 不通过 + 原因"
  * 契约符合：
    * 提示词 要求的都做了吗
    * 提示词 没要求的，fixer 做了吗
    * 提示词 没说删的，fixer 删了吗
  * 架构审查
    * 新增代码有无违法现有架构体系
    * 不能确定的架构安排直接当成不确定项标记
* 发现报告（可选）：审查中注意到的 bug / 改进点 / 不确定项，**按三类分类并标注严重度**（高/中/低）
* 回流建议：不通过项指明"回执行"还是"回规划"

编排者收到后：
* 审查全通过 → 进入更新文档阶段
* 有不通过并且非不确定项 → 按回流建议派 fixer 重做或回规划修 提示词
* 发现报告归入发现文档，编排者复核分类后写入


## 典型工作流

### 基本框架

* 规划与编写提示词文档
  * 操作对象：步骤文档
  * 执行者：@orchestrator（结构决策不委托）
  * 前置探查（按需，@orchestrator 缺乏上下文时触发）：
    * @explorer 探查代码现状与依赖
    * @librarian 查外部库 API，影响子任务拆分
  * 产出：步骤文档 + 提示词文档
    * 提示词文档也是贯穿执行与验证的契约。用户确认，执行，验证阶段共用同一份
  * 注意判断决策是否具有产品语义后果。如果有，可以在步骤规划中单开一个"待确定"区，供用户阅读。
* 用户确认
  * @orchestrator 呈现本次提示词，暂停等待用户确认
  * 用户确认后进入执行；用户要求调整则回规划
  * **禁止**未经确认直接进入执行
* 执行前创建并在执行时跟踪 OpenCode TODO
* 执行
  * 操作对象：代码（少数情况下可能是文档）
  * 机械实现 → @fixer
  * UI/UX 设计/实现 → @designer
    * 判断标准：改动涉及用户可见的视觉元素（布局、颜色、间距、动效、通知、浮层、错误展示位置）时，走 @designer
    * 纯逻辑改动（类型定义、状态管理、数据流、非渲染的计算逻辑）走 @fixer
  * 边做边决策的任务**不得**委托，@orchestrator 自行实现
  * 发现文档在此阶段创建，执行期间各 specialist 报告的发现由 @orchestrator 实时收集
* 简化
  * 操作对象：代码
  * 执行者：@explorer
  * 内容（simplify skill基础版）：
    * **搜索已有的工具函数和辅助函数**，看是否能替代新写的代码。在整个代码库中查找相似模式——常见位置包括工具目录、共享模块，以及变更文件相邻的文件
    * **标记任何与已有功能重复的新函数。** 
    * **标记任何可以用已有工具函数的内联逻辑**
  * 简化明确不通过 → 回@Orchestrator重新安排原有执行者（@fixer/@designer）执行；不确定应不应该简化 → 向上报告
* 验证
  * 读取对象：提示词文档 + git diff + 开发文档
  * 执行者：@oracle
  * 读取对象：代码
  * 代码审查（传入@fixer 执行阶段时的同一份 提示词文档 作为审查契约）
    * 符合提示词契约
      * 检查是否满足最小实现，功能实现**不得**超过提示词要求
      * 检查是否删除任何历史代码，除非 提示词 明确要求
      * 若遇到不确定事项
        * 向 @orchestrator 报告
    * 符合既有架构规则
      * 检查是否满足CLAUDE.md中架构规则
      * 检查是否满足其他开发文档中架构规则
  * 审查不通过 → 回@Orchestrator原委派对象（@fixer/@designer）执行；提示词 本身有误 → 回规划
* 初步更新文档
  * 操作对象：步骤文档 + 发现文档
  * 执行者：@orchestrator（唯一写入者，不委托）
  * 步骤文档：标记状态（`⏳` → `✅`），删除临时实施细节，只保留关键产出
  * 发现文档：归档执行和验证期间收集的发现，分类（bug / 改进 / 不确定），状态标记为"待确认"
* 标记所有 TODO 完成
* 用户确认
  * @orchestrator 呈现更新后的步骤文档 + 发现文档，暂停等待用户确认
  * 用户确认发现项 → 发现文档对应条目状态改为"已确认"
  * 用户要求调整 → 回对应阶段
* 更新并简化开发文档
  * 操作对象：步骤文档 + 发现文档
  * 执行者：@orchestrator
  * 删除临时实现细节，只保留关键产出与决策，以及达成的效果
* 提交
  * 用户明确许可后执行 git commit
  * **禁止**未经用户许可执行 git commit
* 反思
  * 目标：优化 Skill 
  * 回顾上下文窗口，反思这次任务执行时出现的失误或者顺利执行的经验
  * 在 session 中告知用户即可

### 注意事项

#### 委托 @fixer 的条件：

1. 任务有明确的输入、输出和边界
2. 不需要边做边决策
3. 大文件提取可复用已读过该文件的 fixer 会话

#### 处理子代理的空值返回：

* 至少对那个没有返回值的子代理重试一次。不行的话再向上报告此次异常

### 发现文件的创建与维护

* 创建者：编排者
* 创建时机：对应步骤开始写代码时
* 写入者：编排者
* 内容来源：
  * @fixer 在 task result 中报告的原始发现
  * @oracle 在审查报告中列出的自己的发现以及理解
  * @explorer 在探查报告中列出的发现
  * 编排者在协调过程中自己注意到的
* 编排者职责：收到报告 → 复核/判断分类（bug / 改进 / 不确定）→ 整理并写入文件 → 告知用户

## 次要规则

### 开发文档文件名统一中文

- 不要使用英文文件名，统一使用中文文件名，以压缩文件名长度
