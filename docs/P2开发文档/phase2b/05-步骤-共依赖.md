## Step 3：共依赖 — 交互底层基础设施

**目标**：为多个上层功能提供共享的底层交互能力。

### 3.-1 清理 graph_operations.ts 中间层 ✅

难度：🟢/🟢/4处  — 纯搬迁+删除，零算法复杂度，约 250 行变动（删 499 + 改 2 文件）

**背景**：

`graph_operations.ts` 作为 GraphData 操作的中间层，经历 1.11（工具 handler 重构）和 1.13（draft 内联）后，核心消费者已经流失：

| 消费者 | 状态 |
|--------|------|
| 工具栏工具（add-node / add-edge / delete / fold） | 已绕过，直接调 `graphStore.applyBatchToGraph()` |
| `updateDraftNode` / `cancelDraftNode` | 1.13 已删除 |
| `diverge` / `moveNode` | 零消费者（搜索确认：无任何 Vue 组件或 TS 模块调用） |

剩余 5 个认知操作函数（`deconstruct` / `induce` / `internalize` / `explore` / `unearth`）仅被 `operation_controller` 调用，中间隔着一层纯透传。3 个浮空窗编辑函数（`confirmExistingNodeEdit` / `confirmExistingEdgeEdit` / `closeFloatingWindow`）是薄包装——本质是 `graphStore.applyBatchToGraph()` + `uiStore.closeFloatingWindow()`。

**架构定位确认**：

`frontend/src/feature-tools/`（mediator + toolbar handlers）从诞生起就不依赖 `graph_operations.ts`——所有 toolbar handler 直接调 `graphStore.applyBatchToGraph()`，是完全正确的架构实现。本步骤不触及 feature-tools 任何代码。

**设计决策**：

删除 `graph_operations.ts`，将剩余有效代码归位：

- 浮空窗编辑 → 迁入 `GraphNodeWindow.vue`。`GraphNodeWindow.vue` 已 import `useGraphStore`，`confirmExistingNodeEdit` / `confirmExistingEdgeEdit` 迁入后零额外依赖。`closeFloatingWindow` 直接改为调 `uiStore.closeFloatingWindow()`。
- 认知操作 → 迁入 `operation_controller.ts`。`operation_controller` 不再通过 `useGraphOperations()` 透传，改为直接 import engine compose 函数并调 `graphStore.applyBatchToGraph` / `applyBatchToGraphs`。
- `computeNodeRadiusOverrides` / `findCommonLayer` → 随认知操作迁入 `operation_controller.ts` 作为模块级私有函数（它们仅被迁入的认知函数调用）。
- `diverge` / `moveNode` → 迁入 `operation_controller.ts`。两者均为设计文档要求的 feature（`diverge` 是认知工具，`moveNode` 是常驻工具栏工具），当前无 UI 入口但不可删除。迁入后保持现状，后续步骤决定具体激活方式。
- `explore` / `unearth`（Phase 4 TODO stub）→ 迁入 `operation_controller.ts`，保持 TODO 标记。

### 3.0 统一工具激活系统：mediator 接管所有工具

**背景**：

当前存在两套并行的激活系统：

```
tool_mediator（工具栏 8 按钮）
    activeToolId → activeHandler → dispatch events

ui_store（交互模式 + 子工具）
    interactionMode → selectedCognitionAction / selectedArrangementAction
```

工具栏按钮本质上是"使用频繁而常驻化的交互模式"，与认知/布局子工具共享同一互斥约束——用户一次只做一件事。两套激活系统是实现的泄露，不是用户的心智模型。

**设计决策**：

`mediator` 应成为唯一的工具激活管理者，所有互斥行为统一收口：

```
mediator（唯一激活管理者）
    activeHandler: ToolHandler | null
        ├─ 工具栏工具（add-node / add-edge / delete / fold）
        ├─ 认知子工具（deconstruct / induce / internalize / diverge / explore / unearth）
        └─ 布局子工具（moveNode / orbit / path / adjustDistance / adjustOrbit）
```

`ui_store` 退化为"界面展示状态"（浮空窗数据、面板展开/收起等），不再持有工具选择。

**前提条件**：

认知/布局子工具目前尚未实现为 `ToolHandler` 形态。需先将每个子工具封装为独立 handler（或 handler 工厂），才能统一注册到 mediator。

**实施阶段**：

优先将 Layout 使用的方式，后面的 Cognition 再相继对齐。

**依赖关系**：认知/布局 handler 是本步骤的前置依赖，待 1.13（draft 内联）稳定后逐模式推进。

### 3.2 拾取放置解禁

> 见 `docs/设计/06-交互逻辑.md` §预览 -> 执行

将节点移动从 Cytoscape 原生拖拽替换为拾取放置模式。后者不需要按住鼠标键移动，而是"点击拾取 → 自由移动光标 → 再点击放置"。

**流程**：

```
左键点击节点 → 节点拾取（吸附在光标上）
光标自由移动 → 节点跟随（视觉层偏移，不写 GraphData）
左键再点击  → 节点放置（写入 GraphData 作为一次 undo）
右键/Escape → 取消（节点回到原始位置）
```

**改动**：
- 禁用 `cy.nodes().grabify()`（不再使用 Cytoscape 原生拖拽）
- 进入 Arrangement 模式时启用节点拾取放置
- 推出 Arrangement 模式时恢复禁止拾取放置
- `use_graph_interaction.ts` 新增 "click to pick → follow cursor → click to place" 事件流
- 新增 `NodePickAndPlaced` 语义事件替代 `NodeDragEnded`
- 预览阶段的操作参数调整（Orbit/Path/Adjust）同样使用拾取放置

### 3.4 预览 -> 执行

> 见 `docs/设计/06-交互逻辑.md` §预览 -> 执行

认知/布局模式的操作必须经过"预览"阶段才能执行。预览阶段的操作参数调整采用拾取放置（3.2 节）。

**实现状态机**：

```
                ┌──────────┐
                │  操作选择  │
                └────┬─────┘
                     │ 选择操作 + 选择对象
                     ↓
                ┌──────────┐
         ┌─────→│  预览阶段  │
         │      └────┬─────┘
         │           │ 校验通过，用户确认
         │           ↓
         │      ┌──────────┐
         │      │  执行写入  │ → GraphData + undo
         │      └──────────┘
取消(右键/Esc)│
         └──────
```

**改动**：
- `ui_store` 或 `draft_store` 新增 `previewState`（preview data, 可调参数, 校验结果）
- 预览渲染层：半透明/Ghost 样式
- 确认→写入：调用 `graphStore.applyBatchToGraph`
- 取消：清除预览状态，回到操作选择

### 待决设计问题

> **Q3**：多选节点的交互方式是什么？"Ctrl/Shift + 点击" vs "直接逐个点击（toggle 模式，再点取消选中）" vs "拖拽框选"。
>
> **建议**：拖拽框选作为主要多选方式，辅以 toggle 点击（不需要修饰键——直接点击已选中节点则取消选中，点击未选中节点则加入选中）。理由：拖拽框选是画布应用最直觉的多选方式（Cytoscape 原生支持 `boxselect`），而 toggle 点击不需要修饰键降低了操作门槛，符合"低认知负担"设计原则。Ctrl/Shift 是桌面习惯，不适合本应用的沉浸式画布体验。

> **Q4**：框选拖拽过程中，选中区域的视觉呈现是什么？
>
> **建议**：Cytoscape 原生提供的半透明蓝色选框即可。理由：不做自定义渲染——这是通用交互范式，用户不需要被教。后续如果需要统一视觉风格再替换。

### 3.5 待解决设计问题：选中状态归属

**问题**：`graph_store.ts` 当前持有 `selectedNodeId` / `selectedEdgeId`，但选中状态本质上是 UI Runtime 状态，不是 GraphData。

**两种方案**：

| 方案 | 位置 | 优点 | 缺点 |
|------|------|------|------|
| A（当前） | `graph_store.ts` | 与图数据邻近，组件读取方便 | 污染 GraphData Store 的纯度 |
| B | `ui_store.ts` | UI 状态归位，graph_store 只保留 GraphData | 部分读取路径需改到 ui_store |

**建议**：方案 A 在 Phase 2b 可接受，因为当前选中状态主要用于图操作路由；若未来 UI 需要根据选中状态做复杂反馈（如右键菜单、批量操作面板），再迁移到 `ui_store.ts`。

**结论**：暂不迁移，本问题在 Step 3 记录，后续视 UI 复杂度决定是否调整。
