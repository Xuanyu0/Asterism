# 架构对比分析：Asterism 与同类产品的架构适性评估

> 评估标准不是"谁的架构更好"，而是"谁的架构更适合它的产品目标"。
> 调研基于各产品官方文档、公开架构资料、源码结构和创始人博客。

---

## 一、各产品架构的"优化 vs 交换"

每个产品的架构选择反映其核心产品目标。没有架构是绝对正确的——只有适合和不适合的。

### 1. Obsidian — 优化"数据永久性，零供应商锁定"

**核心信条**：*"文件比应用更长寿。应用消失了——笔记还在。"*

**关键架构选择**：

| 选择 | 为什么 | 结果 |
|------|--------|------|
| Markdown 文件作 SSoT | 纯文本 2005 年可读，今日可读，40 年后仍可读 | 零供应商锁定，任意文本编辑器可打开 |
| Graph 视图是核心插件 | 不是数据模型，只是 Markdown 链接的内存投影 | 图谱是可选的导航工具 |
| 无引用完整性 | `[[deleted-note]]` 静默失败，但自由度 > 形式化 | 用户接受此换 |
| 插件 API 作扩展层 | 社区构建功能，核心团队构建约束 | 4000+ 插件 |

**交换掉**：正式图引擎、引用完整性、结构化操作、撤销树、协作

**如果它做 Asterism 的事会崩在哪**：无类型化节点（笔记无类型），无操作日志（撤销不可编程），无 `GraphData` 纯数据值，Cytoscape 不是只读投影

**对 Asterism 的启示**：数据的绝对持久性是对放弃形式化强制力的合理交换。Asterism 不能放弃持久性，但可以坚持图状态的形式化操作是持久性之上的有价值层，不是替代品。

---

### 2. Logseq — 优化"确定性、可查询、不可变"

**核心信条**：在本地优先基础上实现 Roam Research 式的块级大纲 + Datalog 查询能力。

**关键架构选择**：

| 选择 | 为什么 | 结果 |
|------|--------|------|
| DataScript（内存 Datalog 数据库）作核心 | 不可变 db 值 → 时间旅行、确定性状态、解耦客户端 | Datalog 查询回答"当前状态的重要问题" |
| 多线程（DB worker + UI worker） | UI 线程不直接接触数据库，保持响应 | 通过 Comlink RPC 通信 |
| Markdown Mirror | 数据库修改 → Markdown 文件，保证文件可移植 | 可在 Obsidian 中打开 Logseq 笔记 |

**交换掉**：ClojureScript 生态小众（人才/工具受限）、内存使用高、Markdown Mirror 竞态条件、DB 版本花了数年完成

**对 Asterism 的启示**：在不可变数据库方面做重大基础设施投资是合理的——如果它能实现更好的查询和状态管理。Asterism 的纯函数引擎是更轻量的方向（没有 DataScript/Datalog，只是带操作的 `GraphData` 值）。

---

### 3. tldraw — 优化"高频画布交互的细粒度响应性"

**核心信条**：作为嵌入其它应用的画布 SDK，必须处理每帧拖拽 + 数千形状。

**关键架构选择**：

| 选择 | 为什么 | 结果 |
|------|--------|------|
| 自建信号库 `@tldraw/state` | React `useState` 对大型派生集费用过高 | 懒惰评估 + 时钟基础 + 增量差异 |
| `StateNode` 工具状态机 | 有子状态（SelectTool → Brushing/Translating/Resizing） | 工具逻辑清晰分离、自动转换 |
| Record Store + IndexedDB | Schema 版本控制 + 序列化迁移 | 可嵌入任意宿主应用 |
| SDK 模型 | 不是独立 App，是供他人嵌入的包 | 框架锁定（editor 依赖 React） |

**交换掉**：包大小增加、学习曲线（`track()`/`computed()`/`transact()`）、框架锁定

**对 Asterism 的启示**：在特定领域图形应用中，自建基础设施（信号、状态节点、存储）是正确选择。Asterism 的纯函数引擎是类似决定——通用框架（Pinia/Vue）无法满足图引擎需求而不引入不合适约束。

Asterism 的 `feature-tools/mediator.ts` 模式与 tldraw 的 `StateNode` 是最接近的工具架构对标。

---

### 4. Heptabase — 优化"深度理解的外化心理模型"

**核心信条**：*"获得深度理解的关键是原子化你的概念，然后可视化概念间的关系。"*

**关键架构选择**：

| 选择 | 为什么 | 结果 |
|------|--------|------|
| 卡片（原子概念）+ 白板（上下文层） | 白板的真实目的不是可视化，而是追踪每张卡片的思维上下文 | 花了近 2 年在卡片复用 + 双向链接，非画笔工具 |
| Meta Apps（Journal / Whiteboard） | 引用卡片数据库但不拥有数据 | 数据与视图解耦 |
| 无插件系统 | 6 人团队故意选择，"较小团队执行速度更快" | 所有功能来自核心团队 |
| 分阶段实现 | Phase 1: 上下文 + 描述 → Phase 2: 注释 + 集成 → Phase 3: 通信 → Phase 4: 应用层 | 演化式架构 |

**交换掉**：无插件系统、无正式图引擎（白板箭头无形式化边类型）、无协作（优先个人）、无正式撤销树

**如果它做 Asterism 的事会崩在哪**：无形式化图 → 无形式化图转换。Heptabase 的"拆解"是用户在白板上手动分割卡片——无验证、无逆操作、无类型化操作序列。卡片复用是位置性的，非结构化的——Asterism 通过 `reference` 角色 + `sourceNodeId` 处理。

**对 Asterism 的启示**：专注于原子化概念 + 视觉空间关系 + 上下文追踪，如果有足够深思熟虑的设计，可以取代对形式化图系统的需求。Heptabase 选了直觉优先。Asterism 选了形式化优先。这是两种平等的方法论选择，不是优劣。

---

### 5. NoteConnection — 优化"结构化学习路径"

**核心选择**：DAG 层次化布局（非力导向团块）、双渲染引擎（SVG 高保真 + Canvas 万级节点）、客户端-服务器分离。

**关键架构选择**：

| 选择 | 为什么 |
|------|--------|
| DAG 布局 | 显示先决条件 → 后续步骤的学习路径 |
| SVG + Canvas 双渲染 | D3/SVG 到 2-3k 节点，Canvas 处理 10k+ |
| 服务器做图构建/布局/引擎 | 客户端做 UI/交互/运行时桥接 |

**交换掉**：架构厚度（大量移动部件），高耦合（server.ts 被标记为"大的负责人"）

---

### 6. Heartwood — 优化"复合理解（AI 推理）"

**核心信条**：*"Most knowledge tools are storage. Heartwood also reasons on your graph."*

**关键架构选择**：

| 选择 | 为什么 |
|------|--------|
| 6 阶段管道（潜在连接 → 知识差距 → 聚类 → 桥梁 → 矛盾 → 漂移） | 阶段是独立价值："推理引擎无信念层工作；信念层无链接预测工作" |
| 结构性算法 + LLM 语义分离 | 图算法处理结构（中心性、PPR），LLM 处理意义（解释聚类） |
| Python + CLI + MCP | 零 GPU 要求，CLI 可 CI/CD 集成，MCP 使代理可访问 |
| 低成本（Haiku 非 Opus） | 完整管线运行 < $0.10 |

**交换掉**：无前端关注（Three.js 单 HTML 文件）、无实时响应性（管道是运行而非 watch）、依赖 Anthropic API

**如果它做 Asterism 的事**：Heartwood 的"推理"是分析性的，非结构化的——它发现关系，不会通过形式化操作转换图。信念逆转（`revision.py`）是很有趣但范围有限——逆转错误的信念删除，非任意操作。

## 二、Asterism 的"优化 vs 交换"

### 优化

| 目标 | 体现 | 为什么这对学习状态管理重要 |
|------|------|--------------------------|
| **图转换的正确性** | 操作验证前提条件 → 结构化结果（drafts + issues + operations）→ applyBatch 提交。非"改数据"，是"验证，确认后应用" | 学习操作（解构/归纳/内化）有语义前条件，错误操作应被拦截而非静默执行 |
| **认知状态显式化** | NodeRole（知识/引用）/ form（原子/抽象）/ referenceKind（沟通/启发）/ GraphKind（根/子图/常识层）在类型系统中编码 | 用户对所学知识的心理模型的外部化表示——不只是内容存储 |
| **引擎纯性** | 框架无关、无副作用、纯函数。单元测试不需要 DOM/框架/Pinia | 引擎正确性是产品的命脉。图操作错误不可接受。 |
| **分支撤销** | 操作树支持 git checkout 风格的撤销/重做 | 探索复杂主题时你尝试一条路、放弃、走另一条——线性 undo 不够 |
| **渲染隔离** | Cytoscape 是只读投影。不是约定，是架构规则 | 渲染器从不持有或修改 GraphData，保证 SSoT 不分裂 |

### 交换

| 牺牲 | 说明 | 为什么可接受 |
|------|------|------------|
| 通用文件格式 | GraphData 是 JSON，不是 Markdown | 学习状态天生结构化，Markdown 无类型系统或图操作语义 |
| 通用编辑器兼容性 | 用户需要浏览器，不能在终端 cat 笔记 | Asterism 不是 "记笔记" 工具，是 "管理学习状态" 工具 |
| 大插件生态 | 通过引擎级操作组合 + 工具注册扩展，非插件市场 | 架构级可扩展性比数量的优先级更高 |
| 低学习曲线 | 用户必须理解节点角色、图种类、认知操作 | 结构化思考需要结构化工具。这是特征非 Bug |
| 协作 | 无多人编辑，设计为个人工具 | Phase 2b MVP 阶段正确取舍 |

## 三、八大架构维度的跨产品对比

| 维度 | Asterism | Obsidian | Logseq | tldraw | Heptabase | NoteConn | Heartwood |
|------|----------|----------|--------|--------|-----------|----------|-----------|
| **数据模型类型系统** | 强类型判别（编码认知状态） | 弱类型（无结构 Markdown） | 弱类型（DataScript schema） | 类型化记录（几何形状） | 闭源（卡片+标签） | 推断图（KAtom/REdge） | YAML ontology（无形式层次） |
| **数据流** | 严格单向 | 事件驱动 | DataScript 观察者 | 信号推送 | 闭源 | REST/WS | 顺序管道 |
| **引擎独立性** | ✅ 完全独立包 | ❌ 绑定 Electron | ❌ 绑定 DataScript | ⚠️ 部分依赖 React | ❌ 闭源 | ❌ 与 server 混合 | ⚠️ CLI 可独立 |
| **渲染分离** | ✅ 只读投影 | ❌ 图=核心插件 | ❌ 混合 | ❌ 渲染=编辑器 | ❌ 白板=操作层 | ⚠️ 双渲染器 | ❌ 单 HTML 文件 |
| **工具模型** | 中介器模式 | 命令系统 | 块命令 | StateNode 状态机 | 白板操作 | API 调用 | CLI/MCP |
| **撤销** | ✅ 树+分支 | 线性编辑历史 | DataScript 事务 | 线性历史栈 | 版本历史(推测) | 无 | 信念逆转(有限) |
| **可扩展性** | 引擎操作+工具注册 | 4000+ 插件 | 插件 API | 自定义形状/工具 | 无插件 | 开源可改 | YAML ontology |
| **可测试性** | 纯函数（无 DOM 无框架） | 主要手动 | CLJS 测试 | 无头编辑器 | 未知 | Jest | pytest |

## 四、Asterism 的四个架构独特点（从适性角度重述）

### 1. 引擎独立包是最正确的选择

- **为什么必需**：图操作的正确性 Asterism 的核心价值。如果引擎与 UI 框架耦合，则单元测试需要加载浏览器、Pinia、Vue —— 不可接受
- **与之相比**：Obsidian（无独立引擎）、Logseq（绑定 DataScript）、tldraw（部分绑定 React）
- **代价**：包间通信需要序列化 GraphData 值（不是引用传递）
- **判断**：✅ 适合学习状态管理的目标

### 2. 严格单向数据流是最正确的选择

- **为什么必需**：SSoT 必须唯一。如果渲染层可写 GraphData，则竞态条件和状态分裂无法避免
- **与之相比**：所有其它产品的图视图都可直接操作数据
- **代价**：需要明确的 watch 桥梁（`watch(currentGraph) → mapper → Cytoscape`）
- **判断**：✅ 适合 "GraphData 唯一事实源" 的产品信条

### 3. 认知状态编码在类型系统是最正确的选择

- **为什么必需**：认知操作（deconstruct 等）在概念层面依赖于操作数的类型——不能对 `reference` 节点做归纳，不能对 `abstract` 节点做解构。类型系统是这些规则的执行者
- **与之相比**：无产品区分节点角色/形式/引用种类
- **代价**：用户需要理解这些类型的含义
- **判断**：✅ 适合 "管理学习状态" 的定位

### 4. 树形分支撤销是最正确的选择

- **为什么必需**：学习不是线性的。你尝试理解概念的方式 A，发现不行，想回退到之前的分支 B。线性 undo 无法做到
- **与之相比**：所有产品只有线性 undo 或无 undo
- **代价**：存储操作日志，UI 需要分支选择器
- **判断**：✅ 适合 "探索思维路径" 的产品行为

---

## 五、结论：这才是 Asterism 架构的真正优势

不是抽象意义上的 "更好"，而是：

> Asterism 的架构选择与其产品目标（学习状态管理）一致性最高。引擎独立性保证了图操作的正确性可测试。严格单向流保证了 SSoT。类型系统保证了认知操作的概念完整性。树形撤销匹配了非线性的学习过程。

而 Obsidian 的架构完美匹配其目标（长寿文件）。tldraw 的架构完美匹配其目标（高频画布交互）。Logseq 的架构完美匹配其目标（可查询的不变数据库）。

**选对了适合自己目标的架构，远比照搬别人的"最佳实践"更重要。**
