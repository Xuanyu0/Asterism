### 3.0 统一工具激活系统：mediator 接管所有工具

**背景**：

当前存在两套并行的激活系统：

```
tool_mediator（工具栏 8 按钮）
    activeToolId → activeHandler → dispatch events

ui_store（交互模式 + 子工具）
    interactionMode → selectedCognitionAction / selectedArrangementAction
```

工具栏按钮本质上是"使用频繁而常驻化的交互模式"，与认知/布局子工具共享同一互斥约束——用户一次只做一件事。两套激活系统是实现的泄露，不是用户的心智模型。

**设计决策**：

`mediator` 应成为唯一的工具激活管理者，所有互斥行为统一收口：

```
mediator（唯一激活管理者）
    activeHandler: ToolHandler | null
        ├─ 工具栏工具（add-node / add-edge / delete / fold）
        ├─ 认知子工具（deconstruct / induce / internalize / diverge / explore / unearth）
        └─ 布局子工具（moveNode / orbit / path / adjustDistance / adjustOrbit）
```

`ui_store` 退化为"界面展示状态"（浮空窗数据、面板展开/收起等），不再持有工具选择。

**实施策略**：分四次工作流循环，由浅入深。

- **3.0-1（框架）**：搭建统一激活基础设施——类型扩展、mediator 改造、ui_store 清理、operation_controller 清理、Graph.vue 路由统一。以 deconstruct 为最小原型验证框架管线。
- **3.0-2（operation_controller 角色厘清）**：框架搭建后 operation_controller 失去了模式管理角色，同时持有待迁移的 compose 库存。本步骤厘清其架构位置——compose 逻辑归属各 handler，controller 退化为画布默认路由 + UI 状态通道。提取共享辅助函数至 utilities。
- **3.0-3（update handler）**：实现 `toolbar/update.ts` handler，接管浮空窗编辑。验证 handler 模式能否支撑"外部触发（非画布驱动）"的使用场景。
- **3.0-4（move_node + 拾取放置）**：原 3.2（拾取放置解禁）并入此步骤。拾取放置是 move_node 的首要消费者，基础设施与首个 handler 同步骤实现。`move_node.ts` 放 `toolbar/` 下——moveNode 是常驻工具栏工具。

#### 3.0-2 operation_controller 职责收缩 ✅

难度：🟢/🟢/3处 — 删薄包装 + 提取默认工具，删除约 120 行，新增约 40 行

**背景**：

3.0-1 后 mediator 接管了工具激活，operation_controller 失去了模式管理角色。当前 controller 持有三类内容，各有不同处理：

| 类别         | 内容                                                                                 | 3.0-2 处理                                             |
| ------------ | ------------------------------------------------------------------------------------ | ------------------------------------------------------ |
| 薄包装       | `closeFloatingWindow` / `requestCanvasFocus` / `clearCanvasFocus` / `ui.state`       | **删除**——消费者直调 uiStore                           |
| 默认路由     | `handleNodeClicked` / `handleEdgeClicked`（无工具时 → 打开浮空窗）                   | **提取**到 `feature-tools/default.ts` 作为 ToolHandler |
| compose 库存 | `induce` / `internalize` / `diverge` / `moveNode` / `explore` / `unearth` + 私有辅助 | **保留**——各自步骤再迁                                 |

**设计决策**：

- **薄包装一律删除**。它们是 3.0-1 留下的残渣——对 uiStore 的零价值透传，不加校验、不加编排。消费者直调 `useUIStore()` 即可。
- **"默认模式"是跨模式共享的 baseline tool**。设计文档 §"显式表达默认状态"明确：默认指针图标代表"什么都不做"的交互语义，它从这种意义上来说就是一种工具。`feature-tools/default.ts` 实现 ToolHandler 接口，负责 `onNodeClick → openFloatingWindow` / `onEdgeClick → openFloatingWindow`。注册为 mediator 的常驻 fallback——无其他工具激活时自动生效。**不是** update handler（3.0-3）——默认工具只管"打开浮空窗"，不动 GraphData。
- **compose 库存不动**。`induce` / `internalize` / `diverge` / `moveNode` / `explore` / `unearth` 是待迁移库存，各自在 Steps 4/5 / Phase 4 迁出到独立 ToolHandler。
- **YAGNI：不提取共享辅助函数**。`computeNodeRadiusOverrides` 和 `findCommonLayer` 当前仅在同一文件内被调用，不存在多文件消费者。提取到独立 utilities 文件是为假设的未来消费者预先抽象。等某个 handler 真正需要时再由它提取。

              → uiStore.openFloatingWindow         ↓ NO  → fallback: default 工具
                                                            → uiStore.openFloatingWindow
```

#### 3.0-3 default 工具扩展 — 浮空窗 Confirm 走 mediator ✅

难度：🟡/🟡/2处 — 浮空窗 Confirm 走 mediator 管线，涉及 GraphNodeWindow.vue 重构

**背景**：

3.0-2 的默认工具处理了"点击 → 打开浮空窗"，但"浮空窗 Confirm → 写入 GraphData"仍在 `GraphNodeWindow.vue` 中直接调 `graphStore.applyBatchToGraph`。默认模式从查看编辑到保存是一个完整的交互流程，不应拆成两个模块——默认工具本身就是 update 的载体。

**设计决策**：

- **默认工具扩展 `onConfirm`**。默认工具不仅是"打开浮空窗"，它承载"默认交互模式"的完整语义：`onNodeClick → 打开浮空窗 → 编辑 → onConfirm → applyBatch → 关闭浮空窗`。不新建 update handler。
- **复用现有 `onConfirm`**。ToolHandler 接口已有 `onConfirm(label, summary)`（add-node 使用），本步骤需解决签名泛化问题——使其同时覆盖 add-node 的草稿确认和 update 的已有实体修改。
- **外部触发模式**：`onConfirm` 的消费者是组件层（GraphNodeWindow.vue）。浮空窗 Confirm 时通过 `mediator.activeHandler` 获取 handler 引用 → 调用 `handler.onConfirm`。

**架构变更**：

```

#### 3.0-5 Cy 架构角色厘清（待规划）

##### 已确认决策

1. **Cy 的角色重新定位为"交互层 + 渲染层"**（不再单称"渲染层"）。理由：
   - Cy 实际承担两件事——`cy.json()` + stylesheet 负责视觉渲染，`tap`/`cxttap`/`dblclick`/`boxselect` 事件负责用户手势捕获。
   - 现有代码已体现在文件结构上：`use_cytoscape_renderer.ts`（渲染）、`use_graph_interaction.ts`（交互）。

2. **术语替换**：后续开发中不再使用"投影"（`mapNodeToCyElement` 的字段挑选本质上不是投影），替代为：
   - **映射**（mapping）：GraphData 字段 → CSS class 的语义转换（如 `role + kind → ['node-knowledge', 'node-atomic']`）
   - **拷贝**（copy）：GraphData 字段原样写入 Cy `data`，只拷贝 Cy 实际需要的字段（`id`、`label`、`position`、`classes`）

3. **Cy 的 `data` 仅存放渲染所需的最小字段**：`id`、`label`、`position`、`classes`。现有 `CyNodeData` 中的 `role`、`kind`、`form`、`degree`、`abstractionLevel` 在 `getNodeClasses` 消费完后不应再进入 Cy——Cy 不需要它们。

##### 前置发现：渲染层边界被穿越的全部点位

以下为 3.0-4 执行后渲染层外直接操作 Cy 实例的全部位置（排查范围：`frontend/src/render/` 之外的全部 `.style()` / `.addClass()` / `.removeClass()` / `.position()` / `cy.getElementById()` / `getCyInstance()` 调用）：

**点位 1：`move_node.ts` 直调 Cy 实例（~20 处）**

| 操作                                                                 | 用途                           |
| -------------------------------------------------------------------- | ------------------------------ |
| `getCyInstance()` × 6                                                | 获取模块级 Cy 实例             |
| `cy.getElementById(nodeId)` × 4                                      | 按 ID 查找节点                 |
| `.position()` × 5                                                    | 读原位置 / 光标跟随 / 弹回原位 |
| `.style('opacity', ...)` × 3                                         | 拾取时半透明 / 放置后恢复      |
| `.addClass('move-collision')` / `.removeClass('move-collision')` × 4 | 碰撞红色高亮 / 清除            |

**点位 2：`Graph.vue` 直调 Cy 实例（8 处）**

| 操作                                                                         | 用途                  |
| ---------------------------------------------------------------------------- | --------------------- |
| `renderer.getInstance()` → `cy.getElementById(...)` × 4                      | 按 ID 查找节点        |
| `.addClass('edge-source-target')` / `.removeClass('edge-source-target')` × 4 | add-edge 工具起点高亮 |

**归纳议题**：

1. **Cy 实例访问路径分裂**：`getCyInstance()`（模块级，供工具 import）与 `renderer.getInstance()`（闭包级，供 Graph.vue 通过 renderer 返回）两套获取方式并存，无明确选择规则。

2. **样式操作模式不一致**：`.style('opacity', 0.4)` 绕过 stylesheet 直接写在元素上；`.addClass('move-collision')` 走 stylesheet 路径（class 定义在 `cytoscape_style.ts`，工具只负责施加）。两种模式并存，未约定何时用哪种。

3. **视觉反馈归属分散**：add-edge 的起点高亮在 `Graph.vue` 中操作 Cy，move 的碰撞高亮在 `move_node.ts` 中操作 Cy——同一类渲染层操作散落在组件层和工具层两处。

4. **"临时例外"缺乏边界定义**：`getCyInstance()` 是 3.0-4 专为工具绕过渲染抽象而加的导出。当前未定义：哪些 Cy 操作允许直调？哪些必须通过 renderer 封装？视觉预览（position 临时修改）与样式修改是否应走同一套规则？

> 建议方向（待决策）：
>
> - 考虑为所有"视觉预览/工具反馈"提供统一的 renderer API 层——工具不直接 import `getCyInstance()`，而是调 renderer 暴露的高阶方法（如 `highlightNode(id, class)` / `moveNodePreview(id, pos)` / `resetNodePreview(id)`），由 renderer 内部处理 Cy 细节。
> - 考虑将 `Graph.vue` 中的 add-edge 高亮逻辑下移到 `add-edge.ts` handler 或统一 renderer API 中。

##### 前置发现：当前问题带来的可见后果

> 根本原因是工具层与 Cy 渲染层耦合。以下为该耦合导致的 6 个可观察问题：

1. **`syncElements()` 静默覆盖**：renderer 的 `syncElements` 走 `cy.json({ elements })` 全量替换。工具直写在元素上的 `.style()` / `.addClass()` / `.position()` 在下一次 GraphData 变更触发同步时全部丢失。当前"碰巧没出事"只因拾取放置期间不改 GraphData——这是隐式依赖，非显式约束。

2. **不可单测**：`move_node.ts` 的拾取放置状态机逻辑与 Cy DOM 操作耦合在同一函数内。要测"拾取→移动→放置"的状态流转，必须先启动 Cytoscape 实例。视觉预览逻辑与业务逻辑无法独立验证。

3. **Cy 查找样板重复**：`getCyInstance()` → `cy.getElementById()` → 操作 这个模式在 `move_node.ts` 内重复 6 次。后续每新增一个需要视觉预览的工具（orbit 预览、induce 预览），这套样板将再复制一份。

4. **无强制清理契约**：`deactivate()` 负责弹回节点、清样式。若工具异常退出（例如 mediator 被另一工具抢激活时 move_node 的 deactivate 未走到清理分支），Cy 上残留半透明节点或红色边框。无"谁弄脏谁擦"的机制保证。

5. **隐式第二条数据流**：架构定义的单向流是 `GraphData → mapper → renderer`。工具直写 `node.position(x, y)` 绕过了此路径——渲染层凭空多了一路"临时状态"，reader 需要同时关心 GraphData 和 Cy 上的 transient 状态。

6. **样式源分裂**：`.style('opacity', 0.4)` 硬编码在 `move_node.ts` 代码中，`move-collision` 定义在 `cytoscape_style.ts`。未来统一调色板或做暗色主题时，前者不会跟随变更——因为不在 stylesheet 管辖范围内。

##### 前置发现：组合式函数定位问题

1. **`use_cytoscape_renderer` 不可复用**：虽然以 Vue 组合式函数形式存在，但未能提供其他工具需要的视觉预览 API（`move_node.ts` 不得不绕过它，通过 `getCyInstance()` 自行操作 Cy）。一个可复用的渲染器组合式函数应该封装视觉预览方法（如 `moveNodePreview`、`highlightNode`），供上层消费。

2. **`use_graph_interaction` 无内部状态**：组合式函数的核⼼价值是管理响应式状态 + 生命周期绑定。但 `useGraphInteraction(cy, handlers)` 无 ref、无 watch、无 onMounted/onUnmounted——它是一个纯函数，接收外部 `cy` 实例和回调，做完绑定就结束。用组合式函数包装收益不大，作为普通工具函数即可。

3. **散落在 `frontend/src/composables/` 之外**：项目已有 `frontend/src/composables/` 目录（`useDragPosition`、`useOverflowDetection`、`useAutoFade`），而渲染层的两个组合式函数放在 `frontend/src/render/` 下，架构定位不清晰——渲染层文件按功能（mapper / style / interaction / renderer）分文件，但组合式函数的放置位置与功能分类混在一起。

// ── 视口控制（不变） ──
revealElement(elementId: string): void

// ── 视觉预览：位置 ──
setNodePosition(nodeId: string, pos: { x: number; y: number }): void

- `clearAllPreviews('move')` 只清除 move 工具的预览，不影响其他工具
- syncElements 时批量清除所有 transient 状态

> **U-1：syncElements 时 transient 状态的处理策略** ✅ 已确认
>
> 决策：`syncFromGraphData` 调用时清除全部 transient 状态。防御性设计——当前工具遵守"操作期间不改 GraphData"的契约，清理本不需要。但把隐式契约变为显式约束，代价为零（清除不存在的 transient 是空操作），防止未来意外。

> **U-2：highlightNode / highlightEdge 是否应该是 renderer 的职责？** ✅ 已确认
>
> 决策：renderer 暴露 `bindHighlight(getter: () => string | null, className: string)`，内部用 `watch(getter)` 自动管理旧 class 移除 + 新 class 施加。Graph.vue 中只需：
>
> ```ts
> renderer.bindHighlight(
>   () => mediator.activeHandler.value?.highlightNode ?? null,
>   'delete-target',
> )
> renderer.bindHighlight(
>   () => mediator.activeHandler.value?.highlightEdge ?? null,
>   'delete-target',
> )
> ```
>
> 理由：renderer 是组合式函数，用 reactive watch 管理高亮切换是其分内职责，不应让 Graph.vue 手动接 Cy 操作。

> **U-3：mapper 是否保持独立文件？** ✅ 已确认
>
> 决策：保持 `graph_element_mapper.ts` 为独立文件。renderer 的 `syncFromGraphData` 内部调用 mapper，Graph.vue 主同步也走 `syncFromGraphData`。
> 理由：mapper 逻辑核心，值得单独理解；未来导出 PNG/JSON 等场景可能需要在 renderer 之外使用 mapper。

> **U-4：use_graph_interaction 的去向** ✅ 已确认
>
> 决策：改为普通函数 `bindCyEvents(cy, handlers)`，返回 `{ destroy() }`。去掉 `use` 前缀——无内部状态，非组合式函数。
> 附随：目录更名为 `cytoscape/`（替代 `render/`），表达"此目录是 Cy 外部库的严格隔离层"的架构意图。所有 Cy 相关代码在此目录内，目录外不可见 `cytoscape` import。

> **U-5：`getInstance()` 逃生口保留否？** ✅ 已确认
>
> 决策：完全删除。所有消费方改用语义方法后，无合法需求获取裸 Cy 实例。"先删再按需加"比"保留以防万一"更健康。

> **U-6：分步策略**

### 3.1 多选机制

### 3.2 拾取放置解禁 → 已并入 3.0-3

> **本节的详细规格保留不变，实施时并入 3.0-3（move_node + 拾取放置）。** 拾取放置是 move_node 的首要消费者，基础设施与首个 handler 同步骤实现。

见 `docs/设计/06-交互逻辑.md` §预览 -> 执行

将节点移动从 Cytoscape 原生拖拽替换为拾取放置模式。后者不需要按住鼠标键移动，而是"点击拾取 → 自由移动光标 → 再点击放置"。

**流程**：

```
左键点击节点 → 节点拾取（吸附在光标上）
光标自由移动 → 节点跟随（视觉层偏移，不写 GraphData）
左键再点击  → 节点放置（写入 GraphData 作为一次 undo）
右键/Escape → 取消（节点回到原始位置）
```

**改动**：

- 禁用 `cy.nodes().grabify()`（不再使用 Cytoscape 原生拖拽）
- 进入 Arrangement 模式时启用节点拾取放置
- 推出 Arrangement 模式时恢复禁止拾取放置
- `use_graph_interaction.ts` 新增 "click to pick → follow cursor → click to place" 事件流
- 新增 `NodePickAndPlaced` 语义事件替代 `NodeDragEnded`
- 预览阶段的操作参数调整（Orbit/Path/Adjust）同样使用拾取放置

### 3.4 预览 -> 执行

> 见 `docs/设计/06-交互逻辑.md` §预览 -> 执行

认知/布局模式的操作必须经过"预览"阶段才能执行。预览阶段的操作参数调整采用拾取放置（3.2 节）。

**实现状态机**：

```
                ┌──────────┐
                │  操作选择  │
                └────┬─────┘
                     │ 选择操作 + 选择对象
                     ↓
                ┌──────────┐
         ┌─────→│  预览阶段  │
         │      └────┬─────┘
         │           │ 校验通过，用户确认
         │           ↓
         │      ┌──────────┐
         │      │  执行写入  │ → GraphData + undo
         │      └──────────┘
取消(右键/Esc)│
         └──────
```

**改动**：

- `ui_store` 或 `draft_store` 新增 `previewState`（preview data, 可调参数, 校验结果）

- 确认→写入：调用 `graphStore.applyBatchToGraph`
- 取消：清除预览状态，回到操作选择

### 待决设计问题

> **Q3**：多选节点的交互方式是什么？"Ctrl/Shift + 点击" vs "直接逐个点击（toggle 模式，再点取消选中）" vs "拖拽框选"。
>
> **建议**：拖拽框选作为主要多选方式，辅以 toggle 点击（不需要修饰键——直接点击已选中节点则取消选中，点击未选中节点则加入选中）。理由：拖拽框选是画布应用最直觉的多选方式（Cytoscape 原生支持 `boxselect`），而 toggle 点击不需要修饰键降低了操作门槛，符合"低认知负担"设计原则。Ctrl/Shift 是桌面习惯，不适合本应用的沉浸式画布体验。
>
> **Cy.js 原生选项参考**（待决策时参考）：
>
> | 方式         | 配置                                                                                                                                                                                | 选中集读取                                                                         |
> | ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
> | 框选         | `boxSelectionEnabled: true`，默认 Shift/Cmd/Ctrl + 拖拽触发；`selection-box-color` 等 core style 控制选框视觉；`box-selection: 'contain' \| 'overlap' \| 'none'` 控制每元素命中判定 | `cy.nodes(':selected')`，事件：`boxstart` → `boxselect` → `boxend` → `box`         |
> | 点击 toggle  | `selectionType: 'additive'`（点击不取消已有选中），或监 `tap` → `node.toggleSelect()` 手动实现                                                                                      | `cy.nodes(':selected')`，事件：`select` / `unselect` / `tapselect` / `tapunselect` |
> | 防止空白取消 | `autounselectify: true`（点击空白不取消全部选中）                                                                                                                                   | —                                                                                  |

> **Q4**：框选拖拽过程中，选中区域的视觉呈现是什么？
>
> **建议**：Cytoscape 原生提供的半透明蓝色选框即可。理由：不做自定义渲染——这是通用交互范式，用户不需要被教。后续如果需要统一视觉风格再替换。

### 3.5 待解决设计问题：选中状态归属

**问题**：`graph_store.ts` 当前持有 `selectedNodeId` / `selectedEdgeId`，但选中状态本质上是 UI Runtime 状态，不是 GraphData。

**两种方案**：

| 方案      | 位置             | 优点                                      | 缺点                        |
| --------- | ---------------- | ----------------------------------------- | --------------------------- |
| A（当前） | `graph_store.ts` | 与图数据邻近，组件读取方便                | 污染 GraphData Store 的纯度 |
| B         | `ui_store.ts`    | UI 状态归位，graph_store 只保留 GraphData | 部分读取路径需改到 ui_store |

**建议**：方案 A 在 Phase 2b 可接受，因为当前选中状态主要用于图操作路由；若未来 UI 需要根据选中状态做复杂反馈（如右键菜单、批量操作面板），再迁移到 `ui_store.ts`。

**结论**：暂不迁移，本问题在 Step 3 记录，后续视 UI 复杂度决定是否调整。
