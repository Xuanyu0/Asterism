# planning-with-files：定制版 vs 主流版 全面对比分析

---

## 一、总体概览

| 维度 | 主流版 (OthmanAdi) | 定制版 |
|------|-------------------|--------|
| 文件 | task_plan.md、findings.md、progress.md | 步骤.md、发现.md、提示词.md（执行契约） |
| 文件位置 | 项目根目录或 `.planning/slug/` | 阶段目录内：`步骤/`、`发现/`、`提示词/` |
| 注入策略 | 每个 turn 钩子注入（v2），或每次会话注入（v3 自主模式） | 仅会话启动时，通过 `dev-status.sh` |
| 词元成本 | 约 68% 额外开销（均值 19,926 vs 11,899） | 极低（启动时约 30 行脚本输出） |
| 恢复机制 | session-catchup.py + IDE 会话存储 | `dev-status.sh` 交叉验证 git log + 文件修改时间 + 提示词目录 + 待确认项 |
| 事实源 | 人工维护的规划文件 | git log + git diff（不可篡改） |
| 多智能体 | 默认单智能体，`.planning/` 隔离并行会话 | 原生编排者 → @fixer/@designer/@oracle/@simplifier，提示词.md 为共享契约 |
| 人类决策权 | 可选（钩子自动完成决策） | 强制（每个决策都需人类确认） |
| 适用范围 | 笼统的"复杂任务" | 明确枚举：新增功能模块、新设计模式、中大型重构、危险 BUG 修复 |
| 采用量 | 23K+ star，60+ 平台，28K+ 安装 | 内部定制 |

## 二、设计哲学的根本分歧

### 主流版："文件系统即工作记忆"（Manus 风格）

主流版根植于 Manus 的上下文工程理念：文件系统是 **LLM 工作记忆的延伸**。每个 turn 都将计划重新注入上下文，让目标始终停留在注意力窗口内。它解决的是**单个长运行智能体会话中的上下文衰减**问题。

核心命题：*"上下文窗口是 RAM，文件系统是硬盘。每个 turn 都从硬盘重新读取。"*

### 定制版："文件系统即审计轨迹 + 契约"（多智能体编排）

你的版本将规划文件视为**多智能体协作和人类审查的持久化工件**。文件的价值不在于注意力操控（重新注入），而在于：
- **提示词.md**：@fixer 和 @oracle 之间的共享执行契约，用于独立验证
- **Git**："做了什么"的权威事实源
- **`dev-status.sh`**：轻量、无状态的恢复检查，不依赖 IDE 钩子

核心命题：*"真相在 git 里。计划是契约。恢复靠交叉验证。"*

**这是根本不同的两种范式**。主流版优化的是*单智能体上下文窗口的生存能力*。你的版本优化的是*有人类监督的多智能体工作流完整性*。

## 三、各维度详细对比

### 3.1 词元效率

#### 主流版
- **每个 turn 的成本**：`PreToolUse` 钩子在*每一次工具调用前*运行 `head -30 task_plan.md`（甚至更多），每个 turn 向上下文注入 200+ 词元。
- **实测开销**：68% 更多词元（19,926 vs 11,899 均值），17% 更多时间（115s vs 98s）。
- **v3 自主模式（缓解措施）**：去掉每次工具调用的注入，只保留每次 turn 的注入。基准测试："v2.21 评估显示 68% 的词元税"，v3 自主模式旨在降低这一开销。
- **钩子脚本执行时间**：每次钩子触发 289ms（v3.6.0 优化后），此前为 2.0-2.4s。

#### 定制版
- **仅每次会话的成本**：`dev-status.sh` 在会话启动时运行一次，输出约 30 行。
- **无每次工具调用的注入**：没有任何钩子在每步操作时重新注入计划内容。
- **Git 为事实源**：无需读取计划文件来更新状态——`git log` 和 `git diff` 成本更低。

**结论**：定制版在词元效率上显著占优，彻底消除了每次工具调用的注入。

**但需注意**：主流版的每次工具调用注入是*有意为之*——这是防止目标漂移的机制。你的版本放弃了这一机制，接受了长会话中漂移风险可能更高的事实（通过编排者 + 人类把关来缓解）。

### 3.2 人类决策权与决策质量

#### 主流版
- **仅在完成时停止**：Stop 钩子阻止智能体在所有 phase 完成前停止。这是唯一强制性的人类把关。
- **可选的 plan mode 衔接**：*可以*先用 Claude Code 的 plan mode 设计，再交给 skill 执行，但这是可选的。
- **默认自主**：计划一旦设定，智能体基本自行驱动。
- **社区的批评**：Issue #206 记录了 `steer/followUp` 的注入会破坏 `AskUserQuestion` 等交互式工具——钩子的引导内容被当作对话框的回复消费，导致人类被静默绕过。

#### 定制版
- **强制性的人类把关**："所有架构决策都不由编排者独立做出。"
- **过滤后的适用范围**：系统只对特定任务类别激活——人类不需要审查琐碎工作。
- **执行契约**：提示词.md 是 @oracle 验证的契约——一种形式化的验证步骤，映射了多智能体编排模式中的"Planner-Generator-Evaluator"（规划者-生成者-评估者）模式。
- **从设计上保证更高决策质量**：人类在执行前审查架构选择；智能体机械执行。

**结论**：定制版在人类监督的显式性和护栏的完善性上胜出，但代价是较低的自主性——人类必须保持参与。

### 3.3 崩溃恢复的完整性

#### 主流版
- **机制**：`session-catchup.py` 读取 IDE 会话存储的 JSONL 文件（`~/.claude/projects/`、`~/.codex/sessions/`）。
- **钩子驱动**：`SessionStart` 钩子自动运行恢复。`PreCompact` 钩子在压缩前刷入进度。
- **依赖 IDE 元数据**：恢复质量取决于 IDE 存储了什么。各 IDE 的会话存储格式不同（OpenCode 用 SQLite，Claude Code 用 JSONL，Codex 用 sessions/）。
- **已知问题**：
  - v3.2.0：session-catchup.py 在 Windows 上数月不可用
  - OpenCode SQLite：支持有限，SQLite 查询失败时需要人工操作
  - #146/#148：Codex 中跨会话上下文泄漏（v2.36.0 修复）
  - #195：一次性 codex exec 会话被劫持（v3.4.0 添加 PLANNING_DISABLED=1）

#### 定制版
- **机制**：`bash scripts/dev-status.sh`——交叉验证四个独立信号：
  1. `git log`——实际提交了什么
  2. 文件修改时间——哪些文件被改动但未提交
  3. 提示词目录是否存在——是否写过 spec？
  4. 发现文件中的待确认项——是否有未解决的问题？
- **不依赖 IDE**：使用 git + 文件系统，在任何地方行为一致。
- **Git 为事实源**："做了什么"的权威记录，而不是可能失步的人工维护 `progress.md`。
- **无钩子**：显式的启动命令，不依赖自动检测。

**结论**：定制版在恢复机制上更健壮。基于 git 的恢复比刮取 IDE 会话存储更可靠、跨平台。多信号交叉验证比单一的 `task_plan.md` 存在性检查更可靠。

**但需注意**：主流版的恢复是*自动的*（钩子在会话启动时触发）。定制版需要显式执行 `dev-status.sh`，多一件需要记住的事。

### 3.4 多智能体兼容性

#### 主流版
- **设计上为单智能体**：系统为一个 Claude Code/Codex/Cursor 会话构建。
- **`.planning/` 隔离（v2.36.0+）**：并行会话可以使用 `.planning/slug/` 目录，但它们相互独立——之间没有协调。
- **已知问题**：
  - #146/#148：并行会话读写同一文件，导致 phase 状态损坏、发现项交叉污染
  - #195：一次性 `codex exec`（如 CI 审查 bot）被劫持进入 plan 执行循环
  - 社区回应：`PLANNING_DISABLED=1` 退出机制，用于 CI/只读工具
- **无原生角色分离**：所有智能体以相同"角色"执行相同计划
- **值得注意的 fork**：`plan-cascade`（@Taoidle）——"多层次任务编排、并行执行、多智能体协作"——明确针对这一缺口

#### 定制版
- **从底层原生支持多智能体**：
  - **编排者**：中央调度者，不做架构决策
  - **@fixer**：实现智能体
  - **@designer**：设计/架构决策智能体
  - **@oracle**：验证智能体（根据提示词.md 契约交叉检查）
  - **@simplifier**：复杂度缩减智能体
- **提示词.md 为共享契约**：执行契约在 @fixer 和 @oracle 之间共享，用于独立验证——实现了干净角色隔离的"Planner-Generator-Evaluator"模式。
- **无智能体身份混淆**：每个智能体有明确的角色、上下文范围和权限。
- **无交叉污染风险**：独立的 @oracle 审查（类似于 SPOQ 的"盲审"，即审查者看不到执行者的完成声明）。

**结论**：定制版在多智能体支持上显著胜出。主流版的多智能体故事是事后补丁（v2.36.0 因 issue #148 才加入）。你的版本从一开始就是一等架构特征。

### 3.5 上手难度

#### 主流版
- **一行命令安装**：`npx skills add` 或 `/plugin marketplace add`
- **60+ 平台可用**：Claude Code、Codex、Cursor、Gemini CLI、GitHub Copilot、Kiro、OpenCode 等
- **无需写代码**：SKILL.md 文件自身包含所有钩子脚本、模板和规则
- **立即可用**：安装后，智能体立即生效——遇到复杂任务自动创建文件
- **丰富文档**：18+ 平台特定指南、排错、FAQ、基准测试

#### 定制版
- **基于脚本的配置**：需要 `dev-status.sh`、目录结构、编排者配置
- **需要团队导入**：多智能体角色、提示词.md 契约格式、阶段目录约定
- **需要人类遵守流程**：必须记得执行 `dev-status.sh`，必须显式批准决策
- **首次会话摩擦更高**，但配置完成后每次会话的开销更低

**结论**：主流版入⻔门槛远更低——一行命令，零配置。你的版本需要更多前期投入。

### 3.6 维护成本

#### 主流版
- **人工更新 progress.md**：必须保持 `progress.md` 更新——PostToolUse 钩子提醒你但不替你写。
- **findings.md 整理**：研究笔记必须主动写入。忘了写，上下文就不在。
- **计划文件生命周期**：无归档（v3.5.0 后的刻意设计）。完成的计划被覆盖或遮蔽，不自动保存任何东西。
- **Gitignore 膨胀**：三个文件 + `.planning/` 默认被 gitignore，意味着它们不进版本控制。
- **钩子脚本需持续更新**：每次 IDE 更新可能需要更新钩子。
- **SHA-256 认证**：可选但增加了认证管理负担。

#### 定制版
- **Git 是事实源**：无需人工跟踪进度——git log 告诉你发生了什么。
- **提示词.md 为契约**：一旦写完，@oracle 机械地据此验证。比手写进度少很多维护。
- **`dev-status.sh` 稳定**：简单的 shell 脚本，不依赖 IDE 内部实现或钩子 API。
- **目录结构自说明**：阶段目录（步骤/、发现/、提示词/）按工作单元组织。
- **版本变动更少**：不依赖 60 个平台上快速演进的 SKILL.md 标准或钩子 API。

**结论**：定制版长期维护成本更低。不依赖（1）每次操作的手动文件更新，（2）IDE 钩子生命周期管理，（3）追踪快速迭代的 skill 更新。

### 3.7 大规模项目下的伸缩性（10+ 步骤）

#### 主流版
- **v3 自主/门控模式**：为长时间运行的智能体专门打造。
- **账本系统**：JSONL 运行账本替代原始 `progress.md` 尾部，提供结构化摘要。
- **PreCompact 钩子**：压缩前刷入进度。
- **/plan-loop**：Claude Code `/loop` 集成（每 10 分钟重新读取规划文件）。
- **/plan-goal**：从活跃计划推导终止条件。
- **会话隔离**：`.planning/YYYY-MM-DD-slug/` 用于并行任务目录。
- **词元税累积**：超过 50 次工具调用后，68% 的开销变得显著。
- **已知限制**："session-catchup.py 对 OpenCode 支持有限，因为不同的会话存储格式"——恢复质量因平台而异。

#### 定制版
- **阶段目录自然伸缩**：每个阶段有独立目录，跨阶段无歧义。
- **Git log 天然伸缩**：Git 为大项目而生。`dev-status.sh` 交叉验证成本随 git 历史对数级增长。
- **多智能体并行**：@designer、@fixer、@oracle、@simplifier 可以在不同阶段并行工作。主流版本质上串行（一个智能体，一个上下文）。
- **无累积词元税**：无每次工具调用的注入，长会话不递增付费。
- **人类审查是瓶颈**：10+ 步骤后，每个决策点都需要人类批准会降低吞吐。这是为质量付出的刻意代价。

**结论**：取决于优先级。纯自主执行，主流 v3 的账本和自动恢复伸缩性更好。人类监督的多智能体工作，你的架构伸缩性更好——添加并行智能体而不增加词元开销。

## 四、主流版的已知缺陷

### 4.1 安全漏洞（现已修复，但设计上仍然脆弱）

有记录的最严重问题：

> *"PreToolUse 钩子在每一次工具调用前重新读取 `task_plan.md`。这意味着任何写入 `task_plan.md` 的内容都会在后续每次工具使用时注入上下文……这是一种间接提示注入放大模式。"*

修复方案（v2.37.0）：通过 `/plan-attest` 进行 SHA-256 认证。启用后，钩子拒绝注入被篡改的计划内容。但这是*可选启用*的——默认安装不防护。

### 4.2 计划文件注入劫持会话

Issue #195 记录了 v3.4.0 前的一个严重故障模式：

> *"一次性 `codex exec` 运行（CI 审查 bot、只读研究智能体、嵌套编排者）仅仅因为与不完整计划共享工作目录就被劫持：计划上下文被注入，实际输出被重定向到 `progress.md`，伪造的已完成 phase 被追加到 `task_plan.md`。"*

**你的版本不存在此问题**：无钩子、无自动注入，编排者显式管理哪个智能体在做什么。

### 4.3 词元税是真实的、显著的

来自 Neodrop 的独立分析：

> *"成本是真实的：开 skill 平均 19,926 词元/任务，不开 11,899（约多 68%），115 秒 vs 98 秒（约多 17%）。"*

作者将其形容为*"用速度换结构"*——刻意的权衡，但在极长任务上会叠加。

### 4.4 默认瞬态——计划不被归档

Issue #202：

> *"任务完成后……`task_plan.md`（根模式）直接被覆盖……旧的 `.planning/slug/` 目录不再作为活跃计划。没有归档步骤。"*

维护者的回应：*"瞬态行为是一致的、有承载力的……但它从未被声明为设计决策。它是碰巧能用，不是刻意原则。"*

**你的版本避免了此问题**：git 就是归档。每个计划迭代、每个契约、每个决策都提交了。

### 4.5 对简单任务过重

来自 README 自身：*"跳过：简单问题、单文件修改、快速查找。"*

68% 的词元税对短任务一无所获，而且钩子增加了延迟和上下文噪音。

### 4.6 "Plan Mode" 困惑

多个 GitHub issue（如 #19、#17、#58）显示用户对 planning-with-files 和 Claude Code 原生 `/plan` 模式的交互感到困惑。维护者的回答：

> *"Plan mode 在执行前设计方法。planning-with-files 在工作运行时将执行状态持久化到磁盘。"*

这一区别并不明显，需要学习。用户还问：Claude Tasks 引入后它是否还相关（Issue #58）。

## 五、主流版做得更好的地方

### 5.1 零摩擦安装和配置

一行命令：`npx skills add OthmanAdi/planning-with-files`。然后它就在 60+ 个平台上工作了。你的版本需要手动脚本配置、目录搭建、编排者配置。

### 5.2 跨 IDE 可移植性

主流版为 Claude Code、Codex CLI、Cursor、Gemini CLI、GitHub Copilot、Kiro、Mastra Code、OpenCode、Hermes、CodeBuddy、FactoryAI Droid、Continue、Pi Agent、OpenClaw、Antigravity、Kilocode、AdaL CLI、Zed、Amp、Warp、Devin 等 **18+ 个平台**设有专用钩子和配置指南，均有自动化集成。

你的版本依赖编排者存在且智能体按特定角色配置。

### 5.3 `/clear` 后自动恢复

主流版的 `session-catchup.py` + 钩子意味着 `/clear` 后智能体自动恢复。无需显式命令。

你的版本需要用户在会话启动时 `bash scripts/dev-status.sh`。多一步要记住的操作。

### 5.4 完成门强制执行

Stop 钩子阻止过早完成：*"当智能体认为自己完成了，Stop 钩子运行完成检查：所有 phase 是否标记完成，是否一切已记录？如果没有，它被送回继续完成。"*

你的版本依赖 @oracle 根据提示词.md 验证——有效，但智能体没有强制性的 Stop 钩子阻止它谎称完成。

### 5.5 生态和社区

- 23K+ star，2K+ fork，28K+ 安装（skills.sh）
- 5 种语言翻译变体（阿拉伯语、德语、西班牙语、简体中文、繁体中文）
- 活跃的 issue 处理（200+ 已关闭 issue，快速响应）
- 针对特定需求的 fork（plan-cascade 做多智能体，devis 做面试优先）
- 安全审计：Gen Agent Trust Hub、Socket、Snyk

你的版本受益于团队内部对齐，但没有外部社区验证、漏洞报告或贡献。

### 5.6 可测量的基准测试

主流版有**实际的基准数据**：
- 开 skill 后 96.7% 通过率 vs 不开的 6.7%（+90 个百分点）
- 5.0 次 turn 恢复 vs 不开的 13.3 次
- 5 种任务类型上的 30 个断言
- Tessl CI 的独立验证

## 七、设计权衡矩阵

| 你的设计决策 | 主流选择 | 权衡 |
|-------------|---------|------|
| **提示词.md 执行契约** | 无等价物 | + 支持独立 @oracle 验证。+ 正式角色隔离。- 每阶段多维护一个文件 |
| **Git 为事实源** | 手写 progress.md | + 不可变的审计轨迹。+ 计划与现实之间不漂移。- 需要提交纪律 |
| **阶段子目录（步骤/发现/提示词/）** | 根目录或 `.planning/slug/` 下平铺 3 个文件 | + 每阶段干净组织。+ 无文件冲突。- 更多导航开销 |
| **`dev-status.sh` 交叉验证** | session-catchup.py + IDE 钩子 | + IDE 无关。+ 多信号可靠性。+ 实现更简单。- 需要显式执行 |
| **无每次工具调用注入** | UserPromptSubmit 钩子重新注入计划 | + 大幅节省词元。+ 上下文窗口更干净。- 长会话中目标漂移风险更高 |
| **强制性人类把关** | 默认自主，仅 Stop 钩子 | + 更高决策质量。+ 早期捕获架构错误。- 吞吐更低。- 人类必须保持参与 |
| **显式适用范围过滤** | "复杂任务用即可"（模糊） | + 防止琐碎工作误用。+ 清晰知道何时激活。- 需要用户判断来分类任务 |
| **多智能体角色** | 单智能体 + `.planning/` 隔离 | + 真正的角色分离。+ 并行执行。+ 独立验证。- 编排者开销 |

### 结论

**主流版擅长**：让单个智能体完成长任务而不丢失线索，配置成本最低，平台支持广泛。它用词元换结构。

**你的版本擅长**：有人类监督的多智能体工作流，需要 git 可验证的审计轨迹和正式执行契约的场景。它用自主性换可靠性和可验证性。

**研究的核心洞见**：这个模式没有哪个版本对所有人都正确——社区也知道这一点。`plan-cascade`（多智能体）、`devis`（面试优先）、`multi-manus-planning`（git 同步、多项目）等 fork 的存在，说明实践者正在自我选择，趋向匹配自己工作流哲学的变体。你的版本占据了一个特定利基——多智能体、人类把关、git 锚定——开源社区中还没有人完整地将其打包。
