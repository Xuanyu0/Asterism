# 08-异常处理机制补全

---

## 1.通道语义收窄与开发者通道落地 ✅

### 目标

项目异常处理从"三类通道混杂、部分失败路径静默无痕"收敛为**每条失败路径恰好走一个语义明确的通道**：

1. **validation 通道**（`ValidationResult` / `lastValidationResult`）= **图规则校验专用**——产品设计者定义的用户操作自然失败模式（用户调整操作即可补救）。
2. **开发者通道** = 图规则校验以外的一切（数据损坏、链断裂、环、I/O 失败）——工程师可见、用户默认不可见，当前落地为 `console.warn`。
3. **正常状态**（图不存在）与**系统异常**（图损坏）从此可区分。

### 1.1.通道边界判定标准

**子目标**：

* 确立判定标准：**错误是否属于"产品设计者定义的自然补救路径"**（用户通过调整操作即可解决）→ validation 通道；否则（补救方式在产品语义之外）→ 开发者通道。
* 注意精化：**"由用户操作触发" ≠ "产品定义的自然失败模式"**。图损坏同样由用户操作（切图）触发，但产品无法为用户定义补救方式，仍归开发者通道。
* 依据 validation 通道的既有设计证据收窄其语义（不新增通道结构）：
  * `validation.ts` 文件头明示"图规则校验结果的通用类型"；`ValidationTargetType` 仅 `graph | node | edge`——对象枚举即图域实体。
  * 术语映射表：`validate` = "操作前规则检查，不修改数据"。
  * `05-规则分类.md`：自定义规则（图规则）"针对 GraphData 中的元素定义、所有修改操作执行"；硬性规则"违反后编程语言报错、抛异常或崩溃"——数据损坏属于硬性规则层，与 validation 通道天然对立。

* 不确定度：低（概念已确定，仅文档化）
* 算法复杂度：低
* 工作量：低

### 1.2.开发者通道形式确立

**子目标**：

* 开发者通道 = `console.warn`（工程师可见、自动带调用栈、零依赖），为生产期升级遥测（Sentry 等）预留替换点——升级只换"记录"段实现，检测与降级逻辑不动。
* 确立"三段结构"：**检测**（发现异常语义）→ **降级**（决定跳过/默认值/继续用）→ **记录**（`console.warn`，带结构化信息 code / targetId / message）。
* 补齐现状缺口：此前若干路径只有检测+降级、没有记录（如 `graph_persistence` 的 JSON.parse 失败静默吞掉），损坏数据完全无痕。

* 不确定度：低
* 算法复杂度：低
* 工作量：低

### 1.3.处理函数（辅助函数）组织方式

**子目标**：

* 按**异常语义类别**拆分辅助函数（每个辅助 = 检测一种异常语义 + 写入对应通道），不按调用点拆，避免多调用点复制粘贴。
* 私有辅助函数放文件末尾（遵循项目代码规范），主逻辑保持"规则表达"形态：调用辅助 → 按 reason 分派 → 正常路径继续。
* 处理手法定型：**信任边界 try-catch 一次捕获 → 转换成状态值（判别联合）→ 调用方 if 分派 + 处理函数**。try-catch 只出现在边界（读存储/解析处），之后全走值传递，不扩散。

* 不确定度：低
* 算法复杂度：低
* 工作量：低

### 影响范围（通道架构前后对比）

```
旧：                                             新：
lastValidationResult（混装）                     lastValidationResult = 图规则校验专用
  ├─ 规则校验（applyBatch / 工具预校验）✅           ├─ 规则校验（applyBatch / 工具预校验）
  ├─ LOAD_FAILED（I/O 失败借用规则通道）             └─ （清空非规则写入）
  └─ ANCESTOR_CHAIN_BROKEN（valid:true 警告）     
      └─ 死通道：写了没人读（Graph.vue 只显 error）  console.warn（开发者通道·新增）
                                                      ├─ 图损坏（corrupted）
loadGraph：missing/corrupted 折叠为 null              ├─ 父链断裂（ANCESTOR_CHAIN_BROKEN 迁入）
initRegistry：损坏被当作"首次使用"掩盖                 └─ 环检测（防御日志）
                                                    loadGraph：判别联合，missing 静默 / corrupted 入开发者通道
                                                    initRegistry：首次使用 vs 损坏可区分
```

涉及文件：`graph/graph_persistence.ts`、`graph/graph_store.ts`、`graph/adapters/useNavigationAdapter.ts`、`views/Graph.vue`（仅确认消费逻辑不变）。

### 决策项

**已确定决策**

- **损坏图（corrupted）本步骤只落地开发者通道**：`console.warn` + 返回 false + 现有 UI 兜底行为不变；"图谱数据似乎已损坏"式的用户提示（含重建/忽略入口）作为独立 UX 后续排期（涉及提示时机、文案、恢复入口的产品行为设计，不并入本步骤）

- 通道边界判定标准：**产品定义的自然补救路径** → validation；否则 → 开发者通道（"用户操作触发"不构成归入 validation 的理由）
- validation 通道 = 图规则校验专用，依据文件头声明 + `ValidationTargetType` 枚举 + 术语映射 + 规则分类文档收窄语义
- 开发者通道 = `console.warn`（当前阶段），将来可替换为遥测服务；三段结构（检测/降级/记录）
- **图不存在（missing）= 正常状态，静默无告警**；**图损坏（corrupted）= 系统异常，入开发者通道**
- 方案 A：`loadGraph` 改签名返回判别联合（区分 missing / corrupted / ok）
- 处理手法：信任边界 try-catch 一次捕获 → 状态值传递 → if 分派 + 处理函数；try-catch 不扩散
- 辅助函数按异常语义类别拆分，私有辅助放文件末尾，主逻辑保持编排形态
- **graph-engine 不动**（0 throw 现状正确；`PersistenceAdapter` SPI 属引擎契约，签名不因前端通道设计变更）
- **父链断裂默认归开发者通道**（补救方式在产品语义之外）；若将来定义为全局规则（"父链必须可回溯到根"）则合法进 validation 通道

## 2.loadGraph 判别联合（方案 A）✅

### 目标

`loadGraph` 从"丢失原因的 `GraphData | null`"升级为保留原因的判别联合，使"图不存在"与"图损坏"从信号层面可区分，解开 `initRegistry` 的语义黑洞。

### 2.1.签名变更与边界转换

**子目标**：

* `graph_persistence.ts` 定义判别联合：`{ ok: true; graph: GraphData } | { ok: false; reason: 'missing' | 'corrupted' }`。
* `loadGraph` 内部完成信任边界转换：key 不存在 → `missing`；`JSON.parse` 抛异常（try-catch 一次捕获）→ `corrupted`。
* `saveGraph` / `deleteGraph` / `listSavedGraphIds` 不变。

* 不确定度：低（类型 + 单函数改造）
* 算法复杂度：低
* 工作量：低

### 2.2.调用方适配与 initRegistry 黑洞解除

**子目标**：

* 调用方全部适配判别联合：
  * `graph_store`：`loadGraphToView`、`initRegistry`、`buildGraphPath`（惰性加载父图处）
  * `useNavigationAdapter`：`listRootGraphInfos`（`continue` 跳过加载失败图的语义拆分为"跳过 missing 无关 / corrupted 入开发者通道"）
  * `localStorageAdapter.list()`（过滤 `ok` 分支）
* `initRegistry` 语义明确化：`missing` → "首次使用/无历史"正常路径；`corrupted` → 开发者通道记录，不再与首次使用混淆。
* 引擎 SPI `PersistenceAdapter.load` 保持 `GraphData | null` 不动（边界处适配）。

* 不确定度：中（调用方数量多，逐一核对行为）
* 算法复杂度：低
* 工作量：中

### 影响范围

```
graph_persistence.ts
  loadGraph: GraphData | null  →  判别联合（内部边界 try-catch）
  调用方：
    graph_store（loadGraphToView / initRegistry / buildGraphPath）
    useNavigationAdapter（listRootGraphInfos）
    localStorageAdapter.list（适配过滤）
  （引擎 PersistenceAdapter 接口不动）
```

### 决策项

**已确定决策**

- 方案 A（改签名）而非新增 probeGraph——语义最干净，一个函数表达完整状态；改动面已核实可控
- 判别联合形态：`{ ok: true; graph } | { ok: false; reason: 'missing' | 'corrupted' }`
- `missing` 与 `corrupted` 在信号层面必须可区分

## 3.loadGraphToView 与剩余静默路径治理 ✅

### 目标

`loadGraphToView` 退出对 validation 通道的借用；`buildGraphPath` 的防御路径补记录；`deleteRootGraphTree` 静默拒绝确认 UI 不可达、不补反馈。

### 3.1.loadGraphToView 重构

**子目标**：

* `LOAD_FAILED` 拆分：`missing` → 防御态（正常路径下不可达，静默返回 false）；`corrupted` → 开发者通道（`console.warn` + 返回 false），不再写 `lastValidationResult`。
* `ANCESTOR_CHAIN_BROKEN` 从 `lastValidationResult` 迁入开发者通道（`console.warn` 带 code/targetId/message），同时消除"valid:true 警告写了没人读"的死通道现象。
* 移除迁移后遗留的空 warning 写入分支。

* 不确定度：中（拆分语义 + 行为变更需测试确认）
* 算法复杂度：低
* 工作量：中

### 3.2.静默路径治理

**子目标**：

* `buildGraphPath` 环检测 / 父缺失：保留防御行为，补 `console.warn` 记录（不升级用户可见）。
* `deleteRootGraphTree` 静默拒绝：查证 NavigationPanel 双层防护（删除按钮仅对非当前根图渲染 + `requestDeleteRoot` 前置 return），"禁止删除当前根图"分支 UI 不可达——**不补反馈**；适配层防御保留（防御未来引入删除根操作入口）。
* `undo` 空栈：确认保持 `return false`（状态边界，非错误；UI 禁用属交互层范畴）。

* 不确定度：中
* 算法复杂度：低
* 工作量：低

### 影响范围

涉及文件：`graph/graph_store.ts`（loadGraphToView / initRegistry / buildGraphPath + 处理函数拆分）、`views/Graph.vue`（确认 `canvasErrorIssues` 语义：收窄后仍只消费规则校验 error，逻辑不变）。

### 决策项

**已确定决策**

- `deleteRootGraphTree` **不补反馈**：NavigationPanel 已双层防护（按钮 `v-if` 非当前根图 + `requestDeleteRoot` 前置 return），"禁止删除当前根图"分支 UI 不可达；适配层防御保留，防御未来删除根操作入口
- `buildGraphPath` 环检测 / 父缺失：保留防御 + 补 `console.warn`，不升级用户可见
- `undo` 空栈：保持 `return false`，不写任何状态（状态边界，非错误）
- `Graph.vue` 消费逻辑不变（收窄后更纯粹：面板只服务规则校验）
