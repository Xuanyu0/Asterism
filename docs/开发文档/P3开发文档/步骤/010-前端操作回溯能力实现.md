# 010-前端操作回溯能力实现

---

## 1. commitBatchToGraphs 双存接线 ⏳

### 目标

`commitBatchToGraphs` 从"快照式撤销占位"升级为"双存日志写入"——每次用户操作（一批）在执行的同生命周期内构造逆元并写入 OperationLog，undo/redo 得以复用同一执行引擎。

### 1.1. 逐操作逆元构造（回调方案）

**子目标**：

* `commitBatchToGraphs` 调用 `applyBatch` 时传入 `onBeforeEachOperation` 回调——回调内执行 `createReversal(graphBeforeOp, op)`，item 级逆序收集（后执行先撤销）。
* **图级操作跳过逆元构造**：回调对 `add_graph` / `delete_graph` 不调用 createReversal（图级逆元已删除，见 09-1.3）——它们在 entry 组装时提取为 graphSignals。
* 批量内逐操作循环：预校验整批（validate-all-first）→ 全部通过后逐操作 [构造逆元 → 执行 → 更新 latestGraphs]——任一操作校验失败整批不执行、不记录（事务性保持现状）。
* 逆元构造失败（显式错误，见 09-1.4）→ 阻断整批提交。

* 不确定度：低（接线逻辑明确，模型基准定案）
* 算法复杂度：低
* 工作量：中

### 1.2. entry 组装与写入 + recordLog 开关

**子目标**：

* 整批成功后，函数体末尾组装 entry：`operation`（按图分组的正向操作，含图级操作）+ `reversalOperations`（按图分组、item 内逆序的图内逆元）+ `graphSignals`（从批操作提取：add_graph → added、delete_graph → deleted）→ `parentIndex = cursor` → 追加 + `cursor++`。
* `commitBatchToGraphs(batch, { recordLog?: boolean })` 新增开关，默认 `true`；undo/redo 传 `false`（不追加日志，游标由 undo/redo 自己移动）。
* 日志与状态同生命周期：整批成功（执行 + 记录）或整批失败（都不发生）。

* 不确定度：低
* 算法复杂度：低
* 工作量：中

### 1.3. 图级操作软删兑现 + graphSignals 处理（内存版雏形）

**子目标**：

* `delete_graph` 兑现从"unregister + 硬删持久化"改为"**unregister + 保留持久化**"（软删雏形）——保证 undo delete_graph 能从持久化 `loadGraph(graphId)` 恢复。
* `add_graph` 兑现保持"register + saveGraph"。
* **tombstone（防复活标记）不在本步骤**——已注销图在 listSavedGraphIds / 惰性加载中可能复活，属已知限制，步骤 011（IndexedDB + tombstone）补齐。
* **图级兑现收口**：register / unregister / 软删 / 从持久化加载注册抽为单一模块（graph_signals），正向第三阶段、undo 组装、redo 统一走它——图级正/逆向执行集中一处，对齐"图级执行在前端"原则。
* undo 组装时按 entry.graphSignals 处理图级：注销 `added`（撤销 add_graph）、`loadGraph` 加载注册 `deleted`（撤销 delete_graph）。

* 不确定度：中
* 算法复杂度：低
* 工作量：低

### 影响范围

```
graph_store.ts（commitBatchToGraphs）：
  旧：applyBatch 整批 → 拍 graphView 快照入 undoStack → 更新 state → 兑现信号 → 持久化
  新：applyBatch(回调构造逆元) → 整批成功后组装 entry 写日志 → 更新 state
      → 兑现信号（delete_graph 软删）→ 持久化
      └─ recordLog: false 时跳过日志写入（undo/redo 用）
```

涉及文件：`frontend/src/graph/graph_store.ts`、`frontend/src/graph/adapters/useGraphOperationAdapter.ts`（透传 options）。

### 决策项

**已确定决策**：

* 逆元构造在前端回调内（applyBatch 的 `onBeforeEachOperation`），引擎无感知；**图级操作（add_graph/delete_graph）跳过逆元构造**（09-1.3：图级逆元已删除）
* 一次 commitBatchToGraphs = 一条 entry = 一次回溯单元；entry 按图分组双存 + graphSignals 图级元数据
* recordLog 开关（默认 true；undo/redo false）
* delete_graph 兑现改为软删（保留持久化）——tombstone 属 011
* 图级兑现收口到单一模块（graph_signals）——正向第三阶段 / undo / redo 统一走它

## 2. store 日志状态与 undo/redo 执行路径 ⏳

### 目标

store 新增 OperationLog / redoStack 状态；undo/redo 成为"读日志 → 组装 → 复用 commitBatchToGraphs（不记日志）→ 游标移动 → 视图一致性"的统一路径。

### 2.1. 日志状态

**子目标**：

* store 新增 `operationLog: { entries: OperationLogEntry[]; cursor: number }`（共享状态，符合"唯一回溯入口 undo 在 store"判定）。
* 新增 `redoStack: number[]`（运行时撤销足迹，**不持久化**，跨会话从空开始——已知限制 MVP 接受）。
* 移除 `undoStack: GraphData[]`、`MAX_UNDO_STACK_SIZE` 及快照入栈/弹栈逻辑；`undo()` 重写为日志驱动。

* 不确定度：低
* 算法复杂度：低
* 工作量：中

### 2.2. applyEntry 原语（undo/redo/timeLeap 共用）

**子目标**：

* 抽取内部原语 `applyEntry(entryIndex, direction)`：读 entry 双存 → 组装 batch（direction = 逆向执行 reversalOperations + graphSignals 图级回退 / 正向执行 operation + 图级信号兑现）→ `commitBatchToGraphs(batch, { recordLog: false })` → 游标移动。
* **011 时间跳跃（timeLeap）的前置依赖**：timeLeap = applyEntry × 路径长度（上溯段逆向、下溯段正向）——本步骤必须抽出此原语，否则 011 需先补重构。

* 不确定度：低
* 算法复杂度：低
* 工作量：中

### 2.3. undo 执行路径

**子目标**：

* `undo()`：cursor < 0 → return false（不写状态，08 已定边界）；`applyEntry(cursor, 'reverse')`——读 `entries[cursor]` → 组装逆元 batch：
  * **三段式顺序**（图级与图内交错，保证图内逆元执行时目标图在 registry）：
    * ① **图级恢复**：`deleted` 逆序 → `loadGraph` + 注册（撤销 delete_graph）——**最先**，供后续图内逆元使用；依赖软删（数据保留，010-1.3）
    * ② **图内逆元**：`reversalOperations` 顺序遍历 → 组装（graphId → registry 解析）→ applyBatch
    * ③ **图级消失**：`added` 逆序 → 注销（撤销 add_graph，数据保留）——**最后**，图内逆元用完后才让本次新建的图消失
  * 验证：induce 批（added=[S]）= ②图内（S 在 registry）→ ③注销；update+delete_graph 批（deleted=[S]）= ①注册 S → ②图内逆元。两场景均自洽
  * → `commitBatchToGraphs(batch, { recordLog: false })` → 成功后 `cursor--` + 撤销的 entry 压入 redoStack。
* 视图一致性：undo 后若 graphView 指向被注销图（撤销含 add_graph 的批且正在查看该子图）→ 沿 parentGraphId 上溯找活跃图（或根图）+ graphPath 重算。
* 逆元执行失败（防御）→ 不移动游标，错误入开发者通道。

* 不确定度：中（视图一致性是新逻辑）
* 算法复杂度：低
* 工作量：中

### 2.4. redo 执行路径

**子目标**：

* `redo()`：redoStack 空 → return false（redo 可用 ⟺ 用户上一步是 undo）；弹出栈顶 entry 索引 → `applyEntry(index, 'forward')`——组装正向 batch（entry.operation，add_graph 自带数据无需加载）→ `commitBatchToGraphs(batch, { recordLog: false })` → 成功后 cursor 前进到该 entry。
* redo 比 undo 简单：正向数据自带，无动态加载；图级信号由 commitBatchToGraphs 第三阶段兑现；视图一致性对称处理。
* **无分支选择**——redo 永远重走"刚撤销的那一条"（redo 栈唯一确定），设计文档"≥2 子弹选择"是分支导航语义，不采用。

* 不确定度：低
* 算法复杂度：低
* 工作量：低

### 2.5. 树形分支

**子目标**：

* 新操作追加：`entry.parentIndex = cursor`，cursor = 新索引。
* 开分支判断 = 当前 cursor 是否有子节点（`entries.some(e => e.parentIndex === cursor)`）——有则新操作必然形成新分支（旧分支保留）；无则线性延续。无需"已遍历"等额外字段。
* 执行新操作（无论分支或延续）→ **清空 redoStack**（redo 失效）。
* 日志 entry 永不删除——完整记录学习路径（含试错分支）。

* 不确定度：低
* 算法复杂度：低（分支派生 = 一次 filter）
* 工作量：低

### 影响范围（store 结构对比）

```
graph_store.ts：
  旧：graphView / graphPath / graphRegistry / undoStack / lastSaveTime / lastValidationResult
  新：graphView / graphPath / graphRegistry / operationLog(entries+cursor) / redoStack
      / lastSaveTime / lastValidationResult
      └─ undoStack、MAX_UNDO_STACK_SIZE、快照逻辑删除；undo()/redo() 重写

  undo/redo 调用链：
  UI 触发（待 04）→ store.undo()/redo() → applyEntry(entryIndex, direction)
                              → 组装（图级 graphSignals + 图内双存）→ commitBatchToGraphs(recordLog:false)
                              → 游标移动 → 视图一致性
  timeLeap（011）= applyEntry × 路径长度（上溯逆向 + 下溯正向）
```

涉及文件：`frontend/src/graph/graph_store.ts`、`frontend/src/graph/adapters/useGraphOperationAdapter.ts`（新增 undo/redo 暴露）、相关测试（fold/expand + undo 套件更新）。

### 决策项

**已确定决策**：

* undo/redo = 复用 commitBatchToGraphs + recordLog:false + 游标移动（报告决策点 3 定案）
* redo 栈模型：undo 压栈 / redo 弹栈 / 新操作清栈；redo 可用 ⟺ 上一步是 undo（无分支选择）
* 开分支判断 = 有无子节点（entries.some）；日志永不删除；redoStack 不持久化（跨会话失效，MVP 接受）
* 视图一致性：undo 后 graphView 被注销 → 上溯父图/根图 + graphPath 重算

## 3. 测试与验证 ⏳

### 目标

前端回溯能力通过 Runtime 集成测试验证（不重复引擎测试——引擎已有单测，前端只测 store → 日志 → undo/redo 链路）。

### 3.1. 测试套件

**子目标**：

* 双存接线：一次 commitBatchToGraphs → entry.operation/reversalOperations 按图分组双存正确；graphSignals 提取正确（add_graph → added、delete_graph → deleted）；recordLog:false 不追加。
* undo 链：add → update(+summary) → delete 后逐级 undo，节点/边/属性精确恢复；undo 后执行新操作 → 开分支 + 清 redoStack。
* redo 链：undo 后 redo 重走原路径；redoStack 空 → return false；新操作后 redo 失效。
* 图级：含 add_graph 的批（deconstruct）undo → 子图注销（持久化保留）；redo → 重新注册。视图一致性：查看子图时 undo → 跳转父图。
* 边界：空栈 undo / 末尾 redo → false 不写状态。
* 回归：fold/expand + undo 套件更新（快照式 → 日志式）。

* 不确定度：中
* 算法复杂度：低
* 工作量：中

### 决策项

**已确定决策**：

* 前端只测 Runtime 集成链路，不重复引擎单测（沿用 phase2b 核心原则）
* undo 空栈 / redo 末尾保持 return false（08 已定边界，UI 禁用属交互层/04 范畴）

### 3.2. 临时快捷键接线（手动冒烟验证，非契约）

**子目标**：

* 010 主体完成后，加极简 keydown 监听（约 10 行，挂 Graph.vue 或 App.vue）：Ctrl+Z → `store.undo()`、Ctrl+Shift+Z / Ctrl+Y → `store.redo()`；`preventDefault` 拦截浏览器原生回退。
* 目的：手动冒烟验证双存链路——图内（add → update → delete → 逐级 undo/redo）、图级（deconstruct 子图 / 删图 → undo 注销/恢复 → 视图回跳父图）、分支（undo 后执行新操作 → 清 redoStack）。
* **非 010 契约内容**：纯试玩接线，无 UI 设计（无按钮 / 灰显 / 分支导航，属 04）；04 落地正式 UI 时替换或移除。
* 试玩预期：010 为内存版，**刷新页面 undo 历史即丢**（日志未持久化 + redoStack 不持久化，011 IndexedDB 补齐跨会话）。

* 不确定度：低
* 算法复杂度：低
* 工作量：极低
