# 01-派生值分离与类型框架

---

## 1. 类型框架：form / abstractionLevel 派生化 ⏳

### 目标

GE 端确立"持久化数据与派生值分离"的类型框架：从 GraphData 类型移除 `form` / `abstractionLevel` 字段，定义派生契约签名，实现派生函数。完成后，GraphData 只含事实数据（结构 + 用户数据），派生值由读取时计算的纯函数提供。

### 1.1. 类型契约（graph_data.ts）

**子目标**：
  * 移除 `NodeBase.abstractionLevel`（graph_data.ts:102）
  * 移除 `KnowledgeNodeData.form`（graph_data.ts:114）
  * 定义派生契约签名类型：`DeriveNodeForm` / `DeriveAbstractionLevel`（与数据接口同文件，文件级耦合）
  * 文档化派生规则：权威源 = `childGraphId`；空子图 `abstractionLevel = 1`；`form === 'abstract' ⟺ childGraphId !== undefined`

难度：
* 不确定度：低（类型移除 + 签名定义，无行为变化）
* 算法复杂度：无
* 工作量：小

### 1.2. 派生实现（core/derive.ts 新增）

**子目标**：
  * `deriveNodeForm(node)`：`childGraphId` 存在性判断，O(1)
  * `deriveAbstractionLevel(lookupGraph, node)`：沿 `childGraphId` 链递归推导，O(链深度)；空子图 = 1；环防御
  * 单元测试：原子节点 / 抽象节点 / 空子图 / 深层链 / 环防御边界

难度：
* 不确定度：低（签名形态已确认，见已确定决策 Q1）
* 算法复杂度：O(子图链深度)
* 工作量：小

### 1.3. 导出（index.ts）

**子目标**：
  * 从 index.ts 导出派生函数与签名类型（公开 API）
  * 派生契约签名类型随 graph_data.ts 类型一并导出

难度：
* 不确定度：低
* 算法复杂度：无
* 工作量：极小

### 影响范围

```
packages/graph-engine/src/
├── types/graph_data.ts      — 修改（移除字段 + 定义签名契约）
├── core/derive.ts           — 新增（派生函数实现）
├── index.ts                 — 修改（导出派生函数与签名类型）
└── core/derive.test.ts      — 新增（单元测试）
```

### 决策项

**已确定决策**：
* 派生契约签名定义在 graph_data.ts（文件级耦合，满足"数据与计算放一起"诉求），实现放 core/derive.ts（types 目录不混入实现）。
* 权威源 = `childGraphId`（子图结构），派生值不持久化。
* `form` 的推导是节点局部的（O(1)）；`abstractionLevel` 的推导是跨图的（需注入 lookupGraph）。
* **Q1 已确认**：`deriveAbstractionLevel` 签名采用 `(lookupGraph: (id: GraphId) => GraphData | undefined, node: NodeBase) => number` 注入模式。与 `searchNodes` 一致（index.ts:262），引擎不持有状态；此模式是第二步多图迁移的探路石。
* **Q2 已确认**：派生函数与签名类型从 index.ts 导出为公开 API。前端消费方（class_mapper 等）需要调用。
* **degree / radius 不纳入第一步**：radius 已是"惰性计算 + 可选覆盖"的正确模式（collision.ts:82 getRadius 权威），无需改造；degree 是增量维护（execute.ts 核心路径），改动风险高（核心路径 + 渲染层 O(N×E) 性能回归），作为步骤 02 框架评估项（3.3）跟进。

## 2. 引擎消费方迁移 ⏳

### 目标

引擎内部所有 `form` / `abstractionLevel` 的读写迁移到派生函数。完成后，引擎不再写入这两个字段，读取处改接派生函数。

### 2.1. 读取迁移

**子目标**：
  * `deconstruct.ts`：form 检查（deconstruct.ts:105）改接 `deriveNodeForm`
  * `internalize.ts`：form 检查（internalize.ts:183,225,267,371）改接 `deriveNodeForm`

难度：
* 不确定度：低（机械替换，语义等价）
* 算法复杂度：无
* 工作量：小

### 2.2. 写入删除

**子目标**：
  * `deconstruct.ts`：删除 `form: 'abstract'`（:183）与 `abstractionLevel: 0`（:160）写入
  * `induce.ts`：删除 `form: 'abstract'`（:501）与 `abstractionLevel: 0`（:360,505）写入
  * `diverge.ts`：删除 `abstractionLevel: 0`（:277,332）写入
  * `internalize.ts`：删除 `abstractionLevel: 0`（:309）写入

难度：
* 不确定度：低（删除冗余写入，行为不变——派生函数会推导出相同值）
* 算法复杂度：无
* 工作量：小

### 影响范围

```
packages/graph-engine/src/compose/cognitive/
├── deconstruct.ts   — 修改（form 检查改派生 + 删除写入）
├── induce.ts        — 修改（删除 form/abstractionLevel 写入）
├── internalize.ts   — 修改（form 检查改派生 + 删除写入）
└── diverge.ts       — 修改（删除 abstractionLevel 写入）
```

### 决策项

**待确定决策**：

> **Q3**：删除写入后，引擎内部是否还有需要"读取派生值"的地方（除 deconstruct/internalize 的 form 检查外）？
> **建议**：按当前消费盘点，无其他读取点；若迁移中发现遗漏，报告编排者补充。
> **理由**：abstractionLevel 引擎零消费（死字段），form 仅 deconstruct/internalize 消费。

**已确定决策**：
* 删除写入是安全的：派生函数会推导出与写入相同的值（deconstruct 空子图 → 1；induce 新节点 → 1；diverge/internalize 新节点无 childGraphId → 0/atomic）。
* 引擎回归测试必须全绿（GE 纯函数，输出可复现）。
