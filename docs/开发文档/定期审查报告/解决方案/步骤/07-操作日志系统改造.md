# 07-操作日志系统改造

---

## 背景与动机（承接 06）

06 步骤完成后，`applyBatches`（多图管理层）已落地，前端 `commitBatchToGraphs` 已对接（注册表引用替换 + graphViewId）。但操作日志系统仍是旧结构：

- `graphSignals` 旁路字段（图级操作的特殊待遇）
- undo/redo 三段式手工编排（deleted 恢复 → 图内逆元 → added 注销）
- `item` / `entry` 命名（与粒度递进不一致）
- 图级逆元手写（`revertAddGraph` / `revertDeleteGraph` 兑现逻辑）

本步骤改造操作日志系统，使日志、执行、回溯三端统一到"单图 op → 单图批 → 多批次"粒度递进，彻底消灭图级操作的特殊待遇。

## 1. 操作日志统一形态（graphSignals 消失） ⏳

### 目标

图级操作回到有序操作序列，不再旁路 `graphSignals` 字段。图级逆元统一为 add ↔ delete 互逆，作为普通操作（快照式）。undo/redo 对称：执行逆元序列 / 正向序列，三段式与 direction 语义消失。

### 核心设计方向

- **graphSignals 字段消失**：`AtomicOperationLog`（原 `OperationLogEntry`）移除 graphSignals，图级操作作为有序操作进入 `batchLog`（原 `ItemOperations`）的操作序列，与图内操作同形态。
- **图级逆元快照式**：delete_graph 的逆元 = add_graph（携带完整图数据）。操作日志本就全量持久化；软删是前端运行时特例，不进入引擎契约。
- **delete_graph 的角色**：图级操作 = 图粒度（典型场景为子图）；delete_graph 主要作为 add_graph 的逆元在 undo 路径被构造（注销子图），无"用户主动删图"的调用方（故意设计）；根图生命周期走旁路（createRootGraph recordLog: false / deleteRootGraphTree 管理级删除），不进入本管道。快照式逆元（delete_graph → add_graph + 整图）服务于 add ↔ delete 互逆对称的完整性。
- **undo/redo 对称**：undo = 执行 `reversalOperations`（逆元序列，图内逆元 + 图级互逆按序排列），redo = 执行 `operation`（正向序列）。三段式顺序依赖（deleted 先恢复、added 后注销）由逆元序列自然顺序表达，无需特殊编排。
- **命名改造**：树 `operationLogTree`（原 `OperationLog`，容器保留）；条目 `AtomicOperationLog`（原 `OperationLogEntry`）；`batchLog`（原 `ItemOperations`）；放弃 `item` / `entry` 命名。

难度：
- 不确定度：中（操作日志类型变更，undo/redo 路径重构）
- 算法复杂度：无
- 工作量：中
