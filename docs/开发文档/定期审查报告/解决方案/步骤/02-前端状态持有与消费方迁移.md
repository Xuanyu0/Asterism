## 1. 前端状态持有改造（shallowRef） ⏳

### 目标

graphView / graphRegistry 改 shallowRef 持有，GraphData 永不进深代理。消除 proxy workaround（toRaw ×2、JSON 序列化克隆 ×1）。完成后，引擎可直接 structuredClone 图数据，无需解包。

### 1.1. graph_store.ts 状态持有改造

**子目标**：
  * `graphView`：`ref<GraphData | null>` → `shallowRef<GraphData | null>`（引用替换触发更新，与引擎返回新对象模型同构）
  * `graphRegistry`：`ref<GraphRegistry>` → 配套方案（见决策项 Q1）
  * 消除 `commitBatchToGraphs` 内的 `toRaw` 解包（graph_store.ts:319）
  * 消除 `operationLog` entry 的 `markRaw`（graph_store.ts:447）——若 operationLog 配套改造（见决策项 Q2）

难度：
* 不确定度：中（registry 的原地修改模式与 shallowRef 的引用替换语义冲突，需配套方案）
* 算法复杂度：无
* 工作量：中

### 1.2. 消费方 workaround 消除

**子目标**：
  * `default_tool.ts`：消除 `toRaw` 解包（default_tool.ts:151）
  * `preview_engine.ts`：`cloneGraph` 从 `JSON.parse(JSON.stringify())` 改 `structuredClone`（preview_engine.ts:254）

难度：
* 不确定度：低（机械替换，行为等价）
* 算法复杂度：无
* 工作量：小

### 1.3. 渲染链路验证

**子目标**：
  * Graph.vue 渲染同步照常（watch 只依赖引用层面，代码不改）
  * 手动冒烟：加载图 / 添加节点 / 移动节点 / undo / redo 均正常渲染

难度：
* 不确定度：低（Graph.vue 的 watch 与 shallowRef 完全兼容，已分析确认）

* 工作量：小

### 决策项

**待确定决策**：

> **Q1**：graphRegistry 的 shallowRef 配套方案？
> **方案 A（整体替换）**：`registerGraph` 等改为纯函数（返回新 Map），`graphRegistry.value = 新 Map` 触发更新。彻底无代理，与引擎纯函数风格一致，但改动面大（graph_store 内所有 registry 操作）。
> **方案 B（边界解包）**：registry 保持 `ref<Map>`（深代理），取出/存入时在边界 `toRaw` / `deepToRaw`。改动小，但保留少量 toRaw。
> **建议**：方案 A。理由：彻底实现"GraphData 永不进深代理"，且 registry 操作纯函数化是第二步多图迁移的预演。

> **Q2**：operationLog 是否配套 shallowRef？
> **建议**：暂不配套。operationLog 是"容器 + 原地修改"模式（entries.push + cursor），改 shallowRef 需整体替换，改动面大且非本次试验核心。保留 markRaw 防御。
> **理由**：本次试验重心是图数据本体（graphView / graphRegistry），operationLog 的改造可延后评估。

**已确定决策**：
* Graph.vue 代码不改（watch 只依赖引用层面，与 shallowRef 完全兼容）。
* cy_element_mapper 的 position 拷贝保留（架构防御：渲染层只读映射，GraphData 唯一事实源；非 proxy workaround，shallowRef 下污染变静默更危险）。

## 2. 前端消费方迁移 + 抽象等级消费 ⏳

### 目标

class_mapper 改接派生函数，落地设计文档的抽象节点多边形构想（`docs/设计/01-核心定义.md:118`：正多边形，边数 = 抽象等级 + 2）。删除全部 `abstractionLevel: 0` 写入点。

### 2.1. class_mapper 迁移

**子目标**：
  * `node.form` 检查（class_mapper.ts:27）改接 `deriveNodeForm(node)`
  * 新增：`deriveAbstractionLevel` → 多边形形状 class（边数 = level + 2，如 `node-polygon-3` / `node-polygon-4`）
  * 注意：class_mapper 是纯函数（只读节点字段），派生函数调用需注入 lookupGraph（见决策项 Q3）

难度：
* 不确定度：中（class_mapper 需要 lookupGraph 注入，改变其调用签名）
* 算法复杂度：无
* 工作量：中

### 2.2. cy_style 多边形样式

**子目标**：
  * 新增抽象节点多边形样式定义（正多边形，顶点朝下——`docs/设计/01-核心定义.md:124`）
  * 不同抽象等级对应不同边数（3 边 / 4 边 / 5 边...）

难度：
* 不确定度：中（Cytoscape shape 的 polygon 支持方式需确认，见决策项 Q4）
* 算法复杂度：无
* 工作量：中

### 2.3. 删除写入点

**子目标**：
  * `add_node.ts`：删除 `abstractionLevel: 0`（:159）
  * `preview_engine.ts`：删除 `form` / `abstractionLevel` 写入（:91,94）
  * `bootstrap.ts`：删除全部 `abstractionLevel: 0`（15 处）
  * `test_case_factory.ts`：移除 form / abstractionLevel 字段（:38,57-58,72）
  * 相关测试文件同步更新（preview_engine.test.ts:357,398、useFloatingWindow.test.ts:27、useGraphOperationAdapter.test.ts:58,145）

难度：
* 不确定度：低（机械删除，派生函数自动推导等价值）

### 决策项

**待确定决策**：

> **Q3**：class_mapper 如何获得 lookupGraph？
> **建议**：class_mapper 的 `getNodeClasses` 增加可选参数 `lookupGraph`（或由调用方传入派生结果）。渲染层调用链（useRenderer → cy_element_mapper → class_mapper）需透传。
> **理由**：`deriveAbstractionLevel` 需要跨图查找；渲染层持有 registry 访问能力（或由 store 注入）。

> **Q4**：多边形样式的实现形态？
> **方案 A（class 映射）**：class_mapper 输出 `node-polygon-N` class，cy_style 为每个 class 定义 shape。
> **方案 B（shape 计算）**：mapper 直接计算边数，传给 Cytoscape 的 shape 属性。
> **建议**：方案 A。理由：与现有 class_mapper 模式一致（class 驱动样式），样式集中定义在 cy_style。

**已确定决策**：
* 抽象等级消费是设计文档构想（`docs/设计/01-核心定义.md:118,124`）的落地，非新增需求。
* 渲染层继续吃 raw GraphData（不引入包装对象）。
