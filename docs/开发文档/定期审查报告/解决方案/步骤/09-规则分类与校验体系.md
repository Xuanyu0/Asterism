## 背景与动机（承接 07.4 审查 + 语义分类讨论）

### 1. skipValidate 参数的可疑性（07.4 讨论浮现）

`skipValidate` 是"重放模式"与"新操作模式"的分界开关：只跳过 Phase 1（操作前提校验），Phase 3 全局不变量始终生效。其存在根因是**批内依赖**：逆元/正向重放中 `add_edge` 依赖同批 `add_node` 重建端点，validate-all-first 基于输入图校验必然误报 `EDGE_SOURCE/TARGET_NOT_FOUND`（010.1 缺陷 #1 的机制，D-4 实测必要）。正向 compose 靠拆批规避，逆向无法拆批只能 skipValidate。

### 2. EDGE\_\*\_NOT_FOUND 的归属问题

`EDGE_SOURCE/TARGET_NOT_FOUND`（validateAddEdge / validateUpdateEdge）当前在 Phase 1（局部），但其本质是"悬空边"= **图状态不变量**，与 Phase 3 已有 `DANGLING_REFERENCE`（悬空引用）同构。

### 3. 全局规则 13 条平铺、混合不同性质

`global_rules.ts` 13 条规则全部 error 级、平铺在一个开关表（`DEFAULT_GLOBAL_RULES_TABLE`）中，未区分内部性质。观察三类混合：

- **结构类**：`SELF_LOOP_FORBIDDEN` / `DUPLICATE_EDGE_FORBIDDEN` / `DANGLING_REFERENCE` —— 违反 = 数据不一致 / 无法解释
- **语义类**：`REAL_DIRECTED_CYCLE_FORBIDDEN` / `VIRTUAL_NODE_EDGE_TYPE_INVALID` / `HEURISTIC_NODE_EDGE_TYPE_INVALID` —— 数据能表达但违反产品概念模型，且违反后引擎认知操作（折叠 / deconstruct 依赖遍历等）不可解释
- **体验类**：`NODE_LABEL_TOO_LONG` / `NODE_SUMMARY_TOO_LONG` / `EDGE_LABEL_TOO_LONG` / `NODE_COUNT_*` / `VIRTUAL_NODE_TOO_MANY_VIRTUAL_NEIGHBORS` —— 数据合法，仅体验 / 性能差异

### 4. 物理结构散落 + 死代码双轨

- 前置条件文件散在 `core/` 根（`validate_operation_in_graph.ts` / `validate_graph_operation.ts`），不变量在 `core/validators/` 子目录——同一架构两半在不同层级，新人无法靠目录定位
- `validators/rule_config.ts` 是死代码：`DEFAULT_RULES_CONFIG` 全项目无人 import，注释头文件名错误（`registry.ts`）、示例 import 名错误；活着的开关表是 `global_rules.ts` 的 `DEFAULT_GLOBAL_RULES_TABLE` —— 双轨
- `thresholds.ts` 集中存放被多规则共享的阈值；`core/layout_rules.ts` 名字撞"rules"但实为活跃的布局几何参数（placement/collision/cognitive 均引用，index.ts 公开导出），非校验系统

### 5. 语义模型讨论定稿（本步骤的"设计输入"）

经与本项目规则系统现状对照 + 外部调研（Design by Contract / LSP / ESLint / SQL 完整性 / SHACL / SBVR），定稿分类模型：

```
规则 = 类型轴 × 级别轴（两轴正交）

类型轴（契约语义，DbC 对齐）：
├── 前置条件 precondition   —— 操作前提，Phase 1；"操作不可能"级（调用方契约）
│     语义收敛：结构有效性（引用存在、ID 不重复、位置有效、折叠条件）
│     UX 类内容（碰撞/空标签/重名）语义上不属于引擎前置 —— 由 UI 工具层引导（后续步骤 ⑤）
└── 不变量 invariant        —— 图恒真，Phase 3；按可配置性二分：
    ├── 硬性图不变量         —— 不可配置、恒跑、缺席配置面、error 级
    │     组成：结构类 + 语义类
    │     分界判据：违反后数据/引擎是否仍可被正确解释与操作
    │              不可解释/不可操作 → 硬性（cycle/边类型/悬空/自环/重边）
    └── 图不变量偏好         —— 可配置、默认全开、warning/info 级
          分界判据：违反后数据仍合法，仅体验/性能差异 → 偏好（标签长度/节点数/虚邻居数）

级别轴（severity）：error / warning / info 逐条设置，不随类别硬绑定（硬性≈error、偏好≈warning/info 是自然默认，但非推导关系）

后置条件 postcondition：本项目不用 —— 信任执行方（execute）+ 不变量兜底（Phase 3）
```

> 与 L1 `docs/设计/05-规则分类.md` 的关系：L1 由用户并行修订中（规则配置表的"一致性/级联"条目已置空暂缓）。本文档的"偏好开关表"不预设持久化与级联方向，仅落引擎侧机制（BatchOptions 传入），持久化 / UI 配置入口留待 L1 定稿后的后续步骤。

## 1. 分类归位与物理结构重组（①+③） ⏳

### 目标

引擎校验代码落地为 `core/rules/` 分层：前置条件与不变量按目录分离；不变量内部硬性/偏好按文件分离；阈值内联到对应规则文件；死代码清除。完成后的目录结构即上节"新"结构，新人凭目录/文件名即可定位"这是前置还是不变量、硬性还是偏好"。

### 子目标

**1.1 建立 rules/ 骨架并迁移前置文件**

- `validate_operation_in_graph.ts` → `rules/preconditions/in_graph.ts`；`validate_graph_operation.ts` → `rules/preconditions/graph_level.ts`（保留原逻辑，update import 路径）

**1.2 拆 global_rules.ts 为 structural.ts + preferences.ts**

- 按已定分界判据归类：结构 + 语义 → `structural.ts`（硬性）；体验 → `preferences.ts`（偏好）
- `VIRTUAL_NODE_TOO_MANY_VIRTUAL_NEIGHBORS` 按判据归偏好（违反后数据仍可解释，仅视觉歧义）—— 若执行中发现折叠等引擎操作实际依赖该约束，则升为硬性并上报

**1.3 执行入口骨架与死代码清除**

- 新增 `invariants/check_invariants.ts`：invariants 层唯一执行入口。本子步骤先按旧 `runGlobalRules` **等价逻辑搬迁**（内部遍历 structural + preferences 的规则列表，接受全量开关表查询）——行为不变、测试应全绿；"硬性恒跑 + 偏好按表"的语义收窄由**子步骤 3** 完成

- `whole_graph_validator.ts` 归位：保留"全图体检"能力（加载外部数据初始校验），复用 check_invariants 单一入口，不产生第二条校验路径

**1.4 layout_rules.ts 改名去撞名**

- `core/layout_rules.ts` → `core/layout_parameters.ts`：布局几何参数（unitDistance / collisionGap），非校验规则，与 `rules/` 语义撞名
- 标识同步：`LayoutRules` → `LayoutParameters`、`DEFAULT_LAYOUT_RULES` → `DEFAULT_LAYOUT_PARAMETERS`
- 同步范围：engine index.ts re-export + 引擎内 8 处 import（placement / collision / deconstruct / internalize / induce / tests）+ 前端 3 文件（useRenderer / visual_mapper / node_radius）+ 相关测试

## 2. EDGE\_\*\_NOT_FOUND 迁入 Phase 3（②） ⏳

### 目标

`EDGE_SOURCE_NOT_FOUND` / `EDGE_TARGET_NOT_FOUND` 从 Phase 1 局部校验迁入 Phase 3 硬性不变量（与 `DANGLING_REFERENCE` 同族——悬空边 = 图状态不变量）。预期收益：undo/redo 重放误报源消失 → 撤销 undo/redo 侧 skipValidate 传参（preview 侧保留，见 2.2）；正向 compose"节点→边拆批"约束可放松。

### 子目标

**2.1 迁移**

- 端点存在性校验自 `preconditions/in_graph.ts` 的 validateAddEdge / validateUpdateEdge 移除，作为结构类规则并入 `invariants/structural.ts`（rule code 不变：`EDGE_SOURCE_NOT_FOUND` / `EDGE_TARGET_NOT_FOUND`，前端依赖 code 的稳定标识不受影响）
- Phase 1 剩余前置确认收敛为纯结构有效性：ID 重复、节点/边存在（delete/update/move/collapse 目标）、位置有效、折叠条件

**2.2 skipValidate 去留：按消费方分流（两个消费方，理由不同）**

`skipValidate` 有两个消费方，需分别评估：

- **undo/redo 消费方**（`graph_store.ts` undo/redo 传 `skipValidate: true`）：使用理由 = "add_edge 依赖同批 add_node 重建端点，重放必然误报 EDGE 端点前提"。EDGE 迁 Phase 3 后该理由消失 → 受控实验（`skipValidate=false` 下 undo/redo 全通过）验证剩余 Phase 1 前置（ID 重复/节点存在/位置有效/折叠条件）在重放下自然通过后，**撤销 undo/redo 传参**
- **preview 消费方**（`preview_engine.ts` 占位预览传 `skipValidate: true`）：使用理由 = 占位节点空 label 会被 Phase 1 `EMPTY_LABEL` 拒绝，与 EDGE 无关。`EMPTY_LABEL` 是 UX 前置，属 ⑤（迁 UI 层）范围，本次不动 → **参数保留给 preview 专用**，待 ⑤ 迁出 EMPTY_LABEL 后整体退役

结论：本次撤销 undo/redo 侧传参；`skipValidate` 参数收窄为 preview 专用，不整体删除（删除依赖 ⑤）。

难度：

- 不确定度：高——skipValidate 去留依赖受控实验结果，无法预先断言
- 算法实现复杂度：低
- 工作量：中（含实验与回归）

`preconditions/in_graph.ts`（移除端点存在性）+ `invariants/structural.ts`（新增两条）+ undo/redo 执行路径相关测试（`undo_redo.test.ts`、reversal/replay 测试）+ skipValidate 调用方（前端 `applyEntry` reverse/forward）。

## 决策项

**已确定决策**：

- 规则分类采用"类型轴（前置条件 / 不变量）× 级别轴（severity）"正交模型；不变量按可配置性二分（硬性图不变量 / 图不变量偏好）
- 硬性 = 结构类 + 语义类；违反后数据/引擎不可正确解释或操作 → 不可配置、恒跑、缺席配置面、error
- 偏好 = 体验类；违反后数据仍合法仅体验/性能差异 → 可配置、默认全开、warning/info
- severity 逐条设置，不随类别硬绑定
- 本项目不用后置条件——信任执行方（execute）+ 不变量兜底（Phase 3）
- EDGE_SOURCE/TARGET_NOT_FOUND 迁入 Phase 3 硬性不变量（与 DANGLING_REFERENCE 同族）
- UX 类前置（碰撞/空标签/重名）语义上属 UI 工具层引导；本次引擎侧保留原样归位，迁移随 ⑤ 后续步骤
- 物理结构重组为 `core/rules/{preconditions, invariants}`；阈值内联；类别文件只声明规则不实现执行循环，执行逻辑收敛于 `invariants/check_invariants.ts` 单一入口（apply_batch 与 whole_graph_validator 共用，编排层不感知类别切分）；`index.ts` 纯 barrel 聚合
- 删除 `validators/rule_config.ts` 死代码；`core/layout_rules.ts` 改名为 `core/layout_parameters.ts`（标识 `LayoutParameters` / `DEFAULT_LAYOUT_PARAMETERS` 同步，去 `rules/` 撞名）
- skipValidate 按消费方分流：undo/redo 侧撤销传参（受控实验验证），preview 侧保留专用（依赖 ⑤ 迁出 EMPTY_LABEL 后整体退役）
- rule code（`EDGE_*_NOT_FOUND` 等）保持稳定不变——前端按 code 分流，code 是稳定机器标识
- **Q1 已定**：`ValidationIssue` 不增加运行时 `category` 字段——类别由文件结构（preconditions/ vs structural.ts vs preferences.ts）表达，避免为文档性类别引入运行时负担
- **Q2 已定**：`NODE_COUNT_HARD_LIMIT_EXCEEDED` 移除 Phase 1 预判（validateAddNode），只保留 Phase 3 不变量（dry-run 后整批丢弃语义等价），消除"同一条规则两处定义"
- **Q3 已定**：`core/layout_rules.ts` → `core/layout_parameters.ts`（文件 + 标识同步改名，见上）
