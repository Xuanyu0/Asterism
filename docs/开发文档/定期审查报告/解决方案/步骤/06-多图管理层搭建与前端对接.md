# 06-多图管理层搭建与前端对接

---

## 背景与动机（承接 02.3）

02 步骤的子步骤 3「评估图级信号兑现迁移方案」由本步骤接管，扩展为实施。本步骤聚焦**多图管理层搭建 + 前端对接**（含注册表引用替换 + graphViewId）；操作日志系统改造见 [07-操作日志系统改造](07-操作日志系统改造.md)。

**核心矛盾**：add_graph / delete_graph 被建模为原子操作，但 GE execute 对图级操作静默（`default: return graph`），兑现散落在前端 graph_store 第三阶段扫描 + undo 三段式手写逆元。根因是**单图变换执行模型 vs 多图操作语义**——execute 签名 `(graph, op) → graph` 只覆盖"对已存在的单图做变换"，而图级操作是"多图状态（注册表）"的操作，天然无法被单图变换模型表达。

**架构判断**：GE 是"状态转换函数"，前端是"状态持有者"。图级兑现本质是**多图状态转换**，收口到 GE 端多图管理层。

### 架构对比

```
当前（职责混杂）：
execute（单图单操作）→ pipeline（单图多操作）→ graph_store（多图编排 + 图级兑现 + 状态持有 + 持久化 + 日志）

目标（职责分层，core/ 内三个粒度递进）：
execute_operation（单操作）→ apply_batch（单图批）→ apply_batches（多批次 = 多图批）
                                                              │
                                                              ├─ 图内操作：逐个 item 委托 apply_batch
                                                              ├─ 图级操作：兑现（add_graph / delete_graph）
                                                              └─ 逆元构造（图级 + 图内）
                                          ↓ 返回新注册表 + 逆元信息（+ graphSignals 中间态）
                   前端 graph_store（纯状态持有：注册表引用替换 + graphViewId + 持久化 + 日志）
```

### 命名体系（06 涉及 GE 部分；日志命名见 07）

| 粒度 | 全称 | 简称 | 公开函数 | 日志 |
|---|---|---|---|---|
| 单操作 | 原子操作 | `operation` | `executeOperation`（switch-case 路由）| `operationLog` |
| 单图批 | `operationBatch` | `batch` | `applyBatch` | `BatchLog` |
| 多批次 | `operationBatches` | `batches` | `applyBatches`（多图管理层）| `batchesLog` |

- 图内原子操作 `AtomicOperationInGraph`（`executeOperation` 路由）；图级原子操作 `AtomicGraphOperation`（`applyBatches` 兑现）
- 文件递进：`core/execute_operation.ts` → `core/apply_batch.ts`（迁入 core/）→ `core/apply_batches.ts`（新增）

### 图级操作的语义边界

- **图级 = 图粒度（以整个图为操作对象），典型场景为子图**：add_graph / delete_graph 主要由认知操作（deconstruct / induce 创建子图）进入操作管道，可撤销。
- **delete_graph 的角色 = add_graph 的互逆**：主要作为 add_graph 的逆元在 undo 路径被构造（注销子图），无"用户主动删图"的调用方（故意设计）。
- **根图生命周期走旁路，不在本步骤迁移范围**：createRootGraph（add_graph，recordLog: false）与 deleteRootGraphTree（硬删 + 注销，管理级、不可撤销）不进图编辑管道。

## 2. GE 端 applyBatches 与原子操作分层 ✅

### 目标

原子操作类型显式分层（图内 / 图级），新增 `applyBatches` 纯函数（统一批处理循环），`executeOperation` 路由瘦身。

### 2.1. 原子操作类型分层

**子目标**：
  * `AtomicOperation` 联合拆分为 `AtomicOperationInGraph` / `AtomicGraphOperation`
  * 类型层面显式区分图内 / 图级，为路由瘦身提供类型依据

### 2.2. applyBatches 纯函数（融合批处理循环）

**子目标**：
  * 输入：注册表 + `OperationBatch[]`（判别联合）；输出：新注册表 + 校验 + 逆元 + `graphSignals`（中间态，07 移除）
  * **批次判别联合**：`OperationBatch = { kind: 'inGraph', graph, operations: AtomicOperationInGraph[] } | { kind: 'graphLevel', operations: AtomicGraphOperation[] }`——图内批 / 图级批由类型判别，循环 `if-else` 按 `kind` 直接分派，**分类预处理消失**（图内/图级平级由类型系统强制）
  * **路由函数（类 `executeOperation` 的 switch 分派）**：正操作按类型分派——`add_graph` 兑现注册、`delete_graph` 兑现注销、图内操作委托 `applyBatch`（单图批事务）
  * **路由逆元构造函数（类 `createReversal` 的 switch 分派）**：逆元按类型构造——`add_graph` → `delete_graph`、`delete_graph` → `add_graph` + 操作前整图快照、图内 → `createReversal`
  * **图级操作空图对称约定（add ↔ delete 互逆，函数逻辑确保）**：
    - `add_graph`：`graph` 仅含元数据字段（id / kind / parentGraphId / ownerNodeId / 时间戳），nodes / edges 必须为空；图内容统一走后续图内操作构建
    - `delete_graph`：**携带图数据**（签名与 add_graph 统一为 `{ type, graph }`，graph 为被删空图骨架），**只能删除空图**——注册表中目标图 nodes / edges 必须为空才能删除（与 add_graph 只建空图对称，真正互逆）；undo 路径天然满足（图内逆元先清空图）
    - 两者均非口头约定：图级局部规则校验收口 `validate_graph_operation.ts`（与 `validate_operation_in_graph.ts` 对称）——`add_graph` 校验 op.graph 空图；`delete_graph` 校验注册表目标图空图；applyBatches 图级批 **for 循环内边校验边执行**（逐 op：validateGraphOperation → executeGraphOperation，任一失败整批丢弃）。图级操作不进单图 validate（validateOperation 单图上下文无注册表）
  * **compose 返回改造（批次语义统一）**：deconstruct / induce 返回 `{ batches: OperationBatch[]（判别联合）, issues }`——图级操作独立成 `graphLevel` 批，图内操作按图分组为 `inGraph` 批；compose 保证顺序（add_graph 批在对应图内填充批之前）；internalize / diverge 形态统一（`graphOps` 为空）
  * **批次操作对象存在性校验（保险）**：图内批的 `batch.graph.id` 必须存在（注册表或本批 add_graph 已注册）——applyBatches 图内批执行前检查 `newRegistry.has(batch.graph.id)`，不存在返回显式 error issue（`BATCH_GRAPH_NOT_FOUND`）整批丢弃，防止操作构造方对不存在的图操作被隐式创建
  * **融合而非拼接（验收标准）**：禁止保留 graph_store 现有的"第一阶段 + 第三阶段"两个独立循环拼凑；若无法融合（如事务性迫使两阶段）回到规划

### 2.3. executeOperation 路由瘦身

**子目标**：
  * 只处理图内操作（`AtomicOperationInGraph`），default 分支消除
  * 图级操作由 `applyBatches` 兑现

难度：
* 不确定度：高（GE 契约变更，影响面大）
* 算法复杂度：无
* 工作量：大

### 影响范围

```
packages/graph-engine/src/types/atomic_operations.ts — AtomicOperationInGraph / AtomicGraphOperation 拆分；DeleteGraphOperation 改携带 graph（签名统一）
packages/graph-engine/src/types/（compose 类型）— OperationBatch 判别联合（inGraph / graphLevel）
packages/graph-engine/src/core/apply_batches.ts      — 新增（多图管理层：路由函数 + 路由逆元构造函数）
packages/graph-engine/src/core/validate.ts → validate_operation_in_graph.ts — 改名（单图批校验，与 apply_batch.ts 对称）
packages/graph-engine/src/core/validate_graph_operation.ts  — 新增（多图批校验：图级操作局部规则，只有空图校验——add_graph op.graph 空 / delete_graph 注册表目标图空；导出单操作校验函数 validateGraphOperation，applyBatches 图级批 for 内逐 op 调用）
packages/graph-engine/src/core/execute_operation.ts  — 路由瘦身
packages/graph-engine/src/core/reversal.ts           — 图级逆元（add ↔ delete 互逆）支持
packages/graph-engine/src/core/apply_batch.ts        — ops 参数收窄为 AtomicOperationInGraph[]，删除图级跳过逻辑（死代码）
packages/graph-engine/src/compose/cognitive/deconstruct.ts — 返回形态改造（batches 判别联合 + add_graph 空图 + add_node 填充）
packages/graph-engine/src/compose/cognitive/induce.ts       — 返回形态改造（batches 判别联合，add_graph 独立成 graphLevel 批）
packages/graph-engine/src/compose/cognitive/internalize.ts / diverge.ts — 返回形态统一（batches 判别联合，graphOps 为空）
GE 测试 — applyBatches 单测（路由函数/路由逆元构造函数/图级校验边界：add_graph 空图 + 批内构造、delete_graph 注销 + 非空拒绝、逆元互逆）+ compose 返回改造适配
```

### 决策项

**已确定决策**：
* 多图管理层放 GE 端（引擎纯函数，接收注册表作参数）——图级兑现从 graph_store 彻底分离。
* 原子操作分两层（`AtomicOperationInGraph` / `AtomicGraphOperation`），消除 execute default 分支与散落特判。
* 融合而非拼接：统一批处理循环。
* `applyBatches` 返回值携带 `graphSignals`（中间态，07 移除）。
* **图级操作空图对称约定（add ↔ delete 互逆）**：`add_graph` 只建空图（graph 仅元数据字段）；`delete_graph` 携带图数据（签名统一 `{ type, graph }`）且只能删除空图（注册表目标图空图）；图级校验在 applyBatches 图级批执行（validateOperation 单图上下文无注册表）。
* **applyBatch ops 参数收窄**：单图批只收图内操作（`AtomicOperationInGraph[]`），删除图级跳过死代码——图内/图级在类型层分离。

## 4. graphViewId 化 ✅

### 目标

`graphView` → `graphViewId`（ID 存储），渲染层用 computed 派生"当前显示的图"，统一"图操作"与"切换图"两个触发源。

### 4.1. graphView → graphViewId

**子目标**：
  * 响应式状态改为 ID（当前显示的图 ID）
  * 消费方迁移（导航、breadcrumb、视图一致性等读取 graphView 处）

### 4.2. 渲染层 computed 派生

**子目标**：
  * `computed(() => registry.get(graphViewId))` 派生当前显示的图——registry 引用替换（图操作）或 graphViewId 变化（切换图）任一触发重新求值，统一两个触发源
  * `Graph.vue`：`syncFromGraphData` 源改为 computed 派生值（原 175-176、191 行）

难度：
* 不确定度：中（渲染层 + 消费方改造）
* 算法复杂度：无
* 工作量：中

### 影响范围

```
frontend/src/graph/graph_store.ts     — graphView → graphViewId
frontend/src/views/Graph.vue          — 渲染源改为 computed 派生
消费方（导航卡片、breadcrumb、ensureViewConsistency）— 适配 graphViewId
前端测试 — 全量测试绿
```

### 决策项

**已确定决策**：
* graphViewId + computed 派生：注册表是唯一事实源，当前显示的图以 ID 标记；computed 统一两个触发源，渲染层只认"当前显示的图"。
