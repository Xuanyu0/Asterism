## 发现者:@orchestrator（与用户的设计讨论，07.1 收尾）

### 需要用户确定项

#### U-3：redo 时间戳恢复机制（用户已裁决）

* 状态：✅ 已确认
* 问题：早期方案设"redo 时间戳 = 重做时刻"（步骤文档原案的语义边界）。用户指出 redo 也应恢复历史状态。
* 讨论结论：
  1. "redo 传 `preserveTimestamps: true`"不是正确机制——redo 执行正向 operation，而正向操作**不携带原始时间戳**（07.1 已删死代码），preserve 尊重不到；若 operation 意外携带旧值（如 update_node 从视图取旧节点）反而会尊重错误值。
  2. 正确机制：**时间参数 `executedAt` 语义 = 本批次执行的时刻**，redo 组装批次时 `executedAt` = 日志条目 `entry.timestamp`（原执行时刻），execute 用它覆盖 → 对象级与图级时间戳完整恢复该操作被执行后的状态。
* 最终语义：
  * 正向：`executedAt` = 真实当前时刻
  * undo：`executedAt` = 撤销时刻（图级如实记录"变更发生在何时"）+ `preserveTimestamps: true`（对象级尊重逆元快照恢复 T0）
  * redo：`executedAt` = 日志 `entry.timestamp`（原执行时刻 T1）→ 完整恢复
* 命名：时间参数从 `now` 改为 **`executedAt`**（用户裁决，避免"当前时刻"对 redo 历史时刻的误导）。
* 影响：步骤文档 1.1 / 1.2 / 4.4 语义边界已同步更新；07.1 代码已随 fixer 改名（`now` → `executedAt`，测试全绿）。redo 的 `entry.timestamp` 回读落在子步骤 4 实现。

## 发现者:@orchestrator（与用户的设计讨论终局——方案 B 最终裁决）

### 需要用户确定项

#### U-4：时间戳机制终局（用户已裁决：方案 B）

* 状态：✅ 已确认
* 演进链：
  1. 早期方案 A：`executedAt` + `preserveTimestamps` 执行模式标记（undo 时尊重逆元快照时间戳）
  2. 用户质疑 preserveTimestamps 必要性 → 讨论"操作自带时间戳 vs 执行上下文时间"归属
  3. 用户确认理论：**compose 不管理时间、applyBatches 统一管理**（一次调用 = 一个时刻 = 批内同一时间）
  4. 用户确认时间戳来源：**正逆三路径共用 `entry.timestamp`**（批级唯一时间），executedAt 永不 undefined，无"撤销时刻"
* 最终模型（方案 B）：
  * execute 对象级规则 = `操作携带值 ?? executedAt`（无模式分支）
  * 正向：构造不携带时间戳（compose 死代码已删 + **default_tool 构造 update 时清除 updatedAt** 为构造约定）→ executedAt
  * undo：逆元快照携带 T0 → execute 天然尊重 → 恢复历史对象级时刻；executedAt = entry.timestamp（图级 = 批级时间）
  * redo：executedAt = entry.timestamp = T1
  * **preserveTimestamps 全链删除**（ExecuteContext / BatchOptions / ApplyBatchesOptions / commitBatchToGraphs options）
* 图级 updatedAt 语义 = 该图最近参与的批操作时间（批级时间戳）；undo 是该批的一部分，图级保持该批时间
* 关键实证（为什么 preserveTimestamps 曾存在）：`default_tool.ts:164` 正向 update_node 构造 `{ ...data, label }` 携带视图旧 updatedAt，正逆同类型同字段语义相反——方案 B 用"构造清除"解决，替代模式开关
* 落地：07.1 契约重写为方案 B（fixer 收敛执行）；redo/undo 读 entry.timestamp 在 07.4 接线
