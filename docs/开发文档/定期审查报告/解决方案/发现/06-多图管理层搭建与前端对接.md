## 发现者:@orchestrator（06.2 多轮修正总结）

### 设计决策记录（供 oracle 评价参考）

本次 06.2 经历了多轮基于代码审视的设计深化，核心决策：

- **批次判别联合**：`OperationBatch = inGraph | graphLevel`——图级操作独立成批，applyBatches 按 kind if-else 分派，分类预处理消失
- **路由函数 / 路由逆元构造函数**：`executeGraphOperation`（纯函数 `(registry, op) → registry`）/ `createGraphReversal`（add ↔ delete 互逆，签名统一 `{ type, graph }`）
- **图级操作空图对称约定**：add_graph 只建空图、delete_graph 只能删空图（validateGraphOperation 强制）；DeleteGraphOperation 携带图数据（签名统一）
- **顺序正确性上移**：executeGraphOperation 不再查 latestGraphs（批内结果图），add_graph 批在填充批之前的顺序由 compose 保证
- **批次操作对象存在性校验**：inGraph 批的图必须存在（BATCH_GRAPH_NOT_FOUND），防止隐式创建幽灵图
- **validate 对称**：`validate_operation_in_graph.ts`（图内操作校验）/ `validate_graph_operation.ts`（图级操作校验）
- **两个 apply 顶层函数定义**：`apply_batch`（单图批 = 校验 + 分派 executeOperation）/ `apply_batches`（多批次 = 遍历批 + 校验 + 分派）

### 遗留待决

- **globalRules 命名**：`global_rules.ts` 是否改名（batchRule / graphRule / 保留 globalRule）待用户决定

### 设计决策（派生化的必要配套调整，oracle 已裁决在边界内）

#### D-1：loadGraphToView 注册归一化图

* 状态：✅ 已裁决（oracle：边界内、必要正确）
* 位置：`frontend/src/graph/graph_store.ts`（loadGraphToView）
* 问题：契约字面写法是 `store.graphViewId = graph.id`（丢弃 `ensureDefaultCognitiveState`）。但旧代码 graphView 持有归一化副本（含 cognitiveState），registry 持有原始图。若按字面实现，派生 graphView 对旧 localStorage 数据（缺 cognitiveState）会返回未归一化图，与旧语义不一致。
* 处理：`const graph = ensureDefaultCognitiveState(result.graph)` 后 `registerGraph(registry, graph)`（注册表存归一化图）+ `store.graphViewId = graph.id`。附带收益：旧实现 commitBatchToGraphs 手动同步时赋的是 registry 原始图，首次提交后 graphView 即丢失归一化；新实现视图恒为归一化图，一致性更强。
* 副作用（可接受）：持久化形态漂移（提交后 cognitiveState 默认值入库，幂等无害）；注册表混合归一化/原始图并存（惰性加载路径不归一化，无功能影响）。

#### D-2：ensureViewConsistency 从持久化取图数据

* 状态：✅ 已裁决（oracle：边界内、必要正确）
* 位置：`frontend/src/graph/graph_store.ts`（ensureViewConsistency）
* 问题：派生 graphView 使视图图被注销（undo 撤销含 add_graph 的批）时立即为 null，旧守卫 `if (!currentView) return` 会把"视图被注销"误判为"无视图"（测试当场暴露）。
* 处理：早退判断改用 `graphViewId` 为空；图被注销时 `loadGraph(currentViewId)` 从持久化取图回溯父链（软删保留数据，正常流程可达）。未改动断言的 undo_redo.test.ts:816 用例（视图指向子图时 undo → 上溯父图 + path 重算）通过，直接验证该路径。
