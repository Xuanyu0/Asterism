# 07.3 delete_abstract_node（递归删除抽象节点子树）— 提示词

## 当前状态

删除抽象节点（前端 delete 工具）当前只删除节点本身，`childGraphId` 指向的子图成为**孤儿死图**——残留注册表与 localStorage，没有任何入口可达。

GE compose 层已有 `deconstruct` / `induce` / `diverge` / `internalize`，均输出 `{ batches, issues }`，`applyBatches` 直接消费。图级操作 `delete_graph` **只能删除空图**（`validateGraphOperation` 强制校验注册表目标图为空图），因此必须"先清空图内容、再注销图"。`delete_graph` 操作形态为 `{ type: 'delete_graph', graph: 空图骨架 }`，逆元 = 空图 `add_graph`（`createGraphReversal` 已有）。

## 目标

抽象节点删除 = **完全递归删除整棵子图树**（嵌套抽象节点不留死图）；前端 delete 工具对抽象节点改走本 compose（衔接子步骤 5，本子步骤不做前端改动）。

删除语义（用户已裁决）：

- 抽象节点（`deriveNodeForm === 'abstract'`）→ 删整棵子树（完全递归）
- 非抽象节点（含引用节点）→ 保持普通 `delete_node` 单图内语义，**不进入本 compose**（前端分发，07.5 范围）

## 架构变更

```
旧：删除抽象节点 A → 只 delete_node A → 子图 G1 变死图残留

新：deleteAbstractNode({ nodeId, registry }) → 批次序列（图树 DFS 后序）

    A (abstract, childGraphId=G1)
    └── G1: [B (abstract, childGraphId=G2), D (atomic), E (atomic)]
        └── G2: [C (atomic)]

    inGraph G2:  [delete_node C]                    ← ① 递归退出后清空最深层子图
    graphLevel:  [delete_graph G2]                  ← ② 注销最深层子图
    inGraph G1:  [delete_node B, D, E]              ← ③ 同层抽象+原子同批清空
    graphLevel:  [delete_graph G1]                  ← ④ 注销中间层子图
    inGraph G0:  [delete_node A]                    ← ⑤ 顶层最后删除最外层抽象节点
```

## 具体子任务

### 3.1 compose 函数 delete_abstract_node

- 新增 `packages/graph-engine/src/compose/cognitive/delete_abstract_node.ts`，与其他 compose 同构（纯函数、不持有状态、只产批次不执行）。

**签名**：

```ts
export interface DeleteAbstractNodeParams {
    nodeId: NodeId
    registry: GraphRegistry        // 直接用注册表（新接口）；现有 50 处 GraphLookup 不动
}

export function deleteAbstractNode(params: DeleteAbstractNodeParams): {
    batches: OperationBatch[]
    issues: ComposeIssue[]
}
```

**预检（任一失败 → 返回空 batches + error issue）**：

- `nodeId` 不在注册表任何图中 → `DELETE_ABSTRACT_TARGET_NOT_FOUND`
- 目标节点非抽象（`deriveNodeForm(node) !== 'abstract'`）→ `DELETE_ABSTRACT_TARGET_NOT_ABSTRACT`
- 定位方式：遍历 `registry` 查找包含 `nodeId` 的图（数据量小，O(N) 可接受）

**递归后序形态（职责归属：节点自身归父层删除）**：

```
collect(node, registry, batches):
    ① subGraph = registry.get(node.childGraphId)
       子图不存在 → 直接返回（原子节点路径）
    ② for subNode in subGraph.nodes:
           isAbstract(subNode) → 递归 collect(subNode)
    ③ for 退出后（subGraph 全部子树已清理）：
       subGraph.nodes 非空 → 发 inGraph 清空批 [delete_node 全部节点]   ← 抽象+原子混批
    ④ 发 graphLevel 注销批 [delete_graph 空图骨架]
```

- 顶层：预检通过后调 `collect(A)`；最后发 A 所在图的 inGraph 清空批 `[delete_node A]`
- **每个节点恰好被其所在图的清空批删除一次**（不重复、不遗漏）：C 归 collect(B) 的 G2 清空批；B/D/E 归 collect(A) 的 G1 清空批；A 归顶层父图清空批。递归只处理子树，delete_node 全部收在"所在图清空批"
- 边与引用节点：由 `executeDeleteNode` 级联删除（关联边 + 指向被删节点的引用节点 + 折叠状态清理），compose 不构造 delete_edge
- `delete_graph` 骨架构造：取子图元数据字段（id / kind / parentGraphId / ownerNodeId / createdAt / updatedAt），nodes / edges 置空数组
- 批序保证：后序 DFS 天然满足"先清空后注销"（delete_graph 空图校验依赖此序）与"先子树后本图"（先删节点会切断 childGraphId 链导致子树不可达）
- **共享子图不防御**（用户已裁决：两个抽象节点指向同一子图的畸形数据不做检测，不阻塞）

### 3.3 集成测试

- 新增 `packages/graph-engine/tests/compose/cognitive/delete_abstract_node.test.ts`
- 测试模式：`deconstruct.test.ts`（compose 输出断言）+ `pipeline.test.ts`（`applyBatches` 完整执行）；用例工厂用 `tests/test_case_factory.ts` 的 `createNode` / `createEdge` / `assembleGraph`，注册表用 `new Map(...)` 构造
- 场景（至少 5 个用例）：
  1. **三层嵌套 + 沟通节点 + 原子混层**（主场景）：G0=[A(abstract→G1), F(atomic)] 含边 A-F；G1=[B(abstract→G2), D(atomic), E(atomic), 沟通节点(引用→G0)]；G2=[C(atomic)]。删除 A 后断言：
     - 批序：inGraph G2 清空 → graphLevel G2 注销 → inGraph G1 清空 → graphLevel G1 注销 → inGraph G0 清空
     - 同图同批：G1 清空批 operations 含 B、D、E、沟通节点全部
     - `applyBatches` 执行后：registry 无 G1/G2；G0 保留 F、无 A、无 A-F 边；沟通节点与关联边随级联清理；无死图残留
  2. **单层抽象**：A→G1，G1 仅原子节点 → 批：G1 清空 + G1 注销 + G0 清空
  3. **空子图**：A→G1（nodes 空）→ 批：**无 G1 清空批**，仅 G1 注销 + G0 清空（delete_graph 空图校验直接通过）
  4. **原子节点传入** → `DELETE_ABSTRACT_TARGET_NOT_ABSTRACT`，batches 为空
  5. **不存在节点** → `DELETE_ABSTRACT_TARGET_NOT_FOUND`，batches 为空
