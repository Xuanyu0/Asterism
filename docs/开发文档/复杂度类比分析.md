# 算法复杂度视角下的 planning-with-files 对比

## 变量定义

| 变量 | 含义 |
|------|------|
| `n` | 步骤数（一个阶段有多少个子步骤） |
| `t` | 当前会话中的工具调用次数（turn 数） |
| `a` | 并行智能体数量 |
| `s` | 历史会话总数（跨越多次 /clear 或重启） |

---

## 五个复杂度对比

### 1. O(log s) vs O(s) — 历史恢复

| | 主流版 | 定制版 |
|------|------|------|
| 复杂度 | O(s) 线性扫描 | O(log s) |
| 机制 | session-catchup.py 倒读 IDE 会话存储的 JSONL 文件，按时间戳顺序扫描 | git 基于 DAG（有向无环图）的哈希链，`git log -N` 取最近 N 条，内部走 commit graph 索引 |

**差异根源**：Git 为历史查询场景专门优化了数据结构（commit graph + packfile 索引），O(log s) 查询。主流版自己用扁平文件 + 顺序扫描模拟同样的功能，O(s)。

---

### 2. O(1) vs O(n) — 会话启动

| | 主流版 | 定制版 |
|------|------|------|
| 复杂度 | O(n) 随步骤数线性增长 | O(1) 常数 |
| 机制 | `task_plan.md` 一个文件包含所有 n 个步骤的 phase 清单，每次启动必须完整读取。20 个步骤 ≈ 400 行 | `dev-status.sh` 交叉验证总纲表格 + git + mtime，输出 ~30 行固定大小摘要。再读 1 个活跃步骤文档 |

**差异根源**：定制版把 O(n) 的成本从"读时"转移到了"写时"（写 n 个独立步骤文件），读时只做常数量级摘要。经典的**预付代价**策略。

---

### 3. O(t) — 每次 turn 开销（常数因子 PK）

两者的复杂度量级都是 O(t)，但常数因子差距巨大。

| | 主流版 | 定制版 |
|------|------|------|
| 每次工具调用额外词元 | ~200 tokens | 0 |
| 50 次工具调用的累计开销 | ~10,000 tokens | 30 tokens（启动时一次性） |
| 实测数据 | 19,926 tokens/task vs 11,899（+68%） | — |

**差异根源**：主流版的 PreToolUse 钩子每个 turn 重新注入 `task_plan.md` 全文到上下文——这是"注意力维持费"，目的是防止目标漂移。定制版通过人类确认门替代了自动注入，把 O(t) 的持续开销压缩到 O(1) 一次性开销。

---

### 4. O(a²) vs O(a) — 多智能体协调

| | 主流版 | 定制版 |
|------|------|------|
| 复杂度 | O(a²) 全连通 | O(a) 星形拓扑 |
| 机制 | 无原生角色系统。多智能体通过共享文件（`.planning/slug/`）通信，每个智能体需感知其他 a-1 个智能体的状态，产生全连通协调成本 | 编排者是唯一的通信枢纽。每个智能体只和编排者通信，智能体间不直接对话。提示词.md 是共享契约——@fixer 写、@oracle 审，双方不需直接协调 |

**差异根源**：星形拓扑替代全连通拓扑。编排者承担 O(a) 的管理成本，把底层智能体的协调从 O(a²) 压到 O(a)。

---

### 5. O(2ⁿ) vs O(n) — 决策分支的可行性

| | 主流版 | 定制版 |
|------|------|------|
| 复杂度 | O(2ⁿ) 组合爆炸 | O(n) 线性 |
| 机制 | 自主模式：AI 在每个决策岔路口独立选择方向。无每步强制人类确认。一步走错，后续所有步可能基于错误前提 | 每个架构决策 → 人类确认 → 继续。每步确认前不走岔路。n 个决策 = n 次确认 = 单一线性路径 |

**差异根源**：人类在此系统中的角色不是"写代码"——而是 **O(2ⁿ) → O(n) 的线性化器**。每一次确认消灭一个分叉，把指数级的可能错误路径压缩到一条正确路径。

---

## 总结

```
主流版：  O(s) + O(n) + 200·O(t) + O(a²) + O(2ⁿ)
定制版：  O(log s) + O(1) +   0·O(t) + O(a)  + O(n)
```

| 维度 | 降低手段 | 代价 |
|------|---------|------|
| 历史恢复 O(s)→O(log s) | 委托给 Git 数据结构 | 需要 commit 纪律 |
| 启动开销 O(n)→O(1) | 预付代价（分散到 n 个独立文件） | 目录结构更复杂 |
| Turn 开销 200t→0 | 去掉钩子注入 | 需要人类确认门替代注意力维持 |
| 协调成本 O(a²)→O(a) | 星形拓扑（编排者枢纽） | 编排者是单点 |
| 决策风险 O(2ⁿ)→O(n) | 人类线性化器 | 人类必须保持参与 |

**核心洞察**：不是算法优化，是**架构层面的复杂度转移**——把复杂度从系统内部推到外部边界上（Git、文件系统、人类）。每一个 O(大) → O(小) 的背后都是一次"把复杂度赶到它该待的地方"。
