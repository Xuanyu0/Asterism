## 1. 统一写入口 ⏳

### 目标

让「**所有注册表变更都经 `applyBatches`**」从声明变成事实。

**为什么这是前提**：后续要采用的**乐观模型（归纳不变式）**——启动时全量校验一次（base），此后每次写入由后置不变量保持（归纳步）——成立的条件之一是**无旁路**。现在不成立。

**完成后系统的状态**：

- 删除一棵图谱树走**统一写入口**，不再直连持久化与注册表 → 删除路径也受校验、也进操作日志（可撤销）
- 懒加载注册不再是绕过校验的注册表写入口
- 「旁路清单」为空，或每条旁路都有**明确记录**的豁免理由

### 1.1. `deleteGraphTree` 改走统一写入口

**子目标**：

- `useNavigation.deleteGraphTree`（现为 `commitGraphs(...)` + `unregisterGraph(...)` 直连）改为经 `commitBatchToGraphs` 提交。
- **牵出引擎删除契约**：`delete_graph` 现在**只允许删空图**（与 `add_graph` 只建空图对称）→ **非空树删除没有统一入口**，这正是该旁路存在的原因。契约怎么改见 Q1。
- 顺带解决 02 `U-3` / 03 `I-14`（单条失败不中止 → **半删且无信号**）：统一入口天然是整批事务。

难度：

* 不确定度：**高**（引擎删除契约的形状未定）
* 算法实现复杂度：中
* 工作量：中

### 1.2. `findParentGraph` 懒注册收敛

**子目标**：

- `graph_store.ts` 的 `findParentGraph` 在 registry 未命中时会**懒加载 + `registerGraph` 直接写注册表**，绕过 `applyBatches`。需决定收敛方式（见 Q2）。

难度：

* 不确定度：中
* 算法实现复杂度：低
* 工作量：低

### 影响范围

```text
frontend/src/graph/use-case/
    └── useNavigation.ts        ← deleteGraphTree 改走 commitBatchToGraphs
frontend/src/graph/
    └── graph_store.ts          ← findParentGraph 懒注册收敛
packages/graph-engine/src/core/rules/preconditions/
    └── graph_level.ts          ← 删除契约（形状随 Q1）
```

### 决策项

**待确定决策**：

> **Q1**：引擎的删除契约怎么改？（非空图/非空树的删除没有统一入口）
>
> **建议**：**新增「级联删除」图级操作**（如 `delete_graph_tree`，语义 = 删整棵树的成员），而不是放宽 `DELETE_GRAPH_NOT_EMPTY`。
>
> **理由**：放宽 `DELETE_GRAPH_NOT_EMPTY` 会让「删一个仍有内容的图」变成合法且静默丢内容；而级联删除把「删树」这个**真实语义**显式化，也让操作日志/逆元能正确表达一次删树。

> **Q2**：`findParentGraph` 的懒注册怎么收敛？
>
> **建议**：**懒注册保留，但补校验**（加载后先过注册表级不变量再入表），或改为**只读不改注册表**（返回值不经 registry 缓存）。
>
> **理由**：它加载的是持久化中**已存在**的图，本身不是坏数据来源；但它绕过校验进入注册表，会破坏「乐观模型」的归纳步。二选一取决于后续对 registry 完整性的要求。

## 2. 树级校验 + 启动全量校验

### 目标

把散落在前端的**结构防御代码**下沉到引擎，并让「乐观模型」成立：

> 启动时对**全注册表**跑一次全量校验（base case）→ 此后每次写入由**后置不变量**保持（归纳步）→ 运行时无需前置校验。

**完成后系统的状态**：

- 引擎有**树级不变量**：结构完整性 + 树内引用不悬空
- 启动时跑一次**全量校验**，坏数据**响亮**暴露（不静默）
- 前端的结构防御分支（`buildGraphPath` 的环检测/断链 warn、`graph_tree` 的 visited 集合）被删除 —— 它们保护的场景已由引擎保证

### 2.1. 树级不变量

**子目标**：

- **结构完整性**（无环 / 无孤儿 / 根唯一）：注意这是**全树性质**，无法用「本批涉及图」的口径测出（例：`delete_graph` 删父图 → 孤儿是其**子图**，不在批内）→ 作用域见 Q4。
- **树内引用不悬空**：跨子图的 `sourceGraphId`/`sourceNodeId` 必须解析到树内存在的节点。现在 `validateReferenceNodeConsistency` 只查**同图**（`sourceGraphId === graph.id`），跨子图悬空**完全不校验**。
- 已核实的三处缺口（现均无校验）：`add_graph` 不查 `parentGraphId` 是否存在 → 孤儿；`update_graph` 不查成环 → 环；`delete_graph` 不查有无子图 → 孤儿。

难度：

* 不确定度：中
* 算法实现复杂度：中（结构不变量需按变更类型算闭包或全量扫描）
* 工作量：中

### 2.2. 启动全量校验

**子目标**：

- 在启动装配（`useLifecycle.registerAllGraphs` 之后）跑一次**全注册表**校验。
- **必须区分「读取失败」与「结构违规」**：corrupted / missing 的图会伪装成孤儿；前者走存储错误通道，后者走校验通道。
- 失败时的行为见 Q3。

难度：

* 不确定度：中
* 算法实现复杂度：低（一次性）
* 工作量：中

### 2.3. 删除前端结构防御分支

**子目标**：

- 删除 `buildGraphPath`（`graph_store.ts`）的环检测与断链 warn、`graph_tree.ts` 的 visited 环防御。
- ⚠️ **删之前必须先有 2.2**：这些分支保护的正是**既有持久化数据**；直接删会让坏数据从「静默 warn」变成「**静默死循环**」（`buildGraphPath` 的 `while` 遇环会挂死），与「不准任何形式的静默退出」背道而驰。
- 注意区分：`isInGraphTree` 的「`loadGraph` 失败返回 false」是**持久化读取失败**处理，**不是**结构防御，不随本步删除。

难度：

* 不确定度：中
* 算法实现复杂度：低
* 工作量：低

### 影响范围

```text
packages/graph-engine/src/core/rules/
    └── 树级不变量（新增；结构完整性 + 树内引用不悬空）
packages/graph-engine/src/core/
    └── apply_batches.ts            ← 后置不变量接入树级规则
packages/graph-engine/src/index.ts  ← 全注册表校验的公开入口

frontend/src/graph/
    ├── graph_store.ts              ← 删 buildGraphPath 防御分支
    └── utils/graph_tree.ts         ← 删 visited 环防御
frontend/src/graph/use-case/
    └── useLifecycle.ts             ← 启动全量校验接入
```

### 决策项

**已确定决策**：

- 采用**乐观模型（归纳不变式）**：启动全量校验 + 每次写入后置校验，运行时不做结构前置校验。
- 结构完整性归**树级**；跨树引用归**森林级**。
- 启动校验必须区分读取失败与结构违规。

**待确定决策**：

> **Q3**：启动全量校验失败时怎么办？
>
> **建议**：**响亮报告 + 阻断写入**（乐观模型的 base case 不成立时不能继续假装成立）。
>
> **理由**：项目唯一用户是开发者本人，且规则明确不写数据迁移代码 —— 坏数据应被看见并由用户自行重置 localStorage，而不是降级运行后在后续写入时产出「莫名其妙」的校验失败。

> **Q4**：结构后置不变量的作用域？
>
> **建议**：**O(N) 全量扫描**（本项目几十~几百图，完全可接受），不做「本批闭包」的优化。
>
> **理由**：「本批作用域」是**引用不变量**的性能优化；结构不变量的闭包依赖变更类型（删图 → 其子图），按类型算闭包会引入与操作类型的耦合，得不偿失。
