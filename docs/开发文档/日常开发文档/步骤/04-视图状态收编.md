# 04-视图状态收编

---

## 1. 视图状态收进 `persistence/` ⏳

### 目标

让「持久化唯一入口」从**声明**变成**可验证的事实**：仓库里 `localStorage` 的直写点只剩 `persistence/medium/` 一处。

**完成后系统的状态**：

- `frontend/src/composables/useDragPosition.ts` **不再直写 `localStorage`** —— 导航卡片位置经 `persistence/` 落盘
- 「上次打开的根图」与「导航卡片位置」按 Q1 的结论归置（见决策项）
- `grep -rn "localStorage" frontend/src` 的结果**只剩 `persistence/medium/local_storage.ts`**
- 步骤 02 里那条 `s.t. \`localStorage\` 直接读写 ⇒ 仅本层` **第一次真正成立**

**为什么单独一步**：步骤 02 只做了「原样搬入」，键方案与 API 形状都未动；本步骤才做**真正的收编**（改键、改写入点、改调用方）。

### 1.1. 视图状态的键与形状

**子目标**：

- `categories/view_state.ts` 的键与序列化按 Q1 的结论定稿。
- 三个既有公开函数（`saveLastActiveRootId` / `loadLastActiveRootId` / `clearLastActiveRootId`）**按新的键与形状改造** —— 若 Q1 采纳「合并为一个键」，则它们读写的是**同一条记录里的字段**。
- 公开面形状由 Q2 决定（是保留三个具名函数，还是收敛为读写整条视图状态）。

- 不确定度：中（键与 API 形状都会变）
- 算法复杂度：低
- 工作量：低

### 1.2. 收编导航卡片位置

**子目标**：

- `useDragPosition.ts` 改为经 `persistence/` 读写导航卡片位置，**不再直接调 `localStorage`**。
- 该文件是一个**通用**拖拽工厂（可能被设计为跨模块复用）—— 见 Q3，需决定收编后它是否变成项目专用。
- 保持它现有的失败容错语义（导航卡片位置损坏时静默回退默认位置，是**可接受的**：它属于「丢掉只是不方便」的视图状态）。

- 不确定度：中（要判断该 composable 的泛用性与收编方式的张力）
- 算法复杂度：低
- 工作量：低

### 1.3. 让边界可验证

**子目标**：

- 补一条**自动化断言**：`grep` 级的事实要有测试兜底，否则它会随时间腐化。可用一条测试读源码断言 `localStorage` 只出现在 `medium/`（或等价手段）。
- （若 Q4 采纳）加一条 lint / dependency-cruiser 规则：**调用方不得绕过 `persistence/index.ts`** —— 这条约束架构图表达不出来（步骤 02 已记录），只能靠工具。

- 不确定度：中（测试读源码的写法在本项目无先例）
- 算法复杂度：低
- 工作量：低

### 影响范围

```text
frontend/src/persistence/
  └── categories/view_state.ts     ← 键与形状改造（改动，非新增）

frontend/src/composables/
  └── useDragPosition.ts           ← 改为经 persistence 读写，去掉直连 localStorage

frontend/src/graph/
  └── use-case/*（消费视图状态的调用点） ← import 与调用形状随公开面调整
```

### 决策项

**已确定决策**：

- 视图状态**继续落 localStorage**（不随图数据迁移到 IndexedDB）—— 它小、无容量问题、不需要事务。
- 导航卡片位置**损坏时静默回退默认位置**是可接受的（与图数据的「失败必须可见」不同级）。

**待确定决策**：

> **Q1**：两个字段（`lastActiveRootId` 与 `navCardPosition`）合并为**一个键**，还是保持两个键？
>
> **建议**：**合并为一个键**，存 `{ lastActiveRootId, navCardPosition }`。
>
> **理由**：两者都是「这台设备上次把界面摆成什么样」，合并后才是真正的**单例记录**，与「每类数据一个键方案」的模型一致；也省掉「半个类别」的别扭。

> **Q2**：公开面形状 —— 保留三个具名函数，还是收敛为「读写整条视图状态」？
>
> **建议**：**收敛**为读 / 写整条视图状态（两个函数）。
>
> **理由**：合并键之后，三个「读写单个字段」的函数就是在同一条记录上做局部更新 —— 既让调用方知道记录里有哪些字段（泄漏形状），又逼实现做读-改-写。整条读写更简单。**代价**：调用点要改成"读出整条 → 改一个字段 → 写回"。
>
> ⚠️ 此项与 Q1 联动：若 Q1 选「保持两个键」，则 Q2 无意义。

> **Q3**：`useDragPosition.ts` 是通用 composable，收编后它会不会变成项目专用？
>
> **建议**：**先看代码再定**（执行者读完后报告）。若它本就只为导航卡片服务，直接收编；若确为跨模块复用的通用工厂，则**在调用侧**包一层项目专用的存储调用，**不把 persistence 依赖注入通用工厂**。
>
> **理由**：通用工具依赖项目存储层，会让「通用」名不副实；但若它事实上只有一个消费者，则过度设计。

> **Q4**：本步骤是否加 lint / dependency-cruiser 规则强制「调用方不得绕过 `persistence/index.ts`」？
>
> **建议**：**加**，但用最轻的形式（ESLint `no-restricted-imports` 一条规则）。
>
> **理由**：这条约束架构图表达不出来（步骤 02 已记录为发现项），而它正是「唯一入口」的**唯一机制保障**。本步骤做完后 `localStorage` 只剩一处，正好是把边界**焊死**的时机。
>
> ⚠️ 注意：测试文件当前**需要**绕过 `index.ts` 直连 `medium/`（步骤 02 的 `resetMediumForTests` 所致）—— 规则需为测试开这个口子，否则会与既有测试冲突。
