# 02-持久化层抽取与图数据迁移

---

## 1. 打通垂直切片：图数据经新分层落盘 ⏳

### 目标

把「图数据」这一类持久化**纵向打通**到新分层：调用点 → `coordination/` → `categories/` → `medium/` → localStorage 全链路可用，并**顺带消灭今天的三处静默缺陷**。

**完成后系统的状态**：

- `frontend/src/persistence/` 存在，含 `index.ts` / `coordination/` / `categories/` / `medium/` 四个条目。本步骤只落地目标态图（`docs/临时文档/persistence-子架构.md`）中的**图数据这一列**。
- 调用方读写图数据**只经 `persistence/`**，不再直接触碰 storage API。
- **写入失败不再静默**：配额溢出 / 介质不可用时，调用方拿到可判别的失败结果，UI 有可见提示。
- **torn write 的窗口被收窄，但未被消除**：整批序列化先行，故序列化失败不产生任何写入；写入阶段遇失败立即停止并回报，调用方不推进内存。**但 localStorage 无事务 —— 已写成功的条目不撤销，磁盘可能留下半写态，且下次启动会把它读成基线。真原子性由 P2 的 IndexedDB 事务兑现。**
- **内存与磁盘不再分歧**：落盘失败时内存状态不得单方面前进。
- 对用户而言**行为完全不变**（同一份数据、同一批图谱、同样的启动恢复），唯一差别是失败时不再无声。

### 1.1. 骨架与结果类型

**子目标**：

- 建 `frontend/src/persistence/` 与三个子目录，以及 `index.ts` 公开面。
- 定义**统一的结果类型**（读写各一族：成功 / 缺失 / 损坏 / 配额 / 介质不可用），作为本层所有公开函数的返回形状。
- 定义**跨类别变更的联合类型**（本步骤只含图数据一支），**不导出**出本层。

**关键约束**：类型名与判别字段按**最终形态**一次定对，避免 P2 异步化时二次改签名。

- 不确定度：低（结构已定）
- 算法复杂度：低
- 工作量：低

### 1.2. 图数据类别与 localStorage 介质

**子目标**：

- `categories/graph_data.ts`：承接现有图数据部分的**全部行为**（键方案 `graph:<id>`、序列化、判别联合、按 id 读 / 写 / 删 / 列出），并改为**委托介质**而非直接调用 storage API。
- `categories/view_state.ts`：把视图状态的三个函数（`saveLastActiveRootId` / `loadLastActiveRootId` / `clearLastActiveRootId`）**原样搬入**，签名与行为不变 —— 它们本属 §2 的范围，但本步骤要删掉旧文件，故只能一并落位。§2 再做真正的收编（并入导航卡片位置 + 键合并 + 改 API 形状）。
- `medium/local_storage.ts`：按 key 存取字符串的最小实现，并把介质异常翻译成本层结果类型。
- 迁移当前的**惰性父链补读**与**启动全量读取**到新位置。

**关键约束**：`categories/` **不得出现** storage API 标识符（子架构文档里那条 `s.t.` 契约）。

- 不确定度：低（行为是搬迁，不是新写）
- 算法复杂度：低
- 工作量：中

### 1.3. 批量提交入口

**子目标**：

- `coordination/commit.ts`：提供**单一变更入口**，一次接收「新增/更新哪些图 + 删除哪些图」，内部按介质能力组织写入。
- 取代今天 `graph_store.ts` 里「推导 affectedGraphIds → 逐图 save/delete」的循环。
- 写入失败时返回可判别的失败结果，并**不得**让内存状态单方面前进。

**为什么这是核心**：它是**收窄 torn write 窗口**与**消除会话内内存/磁盘分歧**的落点，也为 P3 加操作日志时的跨类别原子性预留了入口形状。本步骤先只有图数据一支，但入口形状一次定对。**注意：P1 的介质无事务，磁盘半写态仍可能（见「目标」里的如实说明）。**

- 不确定度：中（唯一动到写入路径的地方，需保证校验失败时不落盘、成功时语义不变）
- 算法复杂度：低
- 工作量：中

### 1.4. 调用点迁移

**子目标**：

- 迁移**生产代码 5 处**（`graph_store.ts` / `utils/graph_tree.ts` / `use-case/useNavigation.ts` / `use-case/useLifecycle.ts` / `dev/test_case_factory.ts`）与**测试 13 处**（`graph_persistence`、`graph_store`、`undo_redo`、`use-case/*`×3、`feature-tools/**`×5、`tests/integration`）。
- **删除旧文件** `frontend/src/graph/graph_persistence.ts`（不留转发层、不留别名 —— 见 Q5）。

**关键约束**：本步骤保持同步签名，故测试的「先 save 再 load」假设不变，迁移以改 import 路径为主。

- 不确定度：低（机械迁移，但面广）
- 算法复杂度：低
- 工作量：**高**（18 个文件）

### 1.5. 写失败的用户可见反馈

**子目标**：

- 选定失败反馈通道（见 Q4），把落盘失败送达用户，且不与「业务校验失败」混为一谈。
- 今天的行为是：`QuotaExceededError` 同步抛出 → 穿到工具确认回调 → **UI 无任何提示**。
- 读侧损坏的既有通路（`reportCorruptedGraph` 走开发者通道）不变，本步骤只新增**写侧**反馈。

- 不确定度：中（通道选型牵涉 `AGENTS.md` 已有的错误模式约定）
- 算法复杂度：低
- 工作量：中

### 影响范围

**新旧架构对比**（重构类要求）：

```text
【旧】持久化散落在 graph 层内部，且一个文件混三类职责
frontend/src/graph/
  ├── graph_store.ts         — 既持状态，又直接调 saveGraph / deleteGraph
  ├── graph_persistence.ts   — 图数据 + 视图状态 + 1 个域查询混在一个文件（~220 行）★删除
  ├── utils/graph_tree.ts    — 直接调 loadGraph
  └── use-case/*.ts          — 直接调 loadGraph / listSavedGraphIds / lastActiveRootId
frontend/src/composables/useDragPosition.ts — 直写 localStorage ← 本步骤不动（§2 收编）

【新】持久化抽成独立层，调用方只经唯一入口
frontend/src/persistence/                     ← 新增
  ├── index.ts                                — 公开面
  ├── coordination/commit.ts                  — 批量提交
  ├── categories/graph_data.ts                — 图数据
  ├── categories/view_state.ts                — 视图状态（原样搬入，§2 再收编）
  └── medium/local_storage.ts                 — localStorage

frontend/src/graph/                           ← 调用点迁移到 @/persistence
  ├── graph_store.ts                          — 写入改经 commit
  └── utils/ + use-case/                      — import 路径迁移
```

**本步骤新增 5 个文件、删除 1 个文件**：`persistence/{index.ts, coordination/commit.ts, categories/graph_data.ts, categories/view_state.ts, medium/local_storage.ts}`；删除 `graph/graph_persistence.ts`。

### 决策项

**已确定决策**：

- **分层形态照 `docs/临时文档/persistence-子架构.md`**（唯一入口 + 四条目）。
- **API 用领域类型**（`loadGraph(id)` / `commitGraphs(...)`），**不用「按键读写」** —— 键是介质的 API，不是这一层的 API。
- **`categories/` 不知道介质是谁**；介质访问只允许出现在 `medium/`。
- **本步骤保持同步签名、只落 localStorage**；异步化与 IndexedDB 留给 P2。
- **数据丢失不可接受**，故「写失败可见化」是**必交项**，不是可选优化。
- **不写兼容 / 版本迁移代码**，本步骤不引入格式版本号。
- **本步骤不改项目级 `AGENTS.md` 的架构图**（见 Q7）。

**待确定决策**：**无** —— Q1–Q9 已全部敲定（2026-09-20）。

**敲定记录**：

> **Q1**（含批量入口）：**包含** `commitGraphs`。它是**收窄 torn write 窗口**与**消除会话内内存/磁盘分歧**的落点，且与现有调用点形状天然吻合（`graph_store.ts` 本就是「先算 affectedGraphIds 再循环」）。入口形状一次定对，比 P2 再改一次签名 + 调用点便宜。

> **Q2**（公开 API）：**定稿**为下表，且**本步骤只实现打通链路所需的最小子集**：
>
> ```text
> loadGraph(id)                                                          → 判别联合（迁移）
> commitGraphs({ upserts, deletes })                                     → 结果类型（新增）
> listGraphIds()                                                         → ReadResult 迁移
> listRootGraphIds()                                                     → ReadResult 迁移，标注「待归位」
> saveLastActiveRootId / loadLastActiveRootId / clearLastActiveRootId    → 原样搬入（§2 再改造）
> （P3 预留）commit 的操作日志分支 / loadOperationLog(rootGraphId)
> （§2 预留）loadViewState / saveViewState
> （§3 预留）exportGraphs / importSnapshot
> ```

> **Q3**（统一结果类型）：**引入**。`saveGraph(graph): void` 是写失败静默的根因 —— 签名里根本没有「失败」的表达方式。且对调用点非破坏性（忽略返回值仍可编译）。

> **Q4**（失败反馈通道）：**新开状态位**，**不复用** `lastValidationResult`；UI **并入现有错误面板位置，存储错误优先于业务校验错误**，按最高等级（`accent="red"`）呈现。
>
> 事实依据：`NotificationPanel` 是纯展示壳（只有 `visible` / `accent: 'red' | 'blue'` / `closable`），**没有级别与推送接口**；而 `Graph.vue` 已有两个面板且都是 `position: fixed; bottom: 20px` —— **新增第三个会重叠**，故不新增面板。

> **Q5**（旧文件）：**直接删除**，同步改全部调用点。项目 `AGENTS.md` 明令禁止标识符别名与「为同一概念维护两个名字」，转发层正是这种别名。

> **Q6**（`listRootGraphIds`）：**原样搬进** `categories/graph_data.ts`，函数上方标注「待归位」。它反序列化全库图读 `kind`，属域查询而非存储职责；混在一起会让「抽取」与「归位」互相污染。

> **Q7**（`AGENTS.md` 架构图）：**本步骤不改**。属文档变更，且那张图牵连 `FOR-AGENTS/分层森林图详细规则.md` 的校验，宜与代码改动分开审查。

> **Q8**（视图状态三函数）：**本步骤原样搬进** `categories/view_state.ts` —— 签名与行为不变，仅改 import 路径；§2 再做真正的收编。
>
> 理由：本步骤删除旧文件，若把视图状态留在 `graph/`，「唯一入口」当期就不成立，且 §2 要多搬一次。

> **Q9**（写失败 UI 落点）：**并入现有错误面板位置，存储错误优先**。不新增面板、不引入层叠策略。
>
> 边界：本步骤只加**一个状态位 + 一条优先级规则**，**零视觉设计投入** —— 现有面板的样式、布局、动效一律不改。

**另有两处按建议执行**（若有异议请提出）：

- `useNavigation.ts` 的直连 `deleteGraph` → 改走 `commitGraphs({ deletes: [graphId] })`（公开面没有单条删除函数；协调层对单类别写的逻辑开销为零）
- `graph_persistence.test.ts` 随旧文件删除，其判别联合用例迁至 `categories/graph_data.test.ts`
