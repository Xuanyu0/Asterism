## 1. 目标：P3 要落地什么 ⏳

### 转述：目标态图对 P3 的定义

| 阶段 | 落地目标态图的哪些部分 |
| --- | --- |
| **P3** | `categories/operation_log.ts`；**切根图树的行为从「重置日志」改为「加载该树的日志」** |

**P3 只在 `categories/` 内扩** —— 这是「类别可增删」这条设计的可视化验证。

**键方案**（目标态图明文）：`oplog:<rootGraphId>` —— **每棵根图谱树一份操作日志**。

### 完成后系统的状态

- 操作日志**按根图谱树为键**持久化（刷新不丢）；
- **切根图树 = 加载该树的日志**（现在是**重置**）；
- **跨类别原子提交**：一次用户操作同时改图数据与日志 → `coordination/` 增加日志分支 → 二者**同成同败**。

## 2. 为什么必需（目标态图的论证，原文转述）

- **操作日志与图数据在语义上都算权威源**：操作日志原则上足以推导出图数据（沿 `parentIndex` 链回放）；两类都持久化是为了**性能**与**行为直观**，不是为了正确性所必需。
- **这正是它们必须保持一致的理由** —— 冗余的两份表示，一旦不同步，**冗余就变成了分叉**。因此原子提交是**必需的，而不是优化**。
- 而「一次用户操作同时改两样东西」**跨了两个类别**；`categories/` 的契约是「每类数据自持、互不知晓」→ 这个跨类别职责**必须在类别之上**（`coordination/`）。

## 3. 数据模型（已存在，且可序列化）

`packages/graph-engine/src/types/operation_log.ts` —— 两层模型：操作树（细粒度，自动记录）+ 状态标签（粗粒度，用户显式提交）。

| 类型 | 内容 | 关键约束 |
| --- | --- | --- |
| `OperationLogTree` | `entries: CommitLog[]` + `cursor` | 沿 `parentIndex` 链上溯到根 = 当前历史路径 |
| `CommitLog` | `batches` + `reversalBatches` + `parentIndex` + `timestamp` + `source?` | **一次 `commitBatchToGraphs` = 一条 entry = 一次回溯单元** |
| `BatchesLog` | `graphId` + `operations` | 按图分组 |
| `State` | `cursor` + `summary` + `timestamp` | **不存 GraphData 副本**，仅游标 + 摘要；回退 = 跳游标 + 沿链回放 |

均为扁平数组 + 索引 → **可序列化**，无需额外转换。

## 5. 问题背景（为什么需要这一步）

1. **「历史思维变迁」是产品核心价值** —— 操作日志是**本体**，不是调试附属。内存版刷新即失，无法承载这个价值。
2. **「树 = 日志」是由代码定义出来的事实**：`graph_store` 把**根图**定义为操作日志与 undo/redo 的边界（「根图谱 = 日志」）。步骤 05 的**森林级不变量**让「树 = 自洽的编辑历史单元」成立 —— 这才使「**按树为键**存日志」在语义上站得住（否则一次操作横跨两棵树，日志无法表达）。
3. **与步骤 06 的耦合**：跨类别原子提交要求所有写入经统一入口；`deleteGraphTree` / `findParentGraph` 仍绕过（详见步骤 06）。
