## 1. 确立校验判据 ⏳

### 目标

把「硬性不变量 / 软规则」的划分从**主观判断**变成**可判定的判据**，作为整个校验体系归位的依据。

**判据（候选，待定稿）**：

> **硬性 ⟺ 存在某个合法消费者，其契约要求该命题为真。**
> 软 ⟺ 违反后图仍可被正确解释与渲染，只是不合规范 / 不好看。

这与代码里已有的表述等价 —— `check_invariants.ts:6-9` 写的是「**违反后数据 / 引擎无法被正确解释或操作**」，而 `structural.ts`（硬性、恒跑、缺席配置面）与 `preferences.ts`（可开关）已经按这条线分过一次。

**产出**：一条写进代码 / 注释的**可判定判据**，取代主观表述。判据可判定，才能推出「某条规则能否被安全跳过」——**能不能跳是分类的推论，不是另加的一套机制**。

难度：

* 不确定度：中（判据措辞要经得起逐条核对）
* 算法实现复杂度：低
* 工作量：低

## 2. 在新判据下重新归置现有校验 ⏳

### 目标

逐条核对现有校验的**真实去向**，回答三个问题：

- 它**还有存在的必要**吗？（可否删除）
- 应该**拆分到具体调用方**吗？（判定留引擎、义务在调用方）
- 还是应该**下沉为一致的（引擎内）不变量校验**？

**为什么必须重审**：现在 Phase 1 / Phase 3 分的是「**时机**」（操作前前提 vs 结果图不变量），**不是**「硬 / 软」。硬 / 软目前只体现在 Phase 3 **内部**（硬性 `structural` vs 可开关 `preferences`）。而**软规则却住在 Phase 1、又不在任何开关表里** —— 这正是引擎必须提供布尔旁路 `skipValidate` 的**唯一原因**。

### 2.3 参考方案：`add_node` 效仿 `move_node`

`add_node` 的前端**已经做了一半** —— `add_node.ts:214-229` 消费 `collides` 加高亮、`:118-126` 已在 `onCanvasClick` 拒绝落定；引擎 Phase 1 那道只是 **backstop**，正是它逼出了 `skipValidate`。

改造方向（≠ 加模式开关）：

1. 引擎侧把软规则从 Phase 1 撤下（`NODE_COLLISION` / `EMPTY_LABEL` / `EMPTY_TITLE` / `TITLE_DUPLICATE` …）；
2. **判定仍留引擎**（建议新增 `addNode` **compose 入口**，与 `moveNode` 同形，产 issue），保证判定单源、公式不漂移；
3. 调用方在写入前 **gate**（如 `add_node.ts:141-177` 的 `onConfirm` 目前**不** gate，需补）；
4. `skipValidate` 及其 store 透传链**整体退役**。

### 2.4 三个去向（本步骤要回答的核心）

| 去向 | 适用 | 说明 |
| --- | --- | --- |
| **保留**（引擎硬校验、无开关） | 硬规则 | 不可绕过；对齐 FHIR「error 不可 suppress」 |
| **拆分到调用方**（判定留引擎） | 软规则 | 义务在调用方；漏 gate 的后果只是「不好看」，不是脏数据 |
| **下沉为一致的不变量校验** | 时机轴归位 | 把「结果图性质」的检查统一收进 Phase 3，Phase 1 只留真正的「操作前前提」 |

### 决策项

**已确定决策**：

- 判据方向：**硬 ⟺ 被消费者依赖**（本步骤由用户确立）。
- 归属原则：**判定在引擎（单一事实源），义务在调用方，且仅限软规则**。
  理由：「业务规则校验下沉 GE、前端不散落」这条规则针对的是**不可绕过的业务规则**；软规则本来就可被绕过，漏 gate 只导致「不好看」，故不需要收口。
- 目标态：引擎**不提供**布尔校验旁路（`skipValidate` 退役）。
- 预览**不写持久化**（`preview_engine.ts` 用 `structuredClone`）—— 这是「软规则可安全跳过」的强前提：硬规则的消费者（持久化 / 撤销重放 / 导出）**只在提交路径**上。

**待确定决策**：

> **Q1**：判据的最终措辞？（「存在某个合法消费者，其契约要求该命题为真」是否足够可判定？）
>
> **Q2**：`DANGLING_REFERENCE` / `SELF_LOOP_FORBIDDEN` / `DUPLICATE_EDGE_FORBIDDEN` 归硬还是软？（需逐条核对真实消费者）
>
> **Q3**：软规则的**判定**放哪层？引擎 compose 入口（新增 `addNode`，与 `moveNode` 同形）还是 infrastructure 原语（`hasCollisionAt`）+ 调用方自查？
>
> **Q4**：Phase 1「前置校验」这一层是否还有整体存在的必要？若「时机轴」与「性质轴」正交，其中真正属于「操作前前提」的还剩哪些？

## 附：本轮外部调研要点（供规划时引用）

结论（每条均有出处，详见本轮 librarian 报告）：

- **两级划分是成熟共识**：DDD 的 invariant vs validation（判据：违反后还能不能被当成该类型解释）；CAD / 约束求解的 hard vs soft constraints；FHIR 的 error vs warning / guideline；解析器的 strict vs lenient。
- **「按模式分档」业内确实有**（`kubectl --validate strict|warn|ignore`、React Hook Form `mode`、Ajv strict mode），但**「validation profile」不是通用术语**（建议用 validation mode / level）。
- **三条反面教训**：① Fowler《Flag Argument》——布尔 flag 让函数有两种行为，应改独立方法 / 显式值对象；② JSON Schema 的 `format` 断言**默认关闭** → 实践中大量实现不校验，**默认关的开关约等于没有**；③ K8s `ignore` 会 **silently dropping fields** —— 旁路会静默丢数据。
- **正面先例**：FHIR 的 `suppress` **只允许压制 warning / guideline，不能压制 error**（硬性不提供开关）；Rust `unsafe` + safety contract、ProseMirror 只允许**被命名的窄用途**非法 —— 都是「具名边界」而非模式开关。
- **预览态没有单一主流**：影子副本（Unity Prefab Mode / RTK optimistic）、同一模型承载中间态（Excalidraw / tldraw / Figma / Onshape）、原子提交（ProseMirror / CodeMirror）、按需显式校验（FreeCAD / Blender）四种都有。**图形编辑器敢用「同一模型」，正因「重叠」不是它们的 invariant。**
